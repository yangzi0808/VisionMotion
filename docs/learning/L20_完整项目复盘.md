## 1. 项目到底解决什么问题

### 1.1 一句话目标

VisionMotion 的目标是：**利用普通摄像设备进行非接触式位移 / 振动测量**。

也就是说：

- 不接触被测物体、不用专业传感器（加速度计、激光位移计、应变片）；
- 只用普通相机 / 手机拍摄的视频 + 可解释的图像处理；
- 把画面里目标的位置变化提取成**时间序列**，再回答"移动了多少 / 振动多快 / 周期多长 / 频率多少"。

这条目标线（【概念解释】）可以压缩成一句话：

```text
像素位置序列  →  （标定 + 基准 + 投影）  →  物理位移序列  →  运动参数（周期 / 频率 / FFT 交叉验证）
```

### 1.3 项目不是什么

【概念解释】为了不夸大项目，本课明确记录：

- 项目**不是**工业测量系统，没有精度验收、没有计量校准、没有环境控制；
- 项目**不是**算法研究，不使用深度学习 / YOLO / 卡尔曼 / 光流（`src\video_tracker.py` 第 18 行注释明确排除）；
- 项目**不是**"全自动"：M4 的标定点是人工点击（`demo\pick_calibration_points.py`），M6 的参数是人工冻结的；
- 项目的价值在"**整条链路能跑通、每一步能解释、结果能复现**"（README 第 15 行）。

## 5. 检测 vs 测量：两个不同的问题

【概念解释】这是整个项目最重要的一次视角切换：

| 问题 | 含义 | 项目中的回答 | 输出单位 |
| --- | --- | --- | --- |
| **检测（Detection）** | "目标在哪里？" | `detect_marker()` → 质心 `(cx, cy)`（`src\marker_detector.py` 第 100～101、143～151 行）；M6 `detect_dark_band()` → `y0_px`（`src\external_oscillation_tracker.py` 第 243 行） | 像素（px） |
| **测量（Measurement）** | "目标移动了多少？" | `s = x·ux + y·uy`（第 204 行）→ `ds_px = s - s0`（第 378 行）→ `ds_mm = ds_px / PX_PER_MM_004`（第 379 行） | 先是 px，标定后是 mm |

两个关键结论：

1. **像素坐标本身不是物理位移。** `x_px = 852.81` 只回答"目标出现在画面的哪一列"，它随分辨率、相机位置、镜头焦距、画面裁剪一起变化；它不能直接说"目标移动了 3.2 px 的物理距离"，更不能说"移动了 0.53 mm"。
2. **从检测到测量的四步缺一不可。** ② 记录（CSV）→ ③ 有效性（valid gate）→ ④ 投影（把二维压成一维）→ ⑥⑦ 差分 + 标定（`s - s0` 再除以 px/mm）。缺任何一步，`ds_mm` 都不成立。

【真实数据】同一个"检测结果"在两个问题下的读法（EXP-004）：

| 行 | 检测（在哪里） | 测量（移动多少） |
| --- | --- | --- |
| frame 0 | `x_px=852.81, y_px=208.63` | `ds_px=-3.215, ds_mm=-0.5283`（相对 s0 的基准侧） |
| frame 300 | `x_px=985.11, y_px=218.89` | `ds_px=129.043, ds_mm=21.2019`（相对 s0 的正侧） |

【概念解释】为什么 M6 只停在"检测"层面（更准确地说：M6 完成了"检测 + 时域周期测量"，但没有完成"毫米测量"）：M6 没有 px/mm 标定，所以它的位置量 `y0_px` 只能以像素为单位参与后续峰谷 / 周期分析（第 9 节）。

## 6. detected vs valid：两层状态，缺一不可

【概念解释】项目把"帧状态"拆成两层：

- `detected`：视觉检测层——这一帧**找到目标了吗**（`src\video_tracker.py` 第 41 行字段；`build_csv_row()` 第 401～410 行）；
- `valid`：测量可用层——这一帧**能用于物理计算吗**（`src\displacement.py` 第 175～213 行；`src\dynamic_displacement.py` 第 183～222 行）。

八条必须记住的规则（全部有源码出处）：

| # | 规则 | 出处 |
| --- | --- | --- |
| ① | **检测失败不等于程序崩溃**：检测器返回 `{"success": False, "mask": mask}`，主循环继续跑完整个视频 | `src\marker_detector.py` 第 133、137 行；`src\video_tracker.py` 第 527～530 行注释"正常结束，不因为单帧失败中断" |

### 7.2 必须背下来的一条区分：ds 正负 vs Δds 正负

【概念解释】

- **`ds` 的正负表示"位置在哪一侧"**：`ds > 0` 表示目标位于基准的 P1→P2 方向一侧；`ds < 0` 表示位于另一侧；`ds = 0` 表示恰好回到基准。它是**状态**。
- **`Δds` 的正负才表示"运动方向"**：`Δds = ds_i - ds_{i-1} > 0` 表示沿正方向移动；`Δds < 0` 表示沿负方向移动。它是**变化**。

【教学示例】（明确标注：教学示例，不是项目数据）设某一小段 `ds_mm` 序列为 `-0.5, +2.0, +5.5, +4.0`：

| 量 | 值 | 读法 |
| --- | --- | --- |
| `ds` | -0.5 → +2.0 → +5.5 → +4.0 | 位置先从负侧走到正侧、继续增大、然后回落 |
| `Δds` | +2.5 → +3.5 → -1.5 | 运动方向：正向 → 正向 → 负向 |
| 结论 | 第 3 个数 `+5.5` 虽然 `ds` 为正，但此时已经在往负方向运动 | "ds 正"不等于"正在往正方向运动" |

【真实数据】M5 里同样的现象：frame 0 `ds_mm = -0.5283`（负侧）而 frame 300 `ds_mm = +21.2019`（正侧、正在正向移动）；f491 peak 之后 `ds_mm` 开始下降（转向）——位置持续为正，但运动方向已经反了。

## 8. M6 方法为什么不同

【项目真实源码】两条检测链并排对比：

| 对比项 | M5（自采、红色目标） | M6（外部、暗色条带） |
| --- | --- | --- |
| 颜色空间 | BGR → HSV（`src\marker_detector.py` 第 48 行） | BGR → grayscale（`src\external_oscillation_tracker.py` 第 315 行） |
| 分割方式 | 红色双区间 `inRange` + `bitwise_or`（第 51～55 行） | 单阈值 `gray < 120`（第 72、204 行） |
| 区域约束 | 全图搜索 | 先裁 ROI：x ∈ [690, 780)、y ∈ [380, 760)（第 66～69、203 行） |
| 形态学 | 3×3 开运算（第 58～61 行） | 不做形态学 |
| 目标定位 | 外部轮廓 `findContours` → 最大轮廓 → 图像矩质心（第 73～101 行） | 8 邻域连通域 `connectedComponentsWithStats` → 逐行跨度 → 最长连续段 → 几何筛选 → **暗带上缘**（第 205～252 行） |
| 位置特征 | 质心 `(x_px, y_px)`（二维） | `y0_px` = 暗带上缘（一维，物理方向明确） |
| 输出字段 | 6 列（含 x 与 y） | 8 列（含 `x_px` 只作 QC、`y0_px` 是正式位置、bbox 与面积作 QC；第 88～97 行） |

【概念解释】为什么必须换方法（"不同视觉目标需要不同检测策略"）：

1. **目标的视觉特征根本不同。** 自采目标是"颜色鲜明的红色标记"，HSV 颜色分割非常有效；外部视频里根本没有红色标记，目标是一条**暗色条带**，信息在"亮度 + 几何形状"里，不在颜色里。
2. **同一假设不能跨数据复用。** M6 视频的照明、背景、遮挡都无法控制；如果硬套红色检测器，会把整个画面判成"无目标"。
3. **几何先验是可验证的替代方案。** M6 用"ROI + 阈值 + 连通域 + 行宽带 + 几何筛选"把目标限制在"宽度 40～75 px、高度 ≤ 15 px 的暗带"上，这套规则来自 M6.2-2B 的人工冻结，不是运行时自适应（第 74～82 行）。
4. **源码从结构上隔离两条链。** M6 模块的第 34 行明确禁止"调用红色目标检测器（`src\marker_detector.py`）"；M5 模块的第 20～23 行明确禁止把 M4 常量搬进来。**"不要混用"不是口头纪律，而是写进注释和 import 结构里的约束。**

### 10.3 df = fs / N：FFT 的频率格点是怎么来的

【概念解释】FFT 的输出不是一个连续频谱，而是一排**格点**：

```text
df = fs / N            （频率分辨率，单位 Hz）
f_k = k · df           （第 k 个格点，k = 0 … N/2）
```

M6 的真实采样参数（【真实数据】：`src\external_oscillation_tracker.py` 第 61～63 行；报告第 60、181 行；README 第 46～47 行）：

| 量 | 值 | 来源 |
| --- | --- | --- |
| 采样率 `fs` | 30 Hz | M6 视频属性（30 fps） |
| 正式区间帧数 `N` | 160（frame 76～235） | 第 61～63 行 `EXPECTED_FRAME_ROWS = 160` |
| 记录长度 `T_record` | `N / fs = 160 / 30 = 5.3333 s` | 报告第 181 行（首末时间戳差另有 159/30 = 5.3000 s 的口径） |
| 频率格点 `df` | `30 / 160 = 0.1875 Hz` | 报告第 180 行 |
| 1.875 Hz | `10 × 0.1875` → 恰好在 k = 10 格点上 | 【真实数据】 |
| 1.843003 Hz | `1.843003 / 0.1875 ≈ 9.8293` → **不位于格点**，最近格点是 1.875 Hz（距离 0.031997 Hz） | 【真实数据】+【概念解释】 |

### 10.4 为什么会有频谱泄漏，FFT 又为什么只是"交叉验证"

【概念解释】

1. **非整数周期截断。** 记录内包含约 `1.843003 × 5.3333 ≈ 9.83` 个周期——不是整数个周期。把这段信号做周期延拓时，首尾接不上，边界出现跳变；
2. **能量扩散。** 这个边界不连续会让主频能量"漏"到邻近格点上，这就是**频谱泄漏**；1.875 Hz 与 1.843003 Hz 的 0.031997 Hz 差值正是格点化 + 泄漏共同造成的表观差；
3. **差值 < 半格。** 半格 = `0.1875 / 2 = 0.09375 Hz`；`0.031997 Hz` 远小于半格，相对差 `0.031997 / 1.843003 ≈ 1.74%` 也小于半格对应的 ≈5.09%——因此两个数字属于"同一数据上的两种方法在分辨率范围内一致"；
4. **FFT 只做交叉验证。** 报告第 185 行原文："FFT 仅作为独立的频域交叉验证，不替代时域峰—峰周期测量；本报告的中心频率取自时域结果。" 第 186 行进一步说明"不能把 1.875 Hz 视为比 1.843003 Hz 更'正确'"。

【教学示例】本课不做任何新的 FFT 演示（任务边界禁止重算 FFT）。要练习"格点 / 泄漏"，请使用 L18 / L19 已有的教学示例，那些示例均已显式标注"不是项目数据、不是项目代码"。

## 15. 一套通用代码阅读方法

【概念解释】下面这套"六步法"是 L01～L20 反复使用的读代码流程；它不只适用于 VisionMotion，也适用于以后阅读任何 Python / 计算机视觉项目。

```text
【概念伪代码】（流程描述，不是任何项目的真实源码）
第 1 步  找入口：哪个文件是"能跑"的？入口函数在哪里？
第 2 步  找输入：它读什么文件？怎么读？读之前有没有检查？
第 3 步  找核心函数：把文件里的函数列成"输入 → 处理 → 输出"清单
第 4 步  追踪一个真实数据：拿一行真实数据，手工走完整条链
第 5 步  找输出：它写什么文件？字段是什么？写到哪里？
第 6 步  最后看自检和失败处理：错了会怎样？失败会静默吗？
```

### 第 1 步：找入口

- VisionMotion 的入口不是 `src\`，而是 `demo\`：每个阶段一个"无参数脚本"（README 第 96～107 行）；
- 读源码文件本身要找 `main()` 或 `if __name__ == "__main__"`：例如 `src\m63_final_visualization.py` 第 828～834 行、`src\m73_presentation.py` 第 674～696 行；
- 通用技巧：先看文件头 docstring（它通常写了"本模块只做 / 不做"——VisionMotion 的 8 个源码文件全部如此）。

### 第 2 步：找输入

- 搜路径 / 文件名字符串：`data/raw/...`（`src\dynamic_displacement.py` 第 51 行）、`results/...`（`src\m63_final_visualization.py` 第 44 行）；
- 看有没有"输入检查"：视频 SHA-256 校验（`src\external_oscillation_tracker.py` 第 281 行；`src\video_tracker.py` 第 428 行）、文件存在性检查（第 258～259 行）；
- 通用技巧：**输入检查的严格程度，往往就是这个项目的可信度上限。**

### 第 3 步：找核心函数

- 用"函数名 + 行号 + 输入 + 输出"列清单（本课第 3 节就是一次完整示范）；
- 注意"唯一来源"注释：检测唯一来源、投影唯一来源、参数唯一来源（`src\video_tracker.py` 第 19～21 行；`src\displacement.py` 第 20 行）；
- 通用技巧：一个文件如果有两个函数做同一件事，先怀疑它们是历史遗留——VisionMotion 用"结构性禁止 import"避免混用（`src\dynamic_displacement.py` 第 22～23 行）。

### 第 4 步：追踪一个真实数据

- 选**第一行真实数据**（frame 0）手工走一遍：`852.81 / 208.63 → 851.987 → -3.215 → -0.5283`（本课第 4 节）；
- 再选一个"中间帧"验证（frame 300：`985.11 / 218.89 → 984.246 → 129.043 → 21.2019`）；
- 通用技巧：**能跟着一个数字走完整条链，才算真的读懂了代码**；只看函数名不算。

### 第 5 步：找输出

- 找 `write` / `save` / `open(..., "w")` / `savefig` / `to_csv`：`write_ds_csv()`（`src\displacement.py` 第 398～411 行 / `src\dynamic_displacement.py` 第 408～421 行）、`write_trajectory_csv()`（第 357～397 行）、`save_figure()`（`src\m63_final_visualization.py` 第 281～297 行）、`prs.save()`（`src\m73_presentation.py` 第 669 行）；
- 看输出格式规范（列名、小数位数、空值写法）：`FIELD_PATTERNS`（第 84～90 / 103～109 行）；
- 通用技巧：**输出格式是"给别人复核"的接口**，读代码时要和读 CSV 时得到的印象互相印证。

### 第 6 步：最后看自检和失败处理

- `check_csv_data()`（`src\video_tracker.py` 第 643～824 行）：行数 / frame 连续 / 字段完整性 / 越界 / `time_s` 时间轴 / 失败字段语义；
- `check_ds_csv()`（`src\displacement.py` 第 597～796 行 / `src\dynamic_displacement.py` 第 931～1174 行）：gate 复算、s0 复算、公式复算、空值规范；
- `check_presentation()`（`src\m73_presentation.py` 第 563～630 行）：页数、文字、禁用词、溢出；
- 通用技巧：**先问"如果这一步失败会发生什么"，再相信"它跑通了"。** "不写 0 / 不删行 / 不插值"这些纪律，全部是在"失败处理"这一层实现的（第 6 节）。

### 为什么这套方法可迁移

因为它的顺序与项目语言无关：入口 → 输入 → 核心函数 → 真实数据 → 输出 → 自检，本质上是在回答"**这个程序相信什么、忽略什么、保证什么**"。换成任何 Python / 计算机视觉项目，只要照着这个顺序走一遍，就能在建图之前先建立正确的数据流直觉。

## L20 核心结论

1. **VisionMotion 本质上是一条"从视觉检测到物理测量、再到运动分析"的数据流水线**：图片 / 视频 → 解码成帧 → 检测 → 像素位置 → CSV → 有效性判断 → 标定 → 一维投影 → `s` → `s0` → `ds_px` → `ds_mm` → 转向点 → 运动段 →（周期 / 频率 / FFT）→ 可视化 → 报告 / PPT。
2. **检测得到的是像素位置；只有经过标定、投影与基准（s0）之后，才得到"位移"。** `ds` 的正负表示位置在哪一侧，`Δds` 的正负才表示运动方向；M5 的转向点 / 运动段是运行时能力，"周期候选"只是课程只读分析。
3. **当前 M6 的周期、频率与 FFT 属于冻结分析结果，不是运行时代码。** 冻结值：`f_exp = 1.843003 Hz`、`f_FFT = 1.875 Hz`、`df_fft = 0.1875 Hz`；当前仓库没有可执行的 FFT / 窗函数 / 补零 / 去趋势 / 重采样实现，也没有实际频谱数组。
4. **当前最大的工程问题之一是"文档漂移"：M2 / M3 数据已于 2026-10-03 替换并重跑（689,023 B 图片 / 4,624,268 B 视频 / 170 帧 / 24 fps），但 README 与 CHANGELOG 仍描述旧数据（952 帧 / 60.1248 fps），且这些变化尚未提交 Git。** 源码没有变化；变化的是输入、结果与"尚未跟上"的文档。
