## 2. 本节课总路线

本节的知识沿下面这条路线一步一步搭起来（这也是课堂上的主线）：

```text
像素 Pixel
   ↓
数组 NumPy Array
   ↓
颜色（BGR）
   ↓
颜色空间 Color Space（BGR → HSV）
   ↓
阈值条件 Threshold（红色双区间）
   ↓
Mask（inRange + bitwise_or 的逐像素结果）
   ↓
Contour（本节只学到：Mask 是 Contour 的输入）
```

一句话概括这条路线：**先把画面变成数字（像素 → 数组），再把数字变成颜色描述（BGR → 颜色空间 → HSV），然后把"什么算红"写成明确的数值规则（阈值），用逐像素运算把规则应用出去（Mask），最后把 Mask 交给下一步（Contour）。**

## 3. Pixel：像素

### 3.1 像素是什么

一个数字图像可以理解成由大量小方格组成。**每个小方格就是一个像素（Pixel）。**

- 像素是数字图像**最基本的数据单位**；
- 每个像素记录它所处位置的颜色 / 亮度信息；
- 一个像素并不是"看起来像什么"，而是**一组数字**。

### 3.2 计算机为什么要把连续的视觉世界离散成像素和数字

真实世界的视觉信息（光、颜色、亮度）本来是**连续**的：空间中每一点都有颜色，光强可以取无限多个中间值。

而计算机只能存储和处理**离散的数字**，所以必须做两件事：

1. **空间上离散化**：把画面切成有限多个小方格——每个小方格就是一个像素。图像不再是"无穷多个点"，而是"有限个格子"；
2. **数值上离散化**：每个像素的颜色 / 亮度用有限范围内的整数记录（例如 0～255 之间的整数），而不是无限精度。

做完这两件事以后，计算机就有办法用一张"数字表格"来表示画面，"看图"问题因此变成了"算数字"的问题。

代价是：像素是**采样**结果，格子与格子之间的信息计算机并没有记录。像素越密（分辨率越高），画面越接近连续世界——但永远只是"更接近"，不是"变成连续"。

这也是本项目后面一切测量都发生在"像素位置"上的根本原因：计算机看到的画面，本来就是离散的数字网格。

## 4. NumPy Array：图片为什么是数组

### 4.1 彩色图片 = NumPy 数组

彩色图片在 Python / OpenCV 中可以表示为一个 **NumPy 数组**（`numpy.ndarray`）。

课程中用一个例子来说明数组的形状（**教学示意，不是项目实际数据**）：

> 一张 100×80 的彩色图，在数组中的形状是 **(100, 80, 3)**。

三个维度分别表示：

| 维度 | 数值 | 含义 |
| --- | --- | --- |
| 第 1 维 | 100 | **高度 / 行数**（高度是 100 个像素） |
| 第 2 维 | 80 | **宽度 / 列数**（宽度是 80 个像素） |
| 第 3 维 | 3 | **每个像素的 3 个颜色通道** |

注意：数组 shape 的书写顺序是 **(高度, 宽度, 通道)**，不是日常说话习惯的"宽 × 高"。这是看图、写代码时都要小心的一点。

### 4.2 访问一个像素：img[y, x]

必须记住一个非常重要的编程细节：

```python
img[y, x]      # 正确
img[x, y]      # 错误（行列写反）
```

**先写行 y，再写列 x。**

- y 是行下标：0 在最上面，向下增大；
- x 是列下标：0 在最左边，向右增大；
- 所以 `img[0, 0]` 取的是**左上角**那个像素。

这与第 1 课学过的"图像坐标 y 向下增大"完全一致。

### 4.3 数据格式：uint8 与 0～255

典型的 8 位图像数据使用 **`uint8`** 存储：

- `uint8` = 8 位无符号整数，一共能表示 2⁸ = 256 个取值：**0～255**；
- 单个通道的取值范围通常是 **0～255**；
- 0 表示该通道"没有强度"，255 表示"最大强度"。

一个 3 通道像素因此是**三个 0～255 的数字**组成的列表，例如 `[0, 0, 255]`。

## 5. BGR

### 5.1 OpenCV 默认是 BGR

OpenCV 读取彩色图像时，默认使用的通道顺序是 **BGR**：

- 一个像素写作 **(B, G, R)**（蓝、绿、红）；
- **不是** (R, G, B)（红、绿、蓝）。

### 5.2 真实源码定位（第 110 行附近的输入说明）

这个事实不是凭印象说的，它就写在项目源码里：

```text
文件：src\marker_detector.py
函数：detect_marker(image_bgr)（输入说明，第 110 行附近）
源码：image_bgr —— 用 cv2.imread 读进来的 BGR 图像
```

也就是说，`detect_marker` 收到的输入，就是"OpenCV 读进来、并且已经被源码明确标注为 BGR"的图像。

### 5.3 典型数值示例（BGR 顺序）

| BGR 数值 | 颜色 |
| --- | --- |
| (0, 0, 255) | 纯红（红色分量拉满，其余为 0） |
| (255, 0, 0) | 纯蓝（蓝色分量拉满，其余为 0） |
| (0, 0, 0) | 黑（三个通道都为 0） |
| (255, 255, 255) | 白（三个通道都拉满） |
| (0, 0, 128) | 暗红（红通道为中等强度 128，不是纯红） |

**最容易犯的错**：按 RGB 习惯把第一个数字当红色。请反复默念：OpenCV 里第一位是 B（蓝），最后一位才是 R（红）。

## 6. Color Space

### 6.1 颜色空间是什么

颜色空间（Color Space）可以理解成**"描述颜色的一套坐标 / 记账方式"**。

同一个颜色，可以用不同的方式描述：

- **BGR**：用蓝色、绿色、红色三个通道的**强度**描述颜色；
- **HSV**：用**色相（Hue）、饱和度（Saturation）、明度（Value）**描述颜色。

### 6.2 一句必须记住的话

> 同一个颜色可以使用不同的颜色表示方式。颜色空间改变的是**表示方法**，不是**物体本身**。

就像同一个地点，可以用"经纬度"描述，也可以用"距某地多远"描述——描述体系换了，地点没有变；红色物体转成 HSV 之后，它还是那个红色物体，只是记录方式换了。

另外，通道顺序问题（BGR vs RGB）和颜色空间问题（BGR vs HSV）是两件事：前者是"三个数字的排列顺序"，后者是"用什么量来描述颜色"。本节把两件都遇到了，要分清楚。

## 7. HSV

### 7.1 H / S / V 分别回答什么

完整记录三个分量的含义：

| 分量 | 全称 | 回答的问题 | 通俗理解 |
| --- | --- | --- | --- |
| H | Hue = 色相 | "**是什么颜色？**" | 色环上的**位置** |
| S | Saturation = 饱和度 | "**颜色有多浓？**" | 颜色浓不浓（越浓越鲜艳，越淡越接近灰白） |
| V | Value = 明度 | "**有多亮？**" | 亮不亮（越暗越接近黑） |

课程使用的通俗类比就是：**H → 色环上的位置；S → 颜色浓不浓；V → 亮不亮。**

### 7.2 三问法的价值

当我们说"这是一个红色物体"时，其实同时说了三件事：颜色种类（红）、颜色浓淡（鲜红还是淡红）、明亮程度（亮红还是暗红）。

HSV 把这三件事**拆成三个独立的数字**分别记录；BGR 则是把三者混在蓝、绿、红三个强度里。这就是后面"为什么按颜色筛选要用 HSV"的直接原因。

### 7.3 OpenCV 中 H 的范围：0～179

必须记住：

> OpenCV 8 位 HSV 图像中，**H = 0～179**。

课程中的解释是：色相本来是一个 0°～360° 的**角度**，OpenCV 在 8 位图的存储中把角度缩放了一半，因此可近似理解为：

```text
H = 色相角度 / 2
```

对应示例：

| 色相角度 | H（OpenCV 8 位） |
| --- | --- |
| 0° | 0 |
| 340° | 170 |
| 358° | 179 |

所以写 HSV 区间时，H 的上限是 **179**，不能写成 359。S、V 则在 0～255 范围内。

## 8. 为什么 VisionMotion 使用 HSV

### 8.1 同一红色物体在不同光照下 BGR 数值会变化

课程用一组直觉例子说明这件事（**教学示例，不是项目实际数据**）：

```text
亮环境下：BGR ≈ (40, 40, 220)
暗环境下：BGR ≈ (20, 20, 140)
```

同一个红色物体，BGR 的**三个数都可能发生变化**：变暗时整体数值缩小，颜色和明暗纠缠在一起。

因此，如果直接拿 BGR 写"什么算红"的规则，就会很别扭：红色范围要写得又宽又弯，还容易和别的颜色混在一起——**直接用 BGR 写规则不够直观**。

### 8.2 HSV 更适合把"颜色种类、浓淡、明暗"分开描述

HSV 把三件事拆开了：

- 红色"种类"主要由 H 描述（红色在色环上的位置基本稳定）；
- "浓淡"由 S 描述、"明暗"由 V 描述。

于是"筛红色"可以写成一个很直观的形式：**色相落在红色区间 + 浓淡不太淡 + 亮度不太暗**。这正是 VisionMotion 采用 HSV 的原因，也是 `create_red_mask` 第一步就做 BGR → HSV 的原因。

### 8.3 但不要误解为"完全消除光照影响"

必须强调两句话：

- HSV **可以帮助更方便地按颜色筛选**；
- 但**不能理解成"完全消除光照影响"**。

光照变化仍然会影响 S（颜色看起来浓淡不同）和 V（明暗不同），H 也可能发生一定漂移。所以项目里的红色阈值本质上仍然是**经验规则**：它在这个拍摄场景下有效，不代表在所有光照条件下都万无一失。

## 9. VisionMotion 的红色阈值

本节最重要的项目事实：VisionMotion 对"红色"的定义**不是猜的**，而是写在源码里的真实参数。

### 9.1 源码定位

```text
文件：src\marker_detector.py
位置：第 22～27 行（红色 HSV 阈值常量）
```

### 9.2 真实参数（照抄源码）

```python
RED_LOWER_1 = np.array([0, 100, 70])
RED_UPPER_1 = np.array([10, 255, 255])

RED_LOWER_2 = np.array([170, 100, 70])
RED_UPPER_2 = np.array([179, 255, 255])
```

### 9.3 通道顺序是 [H, S, V]

每个数组里的三个数字，依次是 **[H, S, V]**，所以：

| 区间 | H（色相） | S（饱和度） | V（明度） |
| --- | --- | --- | --- |
| 区间 1 | 0～10 | 100～255 | 70～255 |
| 区间 2 | 170～179 | 100～255 | 70～255 |

还可以读出两条"排除规则"：

- **S ≥ 100**：太淡、发白、发灰的像素被排除；
- **V ≥ 70**：太暗、接近黑的像素被排除。

### 9.4 为什么红色需要两个区间

H 是一个**圆环**（色相环）：0° 和 360° 是同一个位置。红色正好位于色环的**接缝附近**（跨越 0°/360°）。

因此在 OpenCV 0～179 的**线性表示**中，红色被分到了**两端**：

```text
H 0～10      （区间 1，接缝的"起点一侧"）
H 170～179   （区间 2，接缝的"终点一侧"）
```

项目对红色的定义 = **"两个区间 + OR 合并"**：先分别用两个区间各做一次筛选，再用"或者"把它们合起来（具体代码见第 11、12 节）。只写其中一个区间，就会漏掉色环另一端的红色。

## 11. 源码：inRange

### 11.1 源码定位

```text
文件：src\marker_detector.py
函数：create_red_mask(image_bgr)
位置：第 51～52 行
```

### 11.2 真实代码

```python
mask_low = cv2.inRange(hsv_image, RED_LOWER_1, RED_UPPER_1)
mask_high = cv2.inRange(hsv_image, RED_LOWER_2, RED_UPPER_2)
```

### 11.3 inRange 做了什么：逐像素检查三个通道

`cv2.inRange` 会**逐像素**检查：

- H 是否在规定范围内；
- S 是否在规定范围内；
- V 是否在规定范围内。

判断规则：

```text
三个都满足   → 输出 255
任意一个不满足 → 输出 0
```

也就是说，**同一个区间内 H、S、V 是"并且"（AND）关系**，不是"或者"：只有三个条件同时成立，这个像素才算通过。

### 11.4 输出是什么

输出是一张 **H×W 的单通道黑白图**：

- 尺寸是 (height, width)，**没有颜色通道**；
- 只有两种取值：**255 = 通过规则，0 = 不通过规则**。

两张 mask 的编号方式要记住：

- `mask_low`：区间 1（H 0～10）的结果；
- `mask_high`：区间 2（H 170～179）的结果。

## 12. 源码：bitwise_or

### 12.1 源码定位

```text
文件：src\marker_detector.py
函数：create_red_mask(image_bgr)
位置：第 55 行
```

### 12.2 真实代码

```python
mask = cv2.bitwise_or(mask_low, mask_high)
```

### 12.3 逐像素 OR

`bitwise_or` 对两张图**逐像素**执行"或"运算，规则可以用真值表写全：

```text
0   OR 0   = 0
0   OR 255 = 255
255 OR 0   = 255
255 OR 255 = 255
```

所以合并的含义是：**只要两个红色区间中有一个区间判断该像素属于红色，最终 Mask 就保留该像素（255）。**

### 12.4 程序里的 OR 对应逻辑上的"或者"

必须指出：程序里的 OR 运算，对应的就是数学 / 逻辑上的"**或者**"。它和第 11 节区间内部的"并且"（AND）正好配对：

- 区间**内部**：H、S、V 三条同时成立 → **AND**；
- 区间**之间**：任意一边成立即可 → **OR**。

这两句话合起来，就是 VisionMotion"红色双区间"的定义方式。

## 13. Mask 到底是什么

本节必须建立一个清晰的概念：

> Mask 是一张逐像素回答：**"这个位置要不要保留？"** 的黑白图。

在 VisionMotion 中：

| 取值 | 含义 |
| --- | --- |
| **255** | 保留 / 认为该像素符合红色条件 |
| **0** | 不保留 / 认为该像素不符合红色条件 |

三句必须记住的定位：

1. **Mask 不是原始图片**——它是单通道黑白图（0 / 255），不是三通道彩色图；
2. **Mask 也不是目标本身**——它只回答"哪些像素符合红色规则"，还没有"对象"的概念，也不区分主体和噪点；
3. **它是"颜色筛选"产生的中间结果**——是数据链上的中间产物，后面还要交给 Contour 等步骤继续处理。

一句话：Mask 是"逐像素的是 / 否判断表"，不是"图片"，也不是"目标"。

## 14. 手算像素案例

> ⚠️ 本节三个例子是**教学示例（人为构造的像素）**，用于练习"逐像素判断"的过程。
> **教学示例不是项目实际数据。**项目真实参数始终以 `src\marker_detector.py` 第 22～27 行为准。

### 例 1：BGR = (0, 0, 128)

```text
推导：HSV = (0, 255, 128)

检查区间 1（H 0～10，S 100～255，V 70～255）：
  H 0   ✔（0 在 0～10 内）
  S 255 ✔（255 在 100～255 内）
  V 128 ✔（128 在 70～255 内）
→ 三个都满足：mask_low = 255

检查区间 2：H = 0 不在 170～179 → mask_high = 0

最终合并：255 OR 0 = 255
结论：判定为红色。
```

### 例 2：BGR = (0, 128, 255)

```text
推导：HSV ≈ (15, 255, 255)

H = 15 既不在 0～10，也不在 170～179

最终：Mask = 0
结论：橙色被排除。
```

这个例子说明：**不是"看起来偏红"就会通过**，而是要严格落进两个 H 区间之一。

### 例 3：BGR = (85, 0, 255)

```text
推导：HSV ≈ (170, 255, 255)

区间 1 失败：H = 170 不在 0～10 → mask_low = 0
区间 2 成功：H = 170 在 170～179，S = 255 ✔，V = 255 ✔ → mask_high = 255

最终合并：0 OR 255 = 255
结论：通过第二个红色区间被识别为红色。
```

三个例子放在一起看：同一套判断流程里，**一个像素只要通过任意一个区间就保留**；两个区间都失败才被丢弃——这正是 OR 合并的意义。

## 15. 3×3 玩具图

> ⚠️ 这是课程中的 **3×3 教学示例（人为构造的玩具图）**，用来解释"逐像素筛选"。
> **教学示例不是项目实际数据。**

原图是一个 3×3 的玩具图：**原图每个位置使用 BGR** 记录一个像素（每个像素三个数字）。

经过两个 `inRange` 之后，得到两张临时的黑白图：

```text
mask_low（区间 1 的结果）
0    255    0
0    255    0
0      0    0

mask_high（区间 2 的结果）
0    0      0
0    0      0
0    0    255
```

再做逐像素 OR（`bitwise_or`）后，最终 Mask：

```text
0    255    0
0    255    0
0      0  255
```

读法（按行、列位置对照）：

- 第 1 行第 2 个、第 2 行第 2 个位置：由**区间 1** 保留（mask_low 为 255）；
- 第 3 行第 3 个位置：由**区间 2** 保留（mask_high 为 255）；
- 其余位置：两个区间都没通过，最终为 0。

必须强调的结论：

> 这说明 Mask 是由"**对每一个像素分别判断**"产生的——9 个位置各自独立地做同一套检查，最后拼出一张 3×3 的黑白结果。Mask 里没有任何"整体形状"或"目标"的概念。

## 18. 本节课最重要的概念

1. **像素是数字图像最基本的数据单位**；计算机必须把连续的视觉世界离散成像素和数字才能处理；
2. 彩色图片在 Python / OpenCV 中就是 **NumPy 数组**，形状是 (高度, 宽度, 3)；
3. 数组访问是 **`img[y, x]`**：先行 y、后列 x；`img[0, 0]` 是左上角；
4. 8 位图像使用 **`uint8`**，单通道 0～255；
5. OpenCV 默认彩色顺序是 **BGR**：一个像素 (B, G, R)；(0,0,255) 是纯红；
6. **颜色空间是描述颜色的一套坐标 / 记账方式**：改变的是表示方法，不是物体本身；
7. **HSV 把颜色种类、浓淡、明暗拆成三个数字**：H 是什么颜色、S 有多浓、V 有多亮；
8. OpenCV 8 位 HSV 中 **H ∈ [0, 179]**，近似 H = 色相角度 / 2；S、V ∈ [0, 255]；
9. VisionMotion 的红色定义是**两个区间 + OR 合并**：H 0～10 与 H 170～179（S ≥ 100，V ≥ 70）；
10. 阈值就是**把"什么算红"写成明确的数值条件**；一个区间内 H/S/V 是 **AND**，两个区间之间是 **OR**；
11. `cv2.inRange` **逐像素**判断：三个通道都满足输出 255，任意一个不满足输出 0；输出 H×W 单通道黑白图；
12. **Mask 不是原图、也不是目标**：它是逐像素回答"要不要保留"的中间结果，255 = 保留、0 = 不保留；
13. `cv2.bitwise_or` 是**逐像素 OR**：只要一个区间判定为红，最终 Mask 就保留；
14. **Mask 是 Contour 的输入**：Mask 把颜色问题转换成黑白区域问题，几何边界由 Contour 接手（本节只到接口为止）；
15. **真实源码与教学示例必须分开**：项目事实用 文件 + 函数 + 行号 定位；3×3 玩具图和手算像素都只是教学示例。

## 19. 本节课容易犯的错误

1. 把 OpenCV 的彩色顺序当成 RGB（应为 **BGR**，(0,0,255) 才是纯红）；
2. 数组访问写成 `img[x, y]`（应为 **`img[y, x]`**，先行 y 后列 x）；
3. 把 H 当成 0～360 的角度来写区间（OpenCV 8 位 HSV 中 H 是 **0～179**）；
4. 以为一个 H 区间就能覆盖红色（红色跨色环接缝，必须**两个区间**）；
5. 把区间内部 H/S/V 的关系当成"或者"（应为**并且 AND**，三个条件同时成立才通过）；
6. 把两个区间之间也当成"并且"（应为**或者 OR**，用 `bitwise_or` 合并）；
7. 把 Mask 当成"处理过的彩色图片"（它是**单通道** 0/255 黑白图）；
8. 以为生成了 Mask 就等于"找到了目标"（Mask 只是像素级判断，还没有对象概念）；
9. 混淆 255 和 0 的含义（**255 = 满足规则、保留；0 = 不满足、不保留**）；
10. 以为 `inRange` 是整体运算（它是**逐像素**判断）；同理 `bitwise_or` 也是**逐像素** OR；
11. 把同一颜色在不同光照下 BGR 数值"应该差不多"当成理所当然（三个数都可能变，这正是要用 HSV 的动机）；
12. 把 HSV 理解成"完全消除光照影响"（光照仍影响 S、V，H 也可能漂移，阈值仍是经验规则）；
13. 把课堂手算的像素数值或 3×3 玩具图当成**项目真实数据**（它们都是教学示例）；
14. 引用项目事实时凭印象（应给出文件路径、函数名、行号，例如："`src\marker_detector.py` 的 `create_red_mask()` 第 48 行"）。
