## 2. marker_detector.py 在项目中的位置

`src\marker_detector.py` 是 VisionMotion 的**底层检测模块**（项目里对应 M2.3 这次业务实现）。

它负责的事情只有一件：

> **在一张图片中找到红色目标，并返回目标位置及相关检测信息。**

这里的"一张图片"是别人已经读进内存的图像数据；它拿到之后，输出检测结果字典，就结束了。

它本身**不负责**：

- 不负责读取文件（不调用 `cv2.imread`，不打开图片/视频）；
- 不负责保存文件（不调用 `cv2.imwrite`，不写 CSV）；
- 不负责画图（不在图上画矩形、圆圈、文字）；
- 不负责弹窗口（不调用 `cv2.imshow`）。

这四件事分别由调用它的上层程序完成，例如 `demo\run_single_image_detection.py`
（读图、打印结果、保存 overlay 与 mask）和 `src\video_tracker.py`
（读视频、逐帧调用、写 CSV、生成叠加视频）。

它可以被：

- **M2 单张图片检测**调用：`demo\run_single_image_detection.py` 读取一张真实图片后，调用 `detect_marker(image)`；
- **M3 视频逐帧检测**调用：`src\video_tracker.py` 在循环中对每一帧调用 `detect_marker(frame)`。

也就是说，同一套检测逻辑同时服务于"单张图片"和"视频逐帧"两种场景，这正是它被单独抽出来的原因。

项目里还有一条重要约定：

> `src\marker_detector.py` 是**检测参数的唯一来源**。

HSV 上下界、形态学核大小、最小面积这些参数只在 `marker_detector.py` 里定义一次；
调用它的模块（例如 `video_tracker.py`）不会重新定义一遍，只是 `from src.marker_detector import detect_marker`。
这样单图检测和视频逐帧检测用的是完全相同的规则，结果才可比、可复现。

模块内部一共只有四个函数，分工非常清楚：

| 函数 | 任务 |
| --- | --- |
| `create_red_mask(image_bgr)` | BGR 图 → 红色二值 Mask（含 BGR→HSV、双区间、bitwise_or、开运算） |
| `find_target_contour(mask)` | Mask → 最大外轮廓（含面积门槛检查） |
| `calculate_centroid(contour)` | 轮廓 → 质心 (cx, cy) |
| `detect_marker(image_bgr)` | 把上面三步串起来，返回结果字典 |

`detect_marker` 的返回值结构（本笔记后面会反复用到）：

- 检测成功：

```text
{
    "success": True,
    "cx": 目标中心 x（浮点数，单位像素）,
    "cy": 目标中心 y（浮点数，单位像素）,
    "area": 目标轮廓面积（浮点数，单位像素）,
    "bbox": 外接矩形 (x, y, w, h)（整数）,
    "contour": 目标轮廓,
    "mask": 红色二值掩膜,
}
```

- 检测失败：

```text
{
    "success": False,
    "mask": 红色二值掩膜,
}
```

注意失败时它也把 mask 一起返回——虽然没找到合格目标，但中间结果还留着，方便排查问题。

## 3. 图片在计算机中是什么

### 3.1 图片是像素网格

计算机里的彩色图片不是"一幅画"，而是一张**数值表格**：

- 图片被划分成许多小方块，每个小方块叫一个**像素（pixel）**；
- 像素按行、列排成网格：有"宽"（多少列）和"高"（多少行）；
- 每个像素里存的不是颜色名字，而是**一组数字**；彩色图片的每个像素有 3 个数字（3 个通道）。

例如一眼看去是"红色"的地方，在计算机里只是三个数字组合而成的一种取值。
计算机并不知道"红"这个概念——它只做数值判断。这一点是理解后面所有步骤的出发点：
**所谓"找到红色目标"，本质上是"找出满足某个数值条件的那些像素"。**

### 3.2 在 Python 里它就是一个 numpy 数组

OpenCV 读进来的图片，在 Python 里是一个 numpy 数组（shape 为 `(height, width, 3)`）：

- `height` 是图像的行数（高）；
- `width` 是图像的列数（宽）；
- 最后的 `3` 表示每个像素有 3 个通道。

访问一个像素写成 `image[y, x]`：

- 下标顺序是"先行后列"，`y` 是行号、`x` 是列号；
- 所以像素坐标 `(x, y)` 和数组下标 `[y, x]` 的顺序正好相反，这是初学者经常写错的地方。

### 3.3 图像坐标系：y 轴向下

和 L01 一样，这里继续使用图像坐标系：

- 原点在图像**左上角**；
- x 向右增加；
- **y 向下增加**。

所以"y 越大"表示位置越靠下，"y 越小"表示越靠上。这与数学课本里"y 向上为正"的笛卡尔坐标系相反，判断位置时一定要先想清楚用的是哪套坐标系。

## 4. BGR

### 4.1 OpenCV 的默认通道顺序

OpenCV 读取彩色图片时，默认使用 **BGR** 顺序。也就是说，一个像素的 3 个数字依次是：

```text
[B, G, R]
```

| 通道 | 名称 | 含义 | 取值范围 |
| --- | --- | --- | --- |
| B | Blue | 蓝色分量：这个像素里"蓝"有多少 | 0 ~ 255 |
| G | Green | 绿色分量：这个像素里"绿"有多少 | 0 ~ 255 |
| R | Red | 红色分量：这个像素里"红"有多少 | 0 ~ 255 |

三个分量一起决定像素最终的颜色。例如纯红是 `[0, 0, 255]`（B=0、G=0、R=255），
纯白是 `[255, 255, 255]`，纯黑是 `[0, 0, 0]`。

### 4.2 为什么必须强调 BGR

因为很多资料、很多其他软件（以及我们对颜色的日常描述）用的是 **RGB** 顺序：

```text
RGB: [R, G, B]
BGR: [B, G, R]
```

两者的顺序**正好相反**。如果不注意这一点，把 OpenCV 读进来的数据当 RGB 用，
那么"红"和"蓝"的数值就会被整体搞反：红色像素 `[0, 0, 255]` 会被误认为"蓝色"。

> 一句话记忆：**OpenCV 颜色三兄弟的排列顺序是 B、G、R。**

那么为什么不在这一步直接处理"红"？因为 BGR 里颜色信息和亮度信息是混在一起的：
同一个红色物体，光照强时 R 值很高，光照弱时 R 值明显下降，用固定数值区间很难稳定地把红色框住。
这正是下一步要转换到 HSV 的原因。

## 5. 为什么要使用 HSV

### 5.1 BGR / RGB 的问题：颜色和明暗纠缠在一起

在 BGR / RGB 里，想知道"这个像素是不是红色"，要同时看三个数字，
而且这三个数字会随着光照一起变化：

- 同一块红纸，在亮处可能接近 `[0, 0, 255]`，在阴影里可能变成 `[0, 0, 120]`；
- 相机白平衡、曝光不同，同一个物体记录下来的数字还会再变；
- 于是"红色"在 BGR 里会对应一大片分散的数值区域，用固定区间很难完整覆盖。

### 5.2 HSV 的思路：把三件事拆开

HSV 换了一种描述颜色的方式，把"这是什么颜色"、"颜色有多浓"、"有多亮"拆成三个分量。
这样一来：

- "是不是红"主要看 H（色相）；
- "颜色够不够浓"看 S（饱和度）；
- "够不够亮"看 V（明度）。

于是"找到红色"就可以写成一句很直接的规则：**H 落在红色区间里、S 不太低、V 不太低**。
光照变化主要影响 S 和 V，色相 H 相对稳定，这正是 HSV 更适合做颜色分割的原因。

### 5.3 代码怎么转换

代码里只有一行：

```python
hsv_image = cv2.cvtColor(image_bgr, cv2.COLOR_BGR2HSV)
```

`cv2.cvtColor` 是 OpenCV 的颜色空间转换函数，`cv2.COLOR_BGR2HSV` 表示"从 BGR 转到 HSV"。
转换后的 `hsv_image` 与原图一一对应：每个像素仍然是 3 个数字，只是这 3 个数字的含义变成了 H、S、V。

## 6. H / S / V

HSV 的三个分量：

| 分量 | 英文 | 中文 | 通俗理解 | OpenCV 取值范围 |
| --- | --- | --- | --- | --- |
| H | Hue | 色相 | 这是什么颜色 | 0 ~ 179 |
| S | Saturation | 饱和度 | 颜色有多浓 | 0 ~ 255 |
| V | Value | 明度 | 有多亮 | 0 ~ 255 |

### 6.1 H：是什么颜色

H 用"在色环上的位置"表示颜色种类：

- 可以把它想象成一个**圆形的色环**，一圈代表所有颜色；
- 数学上的色环是 0° ~ 360°；
- **但在 OpenCV 里，H 的范围是 0 ~ 179，不是 0 ~ 360。** 因为颜色被存进 8 位数值时，角度被除以 2（360 ÷ 2 = 180 个格子，即 0 ~ 179）。

> 这是本节最重要的记忆点之一：**在 OpenCV 里，色相的上界是 179，不是 359。**

### 6.2 S：颜色有多浓

S 描述颜色的"纯度 / 浓度"：

- S 很低 → 颜色发灰、发白，"不纯"；
- S 很高 → 颜色浓、鲜艳。

### 6.3 V：有多亮

V 描述明暗：

- V 很低 → 接近黑色，暗；
- V 很高 → 明亮。

### 6.4 三个分量合起来读

举个直观例子：一块被阴影遮住一半的红纸——

- 两半的 H 都比较接近红色的色相；
- 亮的一半 S、V 都高；
- 暗的一半 V 明显低。

所以判断"是不是红"时，除了限定 H，还要给 S、V 设一个**下限**，把"太淡"和"太暗"的像素排除掉。本项目取的下限就是 S ≥ 100、V ≥ 70（见下一节）。

## 7. 红色双区间

### 7.1 项目中的真实参数

`marker_detector.py` 文件顶部集中定义了四个常量（这是全项目检测参数的唯一来源）：

```python
# 红色掩膜区间 1：色相靠近 0 度的一端
RED_LOWER_1 = np.array([0, 100, 70])
RED_UPPER_1 = np.array([10, 255, 255])

# 红色掩膜区间 2：色相靠近 179 度的一端
RED_LOWER_2 = np.array([170, 100, 70])
RED_UPPER_2 = np.array([179, 255, 255])
```

写成区间形式：

| 区间 | H | S | V |
| --- | --- | --- | --- |
| 第一段 | 0 ~ 10 | 100 ~ 255 | 70 ~ 255 |
| 第二段 | 170 ~ 179 | 100 ~ 255 | 70 ~ 255 |

三个数字的顺序固定为 **[H, S, V]**。

### 7.2 为什么红色要被拆成两段

因为 HSV 色环是**首尾相接的圆形**：0° 和 360° 是同一个位置。

- 色环上的 0°（也就是 360°）附近正是**红色**；
- 红色因此"跨过"了色环的接缝——它一半在 0° 右侧（0° ~ 10°），另一半在 360° 左侧（对应 OpenCV 的 170 ~ 179）；
- 一个连续区间只能表示色环上的一段弧，**盖不住跨过接缝的红色**，所以必须拆成两段分别提取。

如果只写一段（例如只写 `[0,100,70] ~ [10,255,255]`），就会漏掉色相落在 170 ~ 179 的那部分红色像素，目标可能被切成两半，甚至面积不够而被当成"检测失败"。

### 7.3 代码怎么合并两段

```python
mask_low  = cv2.inRange(hsv_image, RED_LOWER_1, RED_UPPER_1)
mask_high = cv2.inRange(hsv_image, RED_LOWER_2, RED_UPPER_2)
mask = cv2.bitwise_or(mask_low, mask_high)
```

说明：

- `cv2.inRange(image, lower, upper)`：逐像素判断"是否落在 [lower, upper] 区间内"，落在区间内的像素给 255，否则给 0，生成一张黑白 Mask；
- 两次 `inRange` 分别得到第一段红色的 mask 和第二段红色的 mask；
- `cv2.bitwise_or` 是**按位或**：两张黑白图逐像素比较，只要有一张是 255，结果就是 255；两张都是 0 才是 0。

所以合并之后得到的 `mask`，同时包含了"0 ~ 10 段的红"和"170 ~ 179 段的红"。

### 7.4 S ≥ 100、V ≥ 70 是什么意思

- **S ≥ 100**：要求颜色足够浓。太淡（发灰、发白）的像素不算红色，避免把灰红色、浅粉色误判成目标；
- **V ≥ 70**：要求足够亮。太暗（几乎黑）的像素不算红色，避免阴影和暗色背景被误判。

上下限里 S、V 的上界都取 255，意思是"浓和亮的方向不设限"——越鲜艳、越亮都欢迎。

## 8. Mask

### 8.1 Mask 是什么

**Mask（掩膜 / 掩码）是一张与原图逐像素对应的黑白图。**

它和原图的关系是：原图的每个像素，在 Mask 里都有一个对应位置，用来回答一个问题——
**"这个像素满足我说的条件吗？"**

在本项目中：

| Mask 中的像素值 | 含义 |
| --- | --- |
| 255（白） | 这个像素满足红色条件（H 在两段红色区间内、S ≥ 100、V ≥ 70） |
| 0（黑） | 这个像素不满足红色条件 |

所以可以把 Mask 理解为一张**"逐像素的是/否判断表"**：白 = 是，黑 = 否。

### 8.2 Mask 的格式特性

- 由 `cv2.inRange` 生成；
- 是**单通道 8 位图**：每个像素只有一个数值（0 或 255），没有颜色通道；
- 尺寸为 `(height, width)`，与原图前两维一致——原图有多少像素，它就有多少格子；
- 它**不是原图**，也不是"处理过的彩色图片"，只是一张判断结果表。

### 8.3 代码位置

```python
mask = create_red_mask(image_bgr)
```

`create_red_mask` 内部的实现顺序是：

```text
BGR 图 → cvtColor 转 HSV → 两次 inRange → bitwise_or 合并 → 3×3 开运算 → 返回 mask
```

到这里为止，我们得到的还只是"哪些像素满足红色规则"，并没有得到"目标"。这一步的差距由后面的 Contour 补上。

## 9. 3×3 开运算

### 9.1 核是什么

形态学操作需要一个小模板来"扫描"图像，这个小模板叫**核（kernel）**。

本项目使用的是 **3×3 矩形核**：

```python
kernel = cv2.getStructuringElement(cv2.MORPH_RECT, (MORPH_KERNEL_SIZE, MORPH_KERNEL_SIZE))
```

其中 `MORPH_KERNEL_SIZE = 3`，`cv2.MORPH_RECT` 表示矩形形状，所以核就是一个 3×3 的小方块。
它会在 Mask 上逐像素移动，每移动到一个位置就看一看"核覆盖范围内的白色像素"。

### 9.2 开运算 = 先腐蚀，再膨胀

**开运算（Morphological Opening）**由两个基础形态学操作按固定顺序组成：

```text
开运算 = 先腐蚀（Erosion）→ 再膨胀（Dilation）
```

代码里一步完成：

```python
mask = cv2.morphologyEx(mask, cv2.MORPH_OPEN, kernel)
```

| 步骤 | 操作 | 效果 |
| --- | --- | --- |
| 第 1 步 | 腐蚀（Erosion） | 白色区域整体缩小；细小的、孤立的白点被"吃掉"消失 |
| 第 2 步 | 膨胀（Dilation） | 白色区域整体扩大；上一步幸存下来的主体区域恢复回近似原来的大小 |

### 9.3 为什么这个顺序能去噪

关键在"幸存"二字：

- 开运算开始时，Mask 上除了目标红色区域，往往还有一些零散的小白点（噪点，比如反光点、杂散红色小斑）；
- **腐蚀**让所有白色区域都缩小：小噪点因为太小，一缩就彻底消失了；主体目标虽然也缩小了一圈，但仍然存在；
- **膨胀**再把白色区域放大：此时只有"主体"能被恢复，噪点已经不存在，回不来了。

最终效果：**去掉零散小噪点，同时尽量保留主体目标。** 这正是本项目使用开运算的目的。

### 9.4 开运算不是什么

必须说清楚：**开运算不是"让图片变模糊"**。

- 它不是模糊、不是平滑滤波、不是高斯模糊（`GaussianBlur` 是另一回事）；
- 它不是降噪滤镜，也不改变图像尺寸；
- 它是**针对二值图（黑白图）的形态学操作**，处理的是"白色区域的形状"，而不是像素的灰度过渡。

项目从"5×5 高斯模糊 + 闭运算"改成了"3×3 开运算"，正是因为闭运算会把被高光切碎的红区"粘"到一起、也可能把附近小红点并入目标；
而开运算的作用方向恰好相反——**去零散噪点、保主体形状**（这一点在项目历史报告中留有可核实的记录）。

## 10. Contour

### 10.1 代码

```python
contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)
```

`cv2.findContours()` 的作用是：**从 Mask 中找出白色区域的边界。**

### 10.2 Contour 是什么

**Contour（轮廓）是二值图上白色区域的边界**——可以理解为一串点连成的一条闭合曲线，
沿着白色区域的边缘走一圈。每个轮廓就是一个"候选形状"。

两个参数的含义：

| 参数 | 含义 |
| --- | --- |
| `cv2.RETR_EXTERNAL` | 只提取最外层轮廓：一个区域套一个区域时，只取最外面那一圈，不关心内部小洞 |
| `cv2.CHAIN_APPROX_SIMPLE` | 压缩轮廓上的冗余点：例如一条直线段只保留端点，省掉中间点 |

第一个返回值 `contours` 是一个"轮廓的列表"：Mask 上有几个互不相连的白色区域，就大致对应几个轮廓。

### 10.3 为什么 Mask 还不等于"目标"

这是本课的关键认知之一：

> **Mask 只是告诉"哪里符合规则"，它本身不是"目标"。**

- Mask 是**像素级**的结果：一张 255/0 的判断表，只回答"这个像素红不红"；
- 它没有"对象"的概念：不会告诉你"这些白点属于同一个物体"、"那个白点是另一个物体"；
- 它也分不清主体和噪点：在它眼里所有白色像素都是平等的。

**Contour 才进一步把这些像素区域表示成一个个候选形状**，轮廓是"对象级"的表示，
它把一大片散落的白色像素总结成"一条边界曲线"，这样我们才能对"一个区域"做整体操作：
算面积、排序、求质心。

所以层次关系是：

```text
Mask（像素级判断表）
      ↓  findContours
Contour 列表（候选形状）
      ↓  选最大 + 面积门槛
目标轮廓
      ↓  moments
Centroid (cx, cy)
```

## 11. 最大轮廓与面积门槛

### 11.1 项目假设：最大的红色区域就是目标

`find_target_contour(mask)` 的做法是：

```python
contours_sorted = sorted(contours, key=cv2.contourArea, reverse=True)
biggest_contour = contours_sorted[0]
```

- 用 `cv2.contourArea` 计算每个轮廓的面积；
- 按面积从大到小排序（`reverse=True`）；
- 取排在最前面的那一个，即**面积最大的轮廓**。

背后的假设是一句话：

> **画面里最大的红色区域，就是我们要找的目标。**

### 11.2 面积门槛 MIN_AREA

光取最大还不够，还要检查它"够不够大"：

```python
if cv2.contourArea(biggest_contour) < MIN_AREA:
    return None
```

项目的最小面积是：

```python
MIN_AREA = 200
```

单位是**像素**（更准确地说，是轮廓面积，单位可理解为平方像素）。

规则是：

- 最大轮廓面积 ≥ 200 → 认为找到了合格目标，返回该轮廓；
- 最大轮廓面积 < 200 → 认为"这不是我们想要的目标" → `find_target_contour` 返回 `None` → `detect_marker` 返回 `{"success": False, "mask": mask}`（检测失败，不是程序崩溃）。

面积门槛的作用是拦住"只有一点点红色"的情况：反光、杂散小红点、噪声，都不应该被当成目标。

### 11.3 必须记住的局限

> **"最大轮廓"只是本项目的规则，不是万能的目标识别方法。**

如果画面背景里出现了比目标更大的红色物体（例如一块大红布、红色包装盒），
算法会理所当然地选那个最大的红色区域——**它可能选错目标**。

所以使用这条规则有一个前提：拍摄场景中，"最大的红色区域"确实就是我们要测的标记。
当场景不满足这个前提时，需要改规则（例如限定颜色、限定区域、换特征），而不是相信输出。

## 12. Moments

### 12.1 代码

```python
moments = cv2.moments(contour)
```

`cv2.moments(contour)` 计算轮廓的**图像矩（image moments）**。

### 12.2 什么是矩

通俗地说，矩就是把形状里的像素"按位置加权求和"得到的一族数值。
不同的矩反映形状不同方面的信息。本项目主要使用三个：

| 矩 | 名称 | 在本项目中的意义 |
| --- | --- | --- |
| `m00` | 零阶矩 | 与轮廓所围面积有关；也用作后面两个公式的分母（权重总和） |
| `m10` | 一阶矩（x 方向） | 描述像素在 x 方向上的加权分布 |
| `m01` | 一阶矩（y 方向） | 描述像素在 y 方向上的加权分布 |

### 12.3 质心公式

```text
cx = m10 / m00
cy = m01 / m00
```

代码里写作：

```python
cx = moments["m10"] / moments["m00"]
cy = moments["m01"] / moments["m00"]
```

### 12.4 本质：按面积分布做加权平均

这个公式的本质是：**把形状里所有像素的位置做加权平均，权重是像素本身**。
只有像素多的地方（形状的主要部分）对结果的"拉扯"才强，所以算出来的点总落在形状的"重心"上。
它与形状的**面积分布**有关，而不是简单地取边界框的中点。

### 12.5 为什么代码要检查 m00

```python
if moments["m00"] == 0:
    return None
```

因为 `m00` 出现在分母上。若 `m00 == 0`（例如轮廓退化成一条线或一个点），除法没有意义，
代码选择明确返回 `None`，让调用方知道"这一步算不出结果"，而不是硬算出一个错误数值或者直接崩溃。

## 13. Centroid

### 13.1 Centroid = 质心

**Centroid（质心）**是形状的"中心点"。在本项目中：

> **(cx, cy) 表示红色目标的中心位置。**

- 单位是像素；
- 是浮点数（可能是 512.7 这样带小数的值）；
- 由 `cv2.moments` 和公式 `cx = m10 / m00`、`cy = m01 / m00` 计算；
- `cx` 对应水平方向（列），`cy` 对应竖直方向（行），并直接使用图像坐标系（y 向下增加）。

在本模块里，`(cx, cy)` 就是**最终输出的目标位置**。从一张 BGR 图片出发的整条链路，到这里结束。

### 13.2 质心 ≠ 外接矩形中心

这一点必须单独强调。除了质心，代码里还有另一组"中心"：

```python
x, y, w, h = cv2.boundingRect(contour)
```

`cv2.boundingRect` 给出的是**外接矩形（Bounding Rectangle）**：能把这个轮廓恰好框住的最小正放矩形，
`(x, y)` 是矩形左上角，`w`、`h` 是宽和高。它自己的几何中心是 `(x + w/2, y + h/2)`。

质心和它**不是一回事**：

| | 质心 Centroid | 外接矩形中心 |
| --- | --- | --- |
| 来源 | `cv2.moments` 的三个矩 | `cv2.boundingRect` 的 x、y、w、h |
| 由什么决定 | 形状的**面积分布** | 框的**最外边界** |
| 形状不规则时 | 仍落在"重心"上 | 可能偏离重心 |

为什么两者会不同？举例：一个呈直角三角形的红色标记，会被外接矩形框住，
但红色像素明显更多地集中在直角一侧，质心会朝那一侧偏；而矩形中心始终在框的正中央。

### 13.3 本项目为什么用质心，boundingRect 用来做什么

- 本项目的位置输出选择**质心**。项目历史记录里留有理由：标记边缘不一定对称，用轮廓矩算质心比用外接矩形中心更稳；
- `boundingRect` 的 `(x, y, w, h)` 随结果字典一起返回，**主要用于框选（在图上画框）和辅助检查**——例如上层 demo 用它在 overlay 图上画绿色矩形，也方便人工核对检测范围是否合理；
- 也就是说：**位置看质心，框选看 boundingRect**，不要把两者的用途混起来。

真实结果示例（项目历史中已记录的实跑输出）：在 `data/raw/EXP-001-IMAGE-001.jpg` 上，
检测得到中心 (512.7, 964.5) px、面积 1278.5 px²、外接矩形 (494, 940, 37, 51)。
注意中心点的两个数字是浮点数，而外接矩形四个数字是整数。

## 14. 完整算法 Pipeline

### 14.1 总览

```text
BGR 彩色图片
      ↓
HSV
      ↓
红色双区间 Mask
      ↓
3×3 开运算
      ↓
Contour
      ↓
最大轮廓
      ↓
面积门槛
      ↓
Moments
      ↓
Centroid
      ↓
(cx, cy)
```

同一张流程图，用函数和数据对象写出来是：

```text
detect_marker(image_bgr)
  ├─ create_red_mask(image_bgr)
  │      BGR 图
  │      → cv2.cvtColor(..., COLOR_BGR2HSV) → HSV 图
  │      → cv2.inRange ×2 + cv2.bitwise_or → 红色 Mask（含噪点）
  │      → cv2.morphologyEx(MORPH_OPEN, 3×3) → 去噪后的 Mask
  ├─ find_target_contour(mask)
  │      Mask → cv2.findContours → 轮廓列表
  │      → 按面积排序取最大 → 检查 MIN_AREA=200 → 合格轮廓
  ├─ calculate_centroid(contour)
  │      轮廓 → cv2.moments → m00/m10/m01 → (cx, cy)
  └─ 返回结果字典（含 cx、cy、area、bbox、contour、mask）
```

### 14.2 逐级四要素

每一步都要能回答四个问题：**输入是什么 → 做什么 → 输出是什么 → 为什么需要这一步。**

| # | 步骤 | 输入 | 做什么 | 输出 | 为什么需要这一步 |
| --- | --- | --- | --- | --- | --- |
| 1 | BGR 彩色图片 | 图片文件/视频帧解码后的图像 | 作为整条链路的起点 | shape `(height, width, 3)` 的 BGR 数组 | 检测器只接受"已经读进内存的图片"，文件读到哪一步由调用方负责 |
| 2 | HSV | BGR 图片 | `cv2.cvtColor` 转换颜色空间 | HSV 图片（每像素 [H, S, V]） | 把"颜色种类"从亮度里分离出来，红色才容易被区间描述 |
| 3 | 红色双区间 Mask | HSV 图片 | 两次 `cv2.inRange` 分别取红色两段，再 `cv2.bitwise_or` 合并 | 单通道 8 位黑白 Mask（红 = 255） | 把"找红色"变成"逐像素的是/否判断" |
| 4 | 3×3 开运算 | 含噪点的 Mask | 先腐蚀去小噪点，再膨胀恢复主体 | 干净一些的 Mask | 去掉零散噪点，减少后续把噪点当成目标的可能 |
| 5 | Contour | 去噪后的 Mask | `cv2.findContours(RETR_EXTERNAL, CHAIN_APPROX_SIMPLE)` | 轮廓列表（候选形状） | 把像素级结果提升为"一个个区域"，才能整体计算 |
| 6 | 最大轮廓 | 轮廓列表 | 按 `cv2.contourArea` 降序排序取最大 | 面积最大的轮廓 | 项目规则：最大的红色区域就是目标 |
| 7 | 面积门槛 | 最大轮廓 | 检查面积是否 ≥ `MIN_AREA = 200` | 合格轮廓，或 `None`（失败） | 拦住"太小、不算目标"的情况，明确失败状态 |
| 8 | Moments | 合格轮廓 | `cv2.moments(contour)` | 一组矩（m00、m10、m01 等） | 用面积分布信息描述形状，为算质心做准备 |
| 9 | Centroid | 矩 | `cx = m10 / m00`、`cy = m01 / m00`（先检查 m00 ≠ 0） | 质心 (cx, cy) | 把整个形状收缩成一个位置点，这是最终要的坐标 |
| 10 | (cx, cy) | 质心 | 与其它信息一起打包返回 | `{"success": True, "cx": ..., "cy": ..., ...}` | 上层（单图/逐帧检测）拿它记录位置、写 CSV、画标注 |

### 14.3 失败路径

注意链路上有两个明确的"失败出口"：

```text
没有轮廓 / 最大轮廓面积 < 200      → find_target_contour 返回 None → detect_marker → success=False
m00 == 0（无法计算质心）           → calculate_centroid 返回 None  → detect_marker → success=False
```

失败时 `detect_marker` 仍然返回 `mask`，方便上层看看"是哪一步没成"。

## 15. 本节课最重要的编程思想

这一节把代码里的工程做法提炼成六条思想，它们比某个具体函数更值得带走。

### 15.1 把算法拆成多个小函数

`marker_detector.py` 没有写成一个大函数，而是拆成
`create_red_mask` / `find_target_contour` / `calculate_centroid` / `detect_marker` 四层。
每个小函数只解决一个小问题，出问题时能立刻定位到是哪一步。

### 15.2 每个函数完成一个明确任务

- `create_red_mask`：只做"图 → Mask"；
- `find_target_contour`：只做"Mask → 合格轮廓"；
- `calculate_centroid`：只做"轮廓 → 质心"；
- `detect_marker`：只负责按顺序调用它们并打包返回值。

任务边界清楚，函数才容易读懂、容易测试、容易复用。

### 15.3 每一步产生中间结果

检测过程不是黑盒：Mask、轮廓、质心都是可见的中间结果。
本模块把 `mask` 和 `contour` 一起放进返回字典，上层就可以单独保存 mask 图、
单独画轮廓去检查"哪一步出了问题"——而不是只能看到最后一句"没找到"。

### 15.4 出错时明确返回 None 或失败状态

没有轮廓 → 返回 `None`；面积不够 → 返回 `None`；`m00 == 0` → 返回 `None`；
最终 `detect_marker` 用 `success: False` 表示检测失败。

这些都是**明确的失败信号**，不是抛异常、更不是随便返回一个假坐标。
调用方看到 `success` 是 `False`，就知道"这一帧没测到"，可以如实记录，而不是被假数据骗到。

### 15.5 用常量保存阈值，而不是散落魔法数字

HSV 区间、核大小、最小面积都写成文件顶部的常量：
`RED_LOWER_1`、`RED_UPPER_1`、`RED_LOWER_2`、`RED_UPPER_2`、`MORPH_KERNEL_SIZE`、`MIN_AREA`。

好处是：

- 想调整参数时，只改一处，不需要在代码里到处搜数字；
- 每个数字都有名字，读到 `MIN_AREA` 就知道它是什么，而不是看到 `200` 猜半天；
- 这套常量还是全项目检测参数的**唯一来源**，调用方引用它而不是复制一份，保证单图与视频结果一致。

### 15.6 核心检测函数不负责文件读写，因此可以复用

`detect_marker` 的输入是"一张读好的图片"，输出是"检测结果字典"，
不碰文件、不弹窗口、不管结果存在哪里。正因为职责单一，
单图检测 demo 和视频逐帧检测可以**共用同一个函数**：

```python
from src.marker_detector import detect_marker
```

同一套规则，两种场景，检测行为完全一致。这就是"把检测逻辑独立成模块"的价值。

## 16. 算法局限性

本节的算法简单、透明、可解释，但它的适用范围也有清楚边界：

1. **只认红色。** 它不做通用目标识别，只找红色目标；其它颜色完全不处理。
2. **依赖固定的 HSV 区间。** 光照、白平衡、相机设备变化，都可能让同一个物体偏移出区间；
   换一个场景可能需要重新调参。
3. **依赖"最大红色区域 = 目标"这一假设。** 背景里出现更大的红色物体，算法会选错目标。
4. **依赖 MIN_AREA = 200 这个门槛。** 目标太小（远距离拍摄）会被当成"不合格"而检测失败；
   门槛太低时，又可能把较大的红色噪声当成目标。它不是万能的，需要按场景调。
5. **质心只给出一个位置点。** 它不包含目标的姿态、朝向、形状信息；目标旋转时质心可能几乎不动，
   仅凭 (cx, cy) 无法判断它是否转了。
6. **不处理遮挡。** 目标被挡住一部分时，算出的质心会偏向未被遮挡的一侧，位置会失真。
7. **逐帧独立检测，没有跟踪记忆。** 每一帧都是从头算一遍，不参考上一帧的结果；
   噪声帧可能产生跳变，也没有对帧与帧之间的运动做任何平滑或预测。
8. **对图像质量敏感。** 过曝、欠曝、严重模糊都会影响 mask 质量，进而影响检测。

理解这些局限，才能正确地使用检测结果，而不是把 (cx, cy) 当成"在任何情况下都可信的真值"。

## 17. 易错点

1. **BGR 和 RGB 不一样**
   - 错：以为 OpenCV 读进来就是 RGB，按 `[R, G, B]` 理解像素。
   - 对：OpenCV 默认 BGR，一个像素是 `[B, G, R]`，与 RGB 顺序相反。

2. **OpenCV 里 H 的范围是 0 ~ 179**
   - 错：把色相当 0° ~ 360° 用，写出 350 之类的大数。
   - 对：8 位图存储时角度除以 2，H 取值范围是 0 ~ 179；本项目红色第二段上界正是 179。

3. **红色需要两个 H 区间**
   - 错：只用一个区间（例如只写 `[0,100,70]~[10,255,255]`）就以为覆盖了所有红色。
   - 对：红色跨过色环 0°/360° 接缝，必须写两段，并用 `cv2.bitwise_or` 合并两张 mask。

4. **Mask 不是原图**
   - 错：把 mask 当成"处理过的彩色图片"。
   - 对：mask 是单通道 8 位黑白图，只有 255 / 0 两种值，尺寸是 `(height, width)`，没有三个通道。

5. **Mask 不等于目标**
   - 错：认为生成 mask 就已经"找到目标"了。
   - 对：mask 只回答"哪些像素符合红色规则"，是像素级判断表，没有对象概念；要经过 `findContours` 变成候选轮廓之后才谈得上"目标"。

6. **Contour 不等于质心**
   - 错：把 `findContours` 的输出直接当成中心点。
   - 对：轮廓是形状的边界曲线（一串点）；质心是 `cv2.moments` 用 `cx = m10/m00`、`cy = m01/m00` 算出来的面积分布中心。一个是形状，一个是点。

7. **Centroid 不等于 bounding rectangle 的几何中心**
   - 错：以为 `cx = x + w/2`、`cy = y + h/2`。
   - 对：质心由面积分布决定；外接矩形中心由框的几何尺寸决定。本项目输出质心，`boundingRect` 主要用于框选与辅助检查；形状不规则时两者明显不同。

8. **最大轮廓只是项目规则**
   - 错：以为"取最大轮廓"是通用的目标识别方法。
   - 对：这是本项目"最大的红色区域就是目标"的假设；背景有更大红色物体时会选错。

9. **开运算不是"让图片变模糊"**
   - 错：把开运算理解成模糊、平滑或降噪滤镜。
   - 对：开运算 = 先腐蚀（吃掉细小孤立白区）再膨胀（恢复主体大小），是二值图的形态学去噪；和 `GaussianBlur` 是两回事。

10. **MIN_AREA 的单位是面积，不是长度**
    - 错：以为 200 是"200 像素长"，或者把轮廓面积和周长搞混。
    - 对：它是 `cv2.contourArea` 算出的轮廓面积（平方像素量级），判断的是区域大小，不是某条边的长度。

11. **检测失败时返回 None / success=False，不是程序崩溃**
    - 错：看到 `None` 或 `success: False` 就以为是代码出 bug。
    - 对：这是设计好的失败信号——"这一帧没有合格目标"是一种正常结果；上层据此记录 detected=False，而不是停止运行。

## 19. 一句话总结

> VisionMotion 把一张 BGR 彩色图片先转成 HSV，用两段 H 区间配合 S、V 下限生成红色 Mask，再用 3×3 开运算去掉零散噪点；接着用 `findContours` 把 Mask 中的白色区域变成候选轮廓，按面积取最大并用 `MIN_AREA = 200` 检查是否合格；最后用 `cv2.moments` 按 `cx = m10 / m00`、`cy = m01 / m00` 计算质心，得到红色目标的位置 (cx, cy)——这就是 `marker_detector.py` 的全部任务。
