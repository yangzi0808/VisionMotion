# VisionMotion 易错知识库

本文件用于收集 VisionMotion 学习过程中容易混淆、容易理解错误的知识点，按课程编号组织。每一条记录包含四部分：错误理解、正确理解、为什么容易错、如何避免与自检。

使用方式：每学完一节课，把当节课新暴露出的易错点追加到对应课程编号下；复习时优先阅读本文件，可以快速定位自己曾经踩过的坑。

## L01 VisionMotion项目、CSV与时间序列

### 1. 图像坐标的 y 轴方向

- **错误理解**：把图像中的 y 当成数学课本里"向上为正"的方向，认为 y0_px 越大目标在画面中越靠上。
- **正确理解**：图像坐标中 y 通常**从上往下增加**。y 越小 → 目标在画面中越靠上；y 越大 → 目标在画面中越靠下。因此本项目里：y0_px 的**局部极大**对应画面中的**较低位置**，y0_px 的**局部极小**对应画面中的**较高位置**。
- **为什么容易错**：在数学课（笛卡尔坐标系）中长期习惯"y 向上为正"；而图像的存储和显示约定是从左上角开始、逐行向下，y 轴方向正好相反。两个习惯同时存在，就容易搞混。
- **如何避免与自检**：看到任何像素坐标先默念一遍"图像里 y 向下增大"，再判断"数值增大代表目标往下走"。用真实数据自检：frame 77 的 y0_px = 508（局部极小）应理解为此时暗带上缘在画面中**较高**的位置；frame 85 的 y0_px = 622（局部极大）应理解为此时暗带上缘在画面中**较低**的位置。

### 2. frame 和 time_s 不是一回事

- **错误理解**：把 frame 和 time_s 当成同一个东西，或者认为它们可以随意互换、都是"时间"。
- **正确理解**：frame 是**帧序号**，回答"这是视频里的第几帧"，是一个计数（整数）；time_s 是**这一帧距视频开始经过了多少秒**，是一个时间量（单位：秒）。两者通过帧率换算：本项目视频 30 fps，所以 time_s ≈ frame / 30。例如 frame 77 对应 time_s = 2.566667 s，frame 78 对应 time_s = 2.600000 s。
- **为什么容易错**：两列都随视频推进而增大，数值上又只差一个比例系数，看起来"差不多"；再加上日常口语中容易把"第几帧"和"第几秒"混着说。
- **如何避免与自检**：牢记判断标准——问"第几帧"用 frame，问"过了多少秒"用 time_s。自检方法：任取一行 CSV，用 frame ÷ 30 心算一遍，看是否约等于 time_s（例如 76 ÷ 30 ≈ 2.533333，与 CSV 中 frame 76 的 time_s 一致）。

### 3. y0_px 才是本阶段主要运动信号

- **错误理解**：把 8 列数据不加区分地当成"8 个运动信号"，或者把 y0_px 简单称为"目标中心坐标"，又或者把 y0_px 和 x_px 混为一谈。
- **正确理解**：y0_px 的准确含义是**暗带上缘的竖直像素位置**（不是目标中心，也不是面积）。在本阶段，它是**唯一用于描述运动的核心信号**：随时间往复变化，构成 y0(t)。x_px 是水平方向的像素坐标，仅作质量检查，不是本阶段的运动信号。
- **为什么容易错**："y0"这个名字看起来像数学里的初值，容易望文生义；同时 x_px 和 y0_px 都是 px 结尾的坐标列，容易顺手当成一对同等重要的量。
- **如何避免与自检**：记住一条硬结论——本阶段运动信号 = y0_px = 暗带上缘竖直像素位置。自检：读 CSV 时问自己"这一列是不是在描述目标位置随时间的变化？"，只有 y0_px 回答"是"。真实数据自检：frame 77 处 y0_px = 508、frame 85 处 y0_px = 622，这一对数值直接体现了 y0_px 随时间的变化。

### 4. 检测质量字段不等于运动测量量

- **错误理解**：把 detected、bbox_w_px、bbox_h_px、area_px 也当作运动信号，甚至因为 area_px 有起伏就认为它是"振动幅度"。
- **正确理解**：这四列是**检测质量指标**，主要回答三个问题：有没有成功检测到（detected）、检测区域有多大（bbox_w_px、bbox_h_px、area_px）、检测区域的形状是否合理。它们的作用是帮助判断"这一帧的测量是否可信"，而不是直接描述目标运动。
- **为什么容易错**：这些字段的数值确实会随帧变化，看起来也"在动"；如果不清楚它们各自的物理含义，就容易误把它们当成位移信号。
- **如何避免与自检**：把 8 列分成两组——运动信号（y0_px）与检测质量指标（detected、x_px、bbox_w_px、bbox_h_px、area_px）。自检：当看到某列的波动时，先问"这个波动反映的是目标在动，还是检测结果本身在变？"

### 5. 视频在计算机中由离散帧构成

- **错误理解**：认为视频是计算机直接理解的一条连续运动，可以像数学函数一样任意取"中间时刻"的值。
- **正确理解**：计算机眼中的视频是**一帧一帧连续排列的离散图片**（Frame 0、Frame 1、Frame 2……），每一帧只代表**一个具体时间瞬间**。30 fps 表示每秒记录 30 帧，相邻两帧之间相隔 Δt = 1/30 s ≈ 0.033333 s。因此本项目得到的位置数据是**离散采样**：每约 0.033333 s 才有一个数据点。
- **为什么容易错**：人眼看视频时感知到的是连续运动，直觉上会把视频当成"连续信号"；而"离散、有采样间隔"这一事实只有从数据结构角度看才明显。
- **如何避免与自检**：牢记"视频 = 一串离散图片 + 播放速度"。自检：任何"视频里某一时刻"的说法，都要能回答"那对应第几帧"；意识到两帧之间的信息计算机并没有记录，这也是本项目把采样间隔（单帧 0.033333 s）视为时间定位上界的原因。

### 6. 一行 CSV 就是一个时刻的一次测量结果

- **错误理解**：把 trajectory.csv 想象成"一条已经画好的连续曲线"，或者以为一行数据代表目标的一整段运动过程。
- **正确理解**：**一行 CSV = 一个时刻的一次视觉测量结果。** 例如真实数据行 `77,2.566667,True,725.00,508.00,57,5,280` 表示：在 frame 77（约 2.566667 s）这个时刻，程序对那一帧画面做了一次测量，得到 y0_px = 508 以及若干检测质量信息。160 行 = 160 个时刻的 160 次测量。
- **为什么容易错**：人眼看视频感觉运动是连续的，很容易忘记数据其实是在离散时刻"一次一次量出来"的；再加上用表格软件画出的曲线看上去是连续的，更容易产生错觉。
- **如何避免与自检**：读到任何一行 CSV，先在心里补全一句话："这一行是第几帧、在什么时刻、量出来的位置是多少。"能补全，说明理解了"一行 = 一次测量"。

（本节 6 条为 L01 的核心易错点；后续如有新增，继续追加在本节下方。）

## L02 marker_detector.py：从图片到目标中心

### 1. BGR 和 RGB 不一样

- **错误理解**：以为 OpenCV 读进来的图片就是 RGB，按 `[R, G, B]` 的顺序理解一个像素。
- **正确理解**：OpenCV 读取彩色图片默认使用 **BGR** 顺序，一个像素是 `[B, G, R]`——蓝色在最前、红色在最后，与常见的 RGB 顺序**正好相反**。纯红在 BGR 里是 `[0, 0, 255]`，纯蓝是 `[255, 0, 0]`。
- **为什么容易错**：大多数教材、网页和图像软件用 RGB 描述颜色，习惯一旦形成，就会下意识把"第一个数字"当成红色；OpenCV 偏偏反着来。
- **如何避免与自检**：看到 OpenCV 的彩色图先默念"BGR"；写颜色相关代码前先确认通道顺序。自检方法：说出纯红、纯蓝在 OpenCV 里的像素写法，再看自己是否搞反。

### 2. H 在 OpenCV 中是 0～179，而不是 0～360

- **错误理解**：把色相当成 0° ~ 360° 的物理角度直接用，写出 `[0,100,70]~[350,255,255]` 之类大于 179 的 H 上界。
- **正确理解**：OpenCV 8 位 HSV 图中，H 的取值范围是 **0 ~ 179**（色相角度被除以 2 存储），S、V 的取值范围是 0 ~ 255。本项目的第二段红色区间上界就是 179，不是 359。
- **为什么容易错**：讲色相时通常说"0° ~ 360° 的色环"，而代码里却变成了 179 上限；两套数字同时存在，不专门记就会写错。
- **如何避免与自检**：写任何 H 区间前先问自己"这是 OpenCV 的 H 吗"，上界一律用 179 检查一遍。自检：本项目红色区间写成 `[0,10]` 与 `[170,179]`，其中 179 就是上限。

### 3. 红色需要两个 H 区间

- **错误理解**：只写一段 H 区间（例如只写 `[0,100,70]~[10,255,255]`）就以为覆盖了所有红色。
- **正确理解**：HSV 色环是首尾相接的圆，红色跨过 0°/360° 接缝，必须拆成两段：`[0,100,70]~[10,255,255]` 与 `[170,100,70]~[179,255,255]`；两段各自生成 mask 后，用 `cv2.bitwise_or` 合并成一张。
- **为什么容易错**：数值区间在直觉上"应该是一段连续的"，不容易想到颜色空间是环形的；而红色恰好落在环的接缝上，是最典型的例外。
- **如何避免与自检**：检查代码里是否同时存在 `RED_LOWER_1`/`RED_UPPER_1` 与 `RED_LOWER_2`/`RED_UPPER_2`，并且两张 mask 做了 `bitwise_or`。自检：问自己"只写一段会漏掉哪部分红色"——答案是色相在 170 ~ 179 的那部分。

### 4. Mask 不是原图

- **错误理解**：把 Mask 当成"处理过的彩色图片"，或者以为 Mask 有三个通道。
- **正确理解**：Mask 是与原图逐像素对应的**单通道 8 位黑白图**，只有 255（满足红色条件）与 0（不满足红色条件）两种值，尺寸为 `(height, width)`，而不是 `(height, width, 3)`。它是"逐像素的是/否判断表"。
- **为什么容易错**：Mask 和原图"长得像"——位置一一对应，看起来就像一张图；只要不专门检查通道数，很容易顺手当成彩色图处理。
- **如何避免与自检**：看到 Mask 就默念"单通道、只有 0 和 255"。自检：确认它的 shape 是两维、显示时是黑白，且不能直接和 BGR 图片做颜色运算。

### 5. Mask 不等于目标

- **错误理解**：认为生成 Mask 就已经"找到目标"了。
- **正确理解**：Mask 只回答"哪些像素符合红色规则"，是**像素级**判断结果，它没有"对象"的概念，也不区分主体和噪点；必须经过 `cv2.findContours` 把白色像素区域表示成一个个候选轮廓（候选形状），再筛选，才谈得上"目标"。
- **为什么容易错**：Mask 上白色的地方看起来就是那个红色物体，视觉上很容易产生"已经找到了"的错觉，从而忽略"像素集合"和"对象"之间的差别。
- **如何避免与自检**：记住数据链的三步——"Mask（哪里符合规则）→ Contour（候选形状）→ 目标轮廓"。自检：问自己"Mask 能算出面积吗、能算出中心吗"——它只能给出像素集合，必须先变成轮廓才能整体计算。

### 6. Contour 不等于质心

- **错误理解**：以为 `cv2.findContours` 的输出就是目标中心点，或把轮廓上的某个点当成中心。
- **正确理解**：Contour 是形状的**边界曲线**（一串点）；Centroid 是由 `cv2.moments` 计算的**面积分布中心**。必须先有轮廓，再用公式 `cx = m10 / m00`、`cy = m01 / m00` 才能得到中心。两者一个是"形状"，一个是"点"。
- **为什么容易错**：轮廓上确实有很多点，看起来"有坐标"；再加上目标是找中心，容易把"找到轮廓"和"找到中心"合并成一步。
- **如何避免与自检**：看到 `(cx, cy)` 时能说出它来自 `moments`，而不是来自 `findContours`。自检：完整说出"先 findContours，再 moments，再除法"这个顺序。

### 7. Centroid 不等于 bounding rectangle 的几何中心

- **错误理解**：认为 `cx = x + w/2`、`cy = y + h/2` 与质心是一回事，甚至以为本项目的位置就是外接矩形中心。
- **正确理解**：质心由形状的**面积分布**决定；外接矩形的几何中心由框的尺寸决定。目标形状不规则或边缘不对称时，二者明显不同。本项目的位置输出用**质心**（`cv2.moments` + 公式），`cv2.boundingRect` 给出的 `(x, y, w, h)` 主要用于**框选显示与辅助检查**。
- **为什么容易错**：矩形中心"看起来"就是中心，而且计算简单（加一半宽高）；只有形状不对称时，两者的差异才不会互相接近，平时不容易暴露。
- **如何避免与自检**：检查 `cx`、`cy` 是否来自 `moments["m10"] / moments["m00"]`；只有需要"框"的时候才用 `boundingRect`。自检：画一个直角三角形，分别说出它的质心和外接矩形中心大概在哪里，看两者是否重合。

### 8. 最大轮廓只是项目规则，不是万能目标识别

- **错误理解**：以为"取最大轮廓"是一种通用的目标识别方法，任何场景都能用。
- **正确理解**：这是本项目的一条明确假设——**画面里最大的红色区域就是目标**；并用 `MIN_AREA = 200` 检查它是否"够大"。如果背景中出现比目标更大的红色物体，算法会选错目标。
- **为什么容易错**："取最大的那个"在直觉上很合理，容易让人忘记它只是"针对这个拍摄场景"的约定，而不是算法本身具有识别能力。
- **如何避免与自检**：使用前先确认场景满足这条假设；不满足时应改规则，而不是相信输出。自检：问自己"如果画面里同时有两块红色，算法会选哪一块？凭什么？"

### 9. 开运算不是"让图片变模糊"，其作用是特定的形态学去噪

- **错误理解**：把开运算理解成模糊、平滑滤波、降噪滤镜或图像缩放。
- **正确理解**：开运算是**形态学操作**，等于"先腐蚀、再膨胀"：腐蚀吃掉细小的孤立白区，膨胀把幸存的主体恢复回近似原来的大小，目的是去掉零散小噪点、同时尽量保留主体目标。它与高斯模糊（`GaussianBlur`）是两种完全不同的操作。
- **为什么容易错**：两者都常被口语化地称为"去噪"，容易混为一谈；而"开运算"这个名字本身也看不出它到底做了什么。
- **如何避免与自检**：听到"去噪"先追问"去的是哪一类噪声、用的什么操作"。自检：能按顺序说出"腐蚀 → 膨胀"，并说清"为什么这个顺序能去掉小噪点、保住主体"。此外要记住：本项目用 3×3 矩形核（`MORPH_KERNEL_SIZE = 3`），不是高斯模糊。

### 10. MIN_AREA 的单位是面积，不是长度

- **错误理解**：以为 `MIN_AREA = 200` 是"200 像素长"，或把它与轮廓周长混为一谈。
- **正确理解**：`MIN_AREA` 是 `cv2.contourArea` 算出的**轮廓面积**门槛，判断的是"这个红色区域够不够大"；它不是某条边的长度，也不是周长。
- **为什么容易错**：面积和长度都常用像素为单位，数值范围又都是几十到几百，不看定义很难分辨。
- **如何避免与自检**：看到面积相关判断先确认用的是 `cv2.contourArea`（面积）还是 `cv2.arcLength`（周长）。自检：说清"最大轮廓面积 < 200 会发生什么"——返回 `None`，`detect_marker` 最终 `success=False`。

### 11. 检测失败返回 None / success=False，不是程序崩溃

- **错误理解**：看到 `None` 或 `{"success": False}` 就以为是代码出了 bug，或者认为程序应该"报错退出"。
- **正确理解**：这是设计好的**失败信号**："这一帧没有找到合格目标"是一种正常结果。`find_target_contour` 和 `calculate_centroid` 出错时返回 `None`，`detect_marker` 用 `success: False` 表示失败，同时把 mask 一起返回，方便上层排查和如实记录（例如轨迹 CSV 里的 detected=False）。
- **为什么容易错**：`None` 在 Python 里常和"出错了"联系在一起；而在本项目的设计里，它是"明确、可控的失败状态"。
- **如何避免与自检**：调用 `detect_marker` 后先检查 `result["success"]`，再做后续计算。自检：能说出两条失败出口——"没有轮廓或最大轮廓面积 < 200"与"m00 == 0 无法计算质心"。

（本节 11 条为 L02 的核心易错点；后续如有新增，继续追加在本节下方。）

## L03 像素、颜色空间与 Mask 的实际运算

### 1. OpenCV 默认彩色图像顺序是 BGR，不是 RGB

- **错误理解**：以为 OpenCV 读进来的彩色图是 RGB，按 `[R, G, B]` 的顺序理解一个像素。
- **正确理解**：OpenCV 读取彩色图像默认使用 **BGR**：一个像素是 `[B, G, R]`，与常见的 RGB 顺序正好相反。纯红是 `(0, 0, 255)`，纯蓝是 `(255, 0, 0)`；`src\marker_detector.py` 第 110 行附近的输入说明明确写着 `image_bgr` 是"用 cv2.imread 读进来的 BGR 图像"。
- **为什么容易错**：大多数教材、网页和图像软件都用 RGB 描述颜色，习惯一旦形成，就会下意识把第一个数字当成红色；OpenCV 偏偏反着排。
- **如何避免与自检**：看到 OpenCV 的彩色图先默念"BGR"；写颜色相关代码前先确认通道顺序。自检：立刻说出纯红、纯蓝在 BGR 里的写法，答反了说明还没记牢。

### 2. 图片数组访问是 img[y, x]，不是 img[x, y]

- **错误理解**：按数学里坐标 (x, y) 的习惯写成 `img[x, y]`，以为自己取的是"第 x 列第 y 行"的像素。
- **正确理解**：NumPy 数组下标是"先行后列"：`img[y, x]`——y 是行号（从上往下增大），x 是列号（从左往右增大）；`img[0, 0]` 是左上角像素。这与"图像坐标 y 向下增大"的约定是一致的。
- **为什么容易错**：数学中坐标写作 (x, y)，而数组下标顺序正好相反；两种习惯同时存在就容易写反。
- **如何避免与自检**：写访问代码前先默念"先 y 后 x"。自检：取"第 5 行、第 12 列"的像素应写 `img[5, 12]`，不是 `img[12, 5]`。

### 3. H 在 OpenCV 8 位 HSV 中是 0～179，不是 0～360

- **错误理解**：把色相当成物理角度直接用，写出 `[0,100,70]~[350,255,255]` 之类大于 179 的 H 上界。
- **正确理解**：OpenCV 8 位 HSV 图中，H 的取值范围是 **0～179**（色相角度 ÷ 2 存储），S、V 是 0～255。换算示例：0°→H 0、340°→H 170、358°→H 179。
- **为什么容易错**：讲颜色时习惯说"0°～360° 的色环"，而代码里 H 的上限是 179；两套数字同时存在，不专门记就会写错。
- **如何避免与自检**：写任何 H 区间前先问自己"这是 OpenCV 的 H 吗"，上界一律对照 179 检查。自检：本项目红色两段区间的上界分别是 10 与 179，出现 350 就是错的。

### 4. 红色在本项目中需要两个 H 区间

- **错误理解**：只写一段 H 区间（例如只写 `[0,100,70]~[10,255,255]`）就以为覆盖了所有红色。
- **正确理解**：HSV 色环首尾相接，红色跨过 0°/360° 接缝，必须拆成两段：`[0,100,70]~[10,255,255]`（第 22～23 行）与 `[170,100,70]~[179,255,255]`（第 26～27 行）；只写一段会漏掉色环另一端的红色（H 170～179 那部分）。
- **为什么容易错**：数值区间在直觉上"应该是一段连续的"，不容易想到颜色空间是环形的；红色恰好落在接缝上，是最典型的例外。
- **如何避免与自检**：检查代码里是否同时存在 `RED_LOWER_1` / `RED_UPPER_1` 与 `RED_LOWER_2` / `RED_UPPER_2`，并且两张 mask 被合并。自检：问自己"只写一段会漏掉哪部分红色"，能答出 H 170～179 才算过关。

### 5. 同一个区间内 H/S/V 三个条件是"并且"（AND）

- **错误理解**：以为 H、S、V 只要有一个落在范围内，这个像素就算通过。
- **正确理解**：同一个区间内三个条件必须**同时**成立：H 在范围内 并且 S 在范围内 并且 V 在范围内；`cv2.inRange` 逐像素检查三个通道，全满足输出 255，任意一个不满足输出 0（第 51～52 行）。
- **为什么容易错**：三个条件写在同一个"下界数组 / 上界数组"里，看起来像"并列关系"，不强调就容易想成"满足其一即可"。
- **如何避免与自检**：记住口诀"区间内 AND、区间间 OR"。自检：一个像素 H=5、S=255、V=60，是否通过区间 1？——不通过（V 低于 70），因为三个条件必须同时成立。

### 6. 两个红色区间之间是"或者"（OR）

- **错误理解**：以为要同时满足区间 1 和区间 2 才算红色；或者根本不知道两张 mask 之间如何合并。
- **正确理解**：两个区间之间是 OR，由 `cv2.bitwise_or(mask_low, mask_high)`（第 55 行）逐像素合并：只要任一区间判定该像素属于红色，最终 Mask 就保留它（255）。
- **为什么容易错**：刚记住"条件要 AND"（区间内），很容易顺手把区间之间也当成 AND；而"同时满足 H 0～10 与 H 170～179"实际不可能，会把所有像素都排除，产生荒谬结果。
- **如何避免与自检**：明确两层结构——区间内 AND（三个通道）、区间间 OR（两张 mask）。自检：一个正常红色像素至少能通过两个区间中的一个，若"所有红色都不通过"，先怀疑是不是把 OR 写成了 AND。

### 7. Mask 不是原图

- **错误理解**：把 Mask 当成"处理过的彩色图片"，或者以为它有 B、G、R 三个通道。
- **正确理解**：Mask 是与原图逐像素对应的**单通道 8 位黑白图**，只有 0 与 255 两种值，尺寸是 (height, width)；`create_red_mask` 的文档字符串（第 45 行）明确写着"返回的掩膜是单通道 8 位图：红色区域为 255，其他区域为 0"。
- **为什么容易错**：Mask 与原图位置一一对应、"长得像"，不专门检查通道数，就容易顺手当成彩色图处理。
- **如何避免与自检**：看到 Mask 先默念"单通道、只有 0 和 255"。自检：确认它的 shape 是两维（没有第三个通道维），也不能直接和 BGR 图片做颜色运算。

### 8. Mask 不是目标本身

- **错误理解**：认为生成了 Mask 就已经"找到目标"。
- **正确理解**：Mask 只回答"哪些像素符合红色规则"，是**像素级**判断结果，没有"对象"的概念，也不区分主体与噪点；必须再经 `cv2.findContours`（第 73 行）把白色像素区域变成轮廓（几何边界），才谈得上"目标"。
- **为什么容易错**：Mask 上白色的地方看起来就是那个红色物体，视觉上很容易产生"已经找到了"的错觉。
- **如何避免与自检**：记住数据链："Mask（哪里符合规则）→ Contour（几何边界）→ 后续筛选/计算"。自检：问自己"Mask 能直接给出目标中心吗？"——不能；中心是后续步骤（L02 已学的 Moments / Centroid）算出来的。

### 9. 255 表示满足规则，0 表示不满足

- **错误理解**：把 0 当成"保留"、255 当成"丢弃"，或者把 255 当成某种颜色数值。
- **正确理解**：在红色 Mask 中：**255 = 通过规则（保留，认为符合红色条件）；0 = 不通过规则（不保留）**。`cv2.inRange` 与 `cv2.bitwise_or` 都在 0/255 这一层工作。
- **为什么容易错**：编程里常见"0 是假、1 是真"的直觉，而这里"真"用的是 255 而不是 1，不看定义就容易记反。
- **如何避免与自检**：用一句话检验自己："白 = 保留 = 255，黑 = 不保留 = 0"。自检：OR 真值表里只有 0 OR 0 = 0，其余组合全是 255。

### 10. inRange 是逐像素判断，不是整图一次性判断

- **错误理解**：以为"整张图看起来是红色"就通过，或以为 `cv2.inRange` 输出的是一个真 / 假值。
- **正确理解**：`cv2.inRange` 对**每个像素**单独检查 H、S、V 是否都在区间内（三个条件 AND）：全满足输出 255，否则输出 0；输出与原图同尺寸的 **H×W 单通道图**。第 51～52 行两次调用分别得到 `mask_low`（区间 1）与 `mask_high`（区间 2）。
- **为什么容易错**：函数名"inRange"读起来像"判断某个值是否在范围内"的一次性判断，看不出"对每个像素各判一次"。
- **如何避免与自检**：记住"输出的是一张图，不是一个数"。自检：能说出输出只有 0 与 255 两种取值、尺寸与原图相同。

### 11. bitwise_or 是逐像素 OR，不是"面积相加"

- **错误理解**：以为 `cv2.bitwise_or` 是把两张图的白色区域"面积相加"，或者会改变图像尺寸。
- **正确理解**：它逐像素执行 OR：0 OR 0 = 0；0 OR 255 = 255；255 OR 0 = 255；255 OR 255 = 255（第 55 行）。效果是"两个红色区间任一通过即保留该像素"；输出尺寸与两张输入 mask 完全相同。
- **为什么容易错**：口语里"or"常说成"或者取一个"，容易联想成"合并/相加"这类整体操作，而不是"每个像素位置逐位运算"。
- **如何避免与自检**：能默写四行真值表（只有 0 OR 0 = 0）。自检：合并后 Mask 的形状与 `mask_low`、`mask_high` 完全一致，不会变大也不会变小。

### 12. 教学示例不能当成项目真实数据

- **错误理解**：把手算像素 `(0,0,128)`、`(0,128,255)`、`(85,0,255)`、3×3 玩具图的 0/255 数组、100×80 的形状示例当成项目里真实出现的数据或真实阈值。
- **正确理解**：这些都是**教学示例**（人为构造），只用来解释机制；"教学示例不是项目实际数据"。项目真实参数只有一处：`src\marker_detector.py` 第 22～27 行的红色 HSV 阈值常量。
- **为什么容易错**：教学示例常出现在最显眼的位置（表格、手算推导），复习时记忆最深，长期下来很容易和真实参数混淆。
- **如何避免与自检**：看到数字先问"这是教学示例还是源码事实"。自检：能立刻背出真实红色阈值两区间的四个数组（`[0,100,70]`、`[10,255,255]`、`[170,100,70]`、`[179,255,255]`）。

### 13. 项目真实源码必须用"文件 + 函数 + 行号"定位

- **错误理解**：凭记忆说"大概在某个函数里"，或者把教学示例里的行号 / 数值当成源码事实。
- **正确理解**：每个项目事实都应能给出：**文件路径 + 函数名 + 行号**。例如：`src\marker_detector.py` 第 22～27 行（红色 HSV 阈值常量）、第 48 行（`create_red_mask` 中 BGR → HSV）、第 51～52 行（两次 `inRange`）、第 55 行（`bitwise_or` 合并）、第 73 行（`find_target_contour` 中 `findContours`）。
- **为什么容易错**：笔记里既有源码事实又有教学示例，不注明来源就容易互相污染；隔一段时间后记忆只剩"大概"。
- **如何避免与自检**：引用前先打开源码文件核对行号，而不是凭印象。自检：任挑一个事实，能否在 30 秒内指出它的文件、函数与行号。

## L04 Contour、Moments 与 Centroid

### 1. Mask 和 Contour 不是一回事

- **错误理解**：把 Mask 和 Contour 当成同一个东西，认为"找到轮廓就是找到白色像素"，或者把 Mask 说成"目标的形状"。
- **正确理解**：Mask 是**像素层**——与图像同尺寸的 0/255 矩阵，逐像素回答"要不要保留"；Contour 是**区域 / 几何层**——把白色区域的外边界抽出来，用一串边界点表示候选区域。源码里 `create_red_mask()` 产出 Mask，`find_target_contour(mask)` 再用 `cv2.findContours`（第 73 行）把它转成轮廓。
- **为什么容易错**：两者在流程里紧挨着出现，中间只隔一次函数调用；画在图上看，"白色块"和"轮廓"长得很像。
- **如何避免与自检**：复述时先说"哪一层"，再说数据形态：Mask 是像素表，Contour 是边界点集。自检：能否各用一句话说出两者分别"回答什么问题"？

### 2. contours 是轮廓列表，不是单个轮廓

- **错误理解**：把 `contours` 当成一个轮廓，直接对它计算面积，或者认为 `contours` 里装的"就是目标"。
- **正确理解**：`cv2.findContours` 返回的 `contours` 是轮廓**列表**：一张 Mask 可以有 0 个、1 个或多个轮廓。所以源码先判空（第 75～76 行 `len(contours) == 0` → `return None`），再排序（第 78～79 行），最后用下标取第一个（第 80 行 `contours_sorted[0]`）。对空列表直接取 `[0]` 会报错。
- **为什么容易错**：变量名是复数，但口语里"找轮廓"听起来像"找到一个轮廓"；单张图的多数情况下又恰好只有一个轮廓。
- **如何避免与自检**：看到 `contours` 先默念"列表"；取下标前先问"列表可能是空的吗"。自检：能否指出源码里判空、排序、取下标分别在哪些行？

### 3. "最大轮廓 = 目标"只是项目规则，不是万能识别方法

- **错误理解**：把"取最大轮廓"当成通用的目标识别方法，以为"计算机视觉找目标就是这么做的"。
- **正确理解**：这是本项目**人为设计的规则**，前提是受控实验场景："画面里最大的那块红色区域就是标记"（第 78～80 行按 `cv2.contourArea` 排序取第一个）。一旦场景里出现更大的红色干扰物或多个红色目标，规则就可能选错或失效；通用目标识别会用颜色、纹理、形状、模板匹配、机器学习等更复杂的方法。
- **为什么容易错**：规则写在代码里、跑得通，很容易被当成"原理"而不是"约定"；而且它确实在这个场景里工作得很好。
- **如何避免与自检**：叙述时带上前提"在本项目的受控场景里"。自检：能否举出一个让这条规则失效的假想场景？

### 4. contourArea 不等于简单统计 255 像素数量

- **错误理解**：认为 `cv2.contourArea` 就是"数一数 Mask 里有多少个 255 像素"，于是把它和像素计数混为一谈。
- **正确理解**：`contourArea` 面向**轮廓（几何边界）**，按几何方式由轮廓点算出围出来的面积（浮点数）；"统计 255 像素个数"是**像素层**统计。对实心区域两者数值可能接近，但概念、算法、适用对象都不同（轮廓点还被 `CHAIN_APPROX_SIMPLE` 简化过）。源码在第 79、83、140 行使用它。
- **为什么容易错**："面积"这个词天然让人联想到"数格子"，而 Mask 恰好就是一堆 0/255。
- **如何避免与自检**：说面积前先问"算的是轮廓还是像素"。自检：能否说明为什么在空心或边界复杂的区域上，两者的差别会更明显？

### 5. Centroid 不一定等于 Bounding Rectangle 中心

- **错误理解**：用 `(x + w/2, y + h/2)` 当作目标中心，或者认为"质心和矩形中心反正差不多"。
- **正确理解**：矩形中心只由轮廓最外圈的范围决定；质心由面积分布决定（第 100～101 行 `cx = m10/m00`、`cy = m01/m00`）。规则、对称的形状上两者接近；有缺口、细长、弯曲的不规则形状上可能相差明显。本项目运动测量使用质心 `(cx, cy)`，`boundingRect`（第 141 行）得到的 bbox 用于框住目标与辅助检查。
- **为什么容易错**：外接矩形画出来直观、中心容易手算；质心公式需要专门记忆。
- **如何避免与自检**：看到"中心"先问"哪种中心"。自检：画一个 L 形区域，能否指出质心偏向哪一侧、矩形中心在哪里？

### 6. Moments 不是直接"返回中心点"

- **错误理解**：认为 `cv2.moments(contour)` 返回的就是 `(cx, cy)`，或者把 moments 的结果直接当坐标用。
- **正确理解**：`cv2.moments` 返回的是一组**统计量**（字典：`m00`、`m10`、`m01`、……）；本项目先取其中三个，再代入公式 `cx = moments["m10"] / moments["m00"]`、`cy = moments["m01"] / moments["m00"]`（第 100～101 行）才得到质心。中间隔着"取统计量 → 用公式组合"这一步。
- **为什么容易错**：最终结果确实是"用矩算出来的中心"，于是把过程压缩成"moments 给中心"。
- **如何避免与自检**：叙述时分两句：先得到统计量，再计算质心。自检：能否写出 m00 / m10 / m01 与 cx / cy 的关系式？

### 7. m00 可能需要做有效性检查

- **错误理解**：拿到 moments 后直接做除法，不考虑分母为 0 的情况。
- **正确理解**：`m00` 在质心公式里是分母，`m00 == 0` 会导致除零；源码第 97～98 行先检查 `if moments["m00"] == 0: return None`，把"无法计算"变成一次明确的失败返回，由上层 `detect_marker()` 转成 `success=False`。这也是"**使用前检查数据是否有效**"这条工程编程思想的具体落点。
- **为什么容易错**：正常图片里很少遇到退化轮廓，"没出过事"就容易忽略边界情况；公式本身也不会提醒你要检查。
- **如何避免与自检**：看到"除法"就检查分母是否可能为 0。自检：能否说出"无效数据返回 None 而不是崩溃"的好处？

### 8. 一段代码的输入、处理、输出必须分开理解

- **错误理解**：读代码只记函数名和一句"它干了什么"的总结，说不清输入是什么、输出去了哪里。
- **正确理解**：每个函数都按"输入 → 处理 → 输出"三段理解。例：`find_target_contour(mask)` 的输入是 Mask，处理是 `findContours`（第 73 行）→ 判空（第 75～76 行）→ 排序取最大（第 78～80 行）→ 面积门槛（第 82～84 行），输出是"目标轮廓或 None"（第 86 行）；`calculate_centroid(contour)` 输入轮廓、输出 `(cx, cy)` 或 None；`detect_marker()` 负责把这些输入输出串成完整 Pipeline（第 129～151 行）。
- **为什么容易错**：代码跑通后注意力集中在"结果对不对"，容易跳过接口层面的理解；一句话总结往往省掉了输入输出的边界条件。
- **如何避免与自检**：给每个函数写"输入 / 处理 / 输出"三行笔记。自检：能否不看源码说出三个底层函数各自的输入与输出？

### 9. m10 与 m01 写反：不报错，但结果错

- **错误理解**：凭印象写成 `cx = m01/m00`、`cy = m10/m00`，或者觉得下标两个数字"顺序无所谓"。
- **正确理解**：矩 `m_pq` 里第一位是 x 的次数、第二位是 y 的次数：**`m10` 带 x（用于 cx）、`m01` 带 y（用于 cy）**。写反不会报错——程序照常运行，只是把目标中心的 x、y 对调，错误很隐蔽。
- **为什么容易错**：`m10` 和 `m01` 只差一个 0，读代码容易看跳；公式层面没有任何类型检查兜底。
- **如何避免与自检**：记口诀"第一位 x、第二位 y"；手写公式后回读一遍。自检：如果 cx 和 cy 被互换，输出的目标点会跑到画面哪个位置？

### 10. RETR_EXTERNAL / CHAIN_APPROX_SIMPLE 不是可有可无的装饰参数

- **错误理解**：只记函数名 `findContours`，把后两个参数当成"固定搭配"抄下来，不理解它们各自控制什么。
- **正确理解**：两个参数各管一件事：`RETR_EXTERNAL` 决定"**要哪些轮廓**"（只取最外层，不单独返回内部孔洞边界）；`CHAIN_APPROX_SIMPLE` 决定"**轮廓点怎么存**"（简化压缩，只保留必要的点）。它们直接影响拿到什么轮廓、每个轮廓记录多少点。
- **为什么容易错**：参数是大写常量名，看起来像模板代码；平时也看不出明显差别。
- **如何避免与自检**：按"要哪些 / 怎么存"分类记忆。自检：如果要"连内部孔洞也取出来"或"保留每一个边界点"，分别应该改动哪一个参数？

### 11. MIN_AREA 是噪声保护 / 失败判断，不是"识别精度"

- **错误理解**：把 `MIN_AREA` 当成"提高识别准确率"的调参旋钮，认为调小一点"更灵敏、能检测到更远的目标"。
- **正确理解**：`MIN_AREA = 200` 是面积门槛（单位是像素面积，不是长度）：面积太小的候选被当成噪声（第 82～84 行返回 `None`），同时让"没有可靠目标"成为一种明确的失败结果，而不是输出一个不可靠的坐标。调大 / 调小改变的是"什么算可靠目标"的尺度，不是算法本身的能力。
- **为什么容易错**：参数放在"核心参数"区，直觉上像"灵敏度"；门槛调小后确实"更容易检测到东西"，但同时也更容易把噪声当成目标。
- **如何避免与自检**：描述它时用"门槛 / 保护 / 失败判断"，不要用"精度"。自检：14×14 与 15×15 的实心正方形（教学算术示例）在 `MIN_AREA = 200` 下分别是什么结果？

（本节 11 条为 L04 的核心易错点；后续如有新增，继续追加在本节下方。）

## L05 从单张图片到视频：逐帧处理

### 1. 视频不是一张巨大图片

- **错误理解**：认为"视频就是一个很大的图像"，可以像单张图片一样一次性读取、一次性检测；或者以为视频里存的是连续的画面数据。
- **正确理解**：视频可以理解成**按时间顺序排列的一系列静态图片**；计算机逐帧处理视频——"一次拿一帧 → 处理 → 换下一帧"（第 483、485、521 行）。本项目从来没有"把整个视频当一张图"这一步。
- **为什么容易错**：人眼看视频感知到的是连续运动，直觉上会把它当成"一整块连续数据"；播放器把帧快速播出来，也让人误以为视频不是由离散图片组成的。
- **如何避免与自检**：复述视频时始终带上"一系列静态图片"这个说法。自检：不看资料，说出程序处理视频的基本节奏（一次拿一帧 → 处理 → 换下一帧）。

### 2. Frame 是一张实际的图像数组

- **错误理解**：把 Frame 当成一个抽象概念或"时间标记"，认为帧只是"第几帧"这个编号。
- **正确理解**：每一帧都是一张**实际的图片**——在本项目里是 BGR NumPy 数组，有高度、宽度与 3 个颜色通道，可以被 `detect_marker()` 直接处理（第 491 行）。"第几帧"是帧号 `frame` / `frame_index`（第 481、531 行），"那一帧的画面"是 `current_frame`（第 480、532 行），两者不是一回事。
- **为什么容易错**：日常语言里"帧"经常被用来指代"第几帧"这个序号；课本里又常把帧描述成"时间上的一个瞬间"，容易被理解成抽象概念。
- **如何避免与自检**：描述帧时先说数据形态（图像数组、高度 × 宽度 × 3）。自检：说出 `frame`（帧号）与 `current_frame`（图像数据）的区别。

### 3. FPS 决定相邻帧的时间间隔

- **错误理解**：把 FPS 当成"视频清晰度"或"画质参数"；或者认为帧与帧之间还有连续的数据可以取用。
- **正确理解**：FPS 是每秒多少帧，直接决定相邻帧的时间间隔：间隔 = 1/fps；30 fps 时约 0.033333 s。视频是**离散采样**，两帧之间的"中间时刻"没有记录。本项目 fps 从视频文件读取（第 130 行，未硬编码），时间换算在第 494 行 `time_s = frame_index / fps`。
- **为什么容易错**：FPS 常和分辨率、码率一起出现在播放器设置里，容易被归为"画质参数"；而"两帧之间有没有数据"这种问题只有从数据结构角度想才会注意到。
- **如何避免与自检**：看到 fps 先想"它决定时间间隔"。自检：30 fps 的相邻帧间隔是多少秒？fps 在源码里从哪一行来？

### 4. ret 和 frame 不是一回事

- **错误理解**：以为 `cap.read()` 只返回图像；或者看到 `ret` 是 `False` 就把 `frame` 当正常图像继续用，甚至把 `ret` 当成图像变量去检测。
- **正确理解**：`cap.read()` 返回两个值：`ret` 是"**是否成功读取**"的布尔标志，`frame` 才是**图像数据**（BGR NumPy 数组或 `None`）。判断是否读到看 `ret`（第 445、557 行），检测用的是 `frame`（第 491 行接收的是 `current_frame`）。本项目写成 `if not ret or next_frame is None: break`（第 528～530 行），两者都检查。
- **为什么容易错**：两个返回值紧挨在一起出现，变量名又都很短；单帧测试时几乎总是成功，"读不到"这种情况很少见到。
- **如何避免与自检**：记住问句分工——"读到了吗"问 `ret`，"读到了什么"看 `frame`。自检：说出第 444 行与第 527 行两次 `cap.read()` 的返回值分别去了哪里。

### 5. current_frame 不等于整个视频

- **错误理解**：把 `current_frame` 当成"整个视频的数据"，以为它保存着所有帧；或者以为循环结束后 `current_frame` 还留着历史画面。
- **正确理解**：`current_frame` 只是"**当前正在处理的那一帧**"：第 480 行初始化为 `first_frame`，第 532 行被整体替换成 `next_frame`（新读到的下一帧）。历史不留在它里面，而是靠 CSV（第 497 行每帧一行）与 `records`（第 499～510 行）另外记账。
- **为什么容易错**：名字里有 "current"，容易被读成"当前视频"；代码里它又贯穿整个循环，看起来像"主角变量"，容易被赋予超出实际的地位。
- **如何避免与自检**：把它读成"当前这一张图"。自检：循环跑到第 3 轮时，`current_frame` 里装的是第几帧？上一帧的数据在哪里能找到？

### 6. video_tracker 不负责重新发明目标检测算法

- **错误理解**：以为 `video_tracker.py` 里有一套"视频专用的检测算法"，或者认为"视频检测"和"图片检测"是两套不同的算法。
- **正确理解**：`video_tracker.py` 只做"测量与记录"（模块说明第 15～23 行），检测参数的唯一来源是 `src\marker_detector.py`；它不重新定义 `RED_LOWER_1` / `RED_UPPER_1` / `RED_LOWER_2` / `RED_UPPER_2` / `MORPH_KERNEL_SIZE` / `MIN_AREA`（第 19～21 行）。视频检测就是"把同一个检测函数放进逐帧循环"（第 34 行导入、第 491 行调用）。
- **为什么容易错**：文件名叫 "video_tracker"，听起来像是视频领域的新算法模块；它的代码量又比检测模块大，容易误以为"里面重新实现了一套检测"。
- **如何避免与自检**：看到 `video_tracker.py` 先找它**调用**了谁。自检：说出 `detect_marker()` 在第几行被导入、第几行被调用；检测参数定义在哪个文件？

### 7. marker_detector 与 video_tracker 的职责不同

- **错误理解**：把两个模块的职责混在一起：让 `marker_detector` 去管理时间与文件，或者让 `video_tracker` 去修改颜色阈值、轮廓规则。
- **正确理解**：`marker_detector.py` 回答"**这一张图片里目标在哪里**"（单张图片内部：像素 → Mask → 轮廓 → 质心）；`video_tracker.py` 回答"**视频什么时候读哪一帧、如何循环、如何记录结果、如何输出**"（帧与帧之间：序列、时间、文件输出）。这是模块化设计：各管一段、接口清晰、改动互不牵连。
- **为什么容易错**：两个模块在调用链上前后紧挨着（第 34 行导入、第 491 行调用），一次运行里又同时"在干活"，不特意区分就容易把功劳与职责混在一起。
- **如何避免与自检**：用一句话分别说出两个模块"负责回答什么问题"。自检：时间换算（`time_s = frame_index / fps`）该写在哪个模块里？颜色阈值该定义在哪个文件里？

### 8. 检测失败不能随便伪造坐标

- **错误理解**：检测失败时用上一帧坐标顶替、写 0 / -1，或者干脆跳过这一帧不写。
- **正确理解**：失败时 `detected=False`，坐标字段**保持为空**；项目第 399 行的原则是"**失败时绝不写 0 / -1 / nan / 字符串**"，失败行写成 `[frame_index, "%.6f" % time_s, "", "", "", "False"]`（第 410 行）。而且失败**不是跳过**——第 497 行注释明确"每帧一行，检测失败也要写"，这样帧号与时间轴才连续。
- **为什么容易错**：写 0 或沿用上一帧"能让数据看起来完整"，图省事的做法在短时间看不出问题；跳过失败帧时表面数据也"干净"，但时间轴会错位。
- **如何避免与自检**：牢记"**测不到，就明确标记缺失，而不是制造一个假测量**"。自检：打开 `check_csv_data()`（第 643 行起）的相关检查项（第 736～740、794～818 行），说出它如何验证"detected=False 的行 x/y/area 全部为空"和"不存在 x=0, y=0 伪数据"。

### 9. VideoWriter 是写输出视频，不是读取视频

- **错误理解**：把 `cv2.VideoWriter` 与 `cv2.VideoCapture` 记混，以为 VideoWriter 用来"读取视频"，或者把两个对象的功能对调。
- **正确理解**：读取视频用 `cv2.VideoCapture`（第 125 行）；写输出视频用 `cv2.VideoWriter`（第 253 行，创建于 `open_overlay_writer()`）。两者方向相反：一个把视频"读进来"，一个把帧"写出去"。VideoWriter 创建时要给出编码器（fourcc，第 252 行）、fps 和画面尺寸，且写入帧的尺寸必须与之一致（第 513～521 行）。
- **为什么容易错**：两个类名只差一个词（Capture / Writer），函数签名都出现在同一份代码里；不写输出视频的场景下很少接触 VideoWriter。
- **如何避免与自检**：按"进 / 出"记：Capture = 进（读），Writer = 出（写）。自检：说出第 125 行与第 253 行分别创建的是什么对象、各自做什么。

### 10. 使用视频资源后要 release

- **错误理解**：程序跑完就直接结束，不调用 `release()`；或者只释放 `cap` 而忘了 `writer` / CSV 文件。
- **正确理解**：视频读取器、写入器、CSV 文件都要成对释放：第 540～544 行 `finally` 中 `csv_file.close()`（第 541 行）、`cap.release()`（第 542 行）、`writer.release()`（第 544 行，writer 存在时）。放在 `finally` 的意义：无论正常结束、异常还是 Ctrl+C（第 536～539 行），清理都会执行。不释放可能造成输出文件不完整、资源被占用。
- **为什么容易错**：脚本短、跑得快，"不 release 好像也没事"；解释器退出时操作系统最终也会回收资源，掩盖了问题。
- **如何避免与自检**：看到"打开"就找"关闭"。自检：本节要释放的三个资源分别叫什么、在第几行释放？如果程序中途抛异常，`release()` 还会执行吗？

### 11. 循环顺序写反会导致最后一帧被丢掉

- **错误理解**：把循环写成"先读取下一帧、先判断有没有下一帧、再处理"，并认为这只是风格差异。
- **正确理解**：本项目采用的顺序是"**处理当前帧 → 读取下一帧 → 判断是否结束**"：第 491 行检测、第 497 行写 CSV、第 527 行读下一帧、第 528～530 行判断并 `break`。这个顺序保证**最后一帧在 break 之前已被完整处理**；先判断后处理的写法会在发现没有下一帧时顺手丢掉最后一帧。
- **为什么容易错**：两种写法在多数帧上行为一致，差别只在"最后一帧"，不特意对比很难发现；少一帧的错误又不会报错。
- **如何避免与自检**：记住口诀"先处理、后读帧、再判断"。自检：用 3 帧的小视频推演一遍循环，说明第 2 帧（最后一帧）在第几轮、在 break 之前还是之后被处理。

### 12. 视频结束不是检测失败

- **错误理解**：看到最后 `cap.read()` 的 `ret=False`，就以为"最后一帧检测失败了"；或者反过来，把某帧检测失败当成"视频读完了"。
- **正确理解**：两者层次不同——视频结束是**序列层面的正常终止**（第 528～530 行 `break`：读不到下一帧），不是错误；检测失败是**单帧层面的缺失**（该帧没有测到目标，`detected=False`，坐标留空，第 410 行）。视频结束时循环退出；检测失败时循环继续，只影响那一行数据。
- **为什么容易错**：两者都表现为"没有拿到目标坐标"，从输出上看有相似的"缺失感"；代码上 `break` 又紧跟在 `ret` 判断后面，容易和"失败"混淆。
- **如何避免与自检**：先问"是整段结束了，还是这一帧没测到"。自检：`break` 在第几行？它由什么条件触发？检测失败那一帧的 CSV 行长什么样？

（本节 12 条为 L05 的核心易错点；后续如有新增，继续追加在本节下方。）

## L06 从逐帧结果到 CSV：数据记录、字段设计与时间序列

### 1. 逐帧结果只留在单个 result 变量里

- **错误理解**：以为循环里反复写 `result = detect_marker(current_frame)` 就等于"把每帧结果都保存下来了"；以为程序结束后还能从 `result` 里找回历史数据。
- **正确理解**：`result` 是**单帧快照**：第 491 行每一轮都被整体重新赋值，只装"当前这一帧"的检测结果；`current_frame` 第 532 行会被下一帧替换，`frame_index` 第 531 行只是一个递增的编号。历史必须另找地方记账——磁盘上的 CSV（第 483～485 行打开并写表头、第 497 行每帧写一行）与内存里的 `records`（第 476 行创建、第 499～510 行逐帧追加）。程序结束、变量消失，留下来的只有文件。
- **为什么容易错**：变量名始终不变，循环里看起来像"在更新同一个结果"；运行过程中随时打印 `result` 又都能看到数据，容易误以为"数据一直在"。
- **如何避免与自检**：见到"逐帧结果"先问一句："这份数据在程序结束之后还存在哪里？"答不出文件路径，就说明还没有真正记录。自检：说出 `result` 第几行被重新赋值、CSV 第几行写入、`records` 第几行追加。

### 2. records 和 CSV 不是同一张记账表

- **错误理解**：把 `records` 当成"CSV 的另一种写法"，或以为有了 `records` 就不必写 CSV、有了 CSV 就不需要 `records`。
- **正确理解**：两者职责不同。CSV 是**磁盘文件**：全是文本 cell，字段是 `frame / time_s / x_px / y_px / area_px / detected`（第 41、402～410 行），长期保存、供后续分析与其他工具读取。`records` 是**内存列表**：存原始浮点数与布尔值，键名是 `success` 而不是 `detected`（第 502 行）、坐标键名是 `cx / cy / area` 而不是 `x_px / y_px / area_px`（第 505～507 行），只在运行期间存在，供 `summary` 统计（第 562～586 行）与 PNG 回退选帧（第 266～292、316～340 行）使用。
- **为什么容易错**：两者都是"每帧一条"、在循环里紧挨着出现（第 497 行写 CSV、第 499～510 行追加 `records`），数据内容也大部分相同，很容易被当成一份东西。
- **如何避免与自检**：分两条线记：CSV 面向"以后还要读这份数据的人/程序"；`records` 面向"本次运行自己的统计与回退逻辑"。自检：说出 CSV 里的 `detected` 列对应 `records` 里的哪个键，`x_px` 列对应哪个键。

### 3. 检测失败时写 0 / -1 / 上一帧坐标

- **错误理解**：失败帧写 0 或 -1 "占位"，或者复制上一帧坐标让数据"看起来完整"。
- **正确理解**：第 399 行的硬规则是"**失败时绝不写 0 / -1 / nan / 字符串**"，第 410 行只写 `frame`、`time_s`、三个空 cell 与 `"False"`；模块说明第 18 行也明确"不做上一帧预测"。原因：0 与 -1 都是**合法数值**，会被后续统计（如面积 min/median/max，第 575～577 行）和任何时间序列分析当成真实测量——制造"假测量"；写上一帧坐标则是直接伪造数据。空 cell 表达"没测到"，自检用文本视角把它与 `detected=False` 对账（第 794～818 行，第 817 行判定），缺失是可计数、可核对的事实。自检程序专门验证这一点：第 726～727、738 行检查"不存在 x=0, y=0 伪数据"；第 730～732、737 行检查失败行必须全空。
- **为什么容易错**：填 0 / -1 让表格看起来"整齐、不留洞"；沿用上一帧又最省事，短时间看不出差别。
- **如何避免与自检**：牢记"**测不到，就明确标记缺失，而不是制造一个假测量**"。自检：写出失败行的 6 个 cell 分别是什么，并说明为什么 `frame` 与 `time_s` 仍然照常填写（时间轴必须连续）。

### 4. 检测失败的帧直接跳过不写

- **错误理解**：检测失败就不写这一行——"没有数据就不记录"。
- **正确理解**：第 496 行注释明确"**每帧一行，检测失败也要写**"。失败行一样占用一个 frame 编号与 time_s；第 674～675 行自检要求"数据行数 = 实际解码帧数"；第 692～693 行要求 frame 从 0 到 N-1 连续、无重复。跳过失败帧会让"行号对不上帧号"，时间轴出现看不见的缺口，后续按帧对齐数据时就会错位。
- **为什么容易错**：跳过失败帧后 CSV 看起来更"干净"，而且不会报错；只有把 frame 列与帧数对照时才会暴露。
- **如何避免与自检**：把 CSV 理解为"每帧一行的测量台账"而不是"成功案例清单"。自检：读一份 CSV，确认 frame 列恰好是 0, 1, 2, …, N-1。

### 5. 把 y_px 和 y0_px 当成同一列

- **错误理解**：看到 M6 的 `y0_px` 就以为是 M3 的 `y_px` 换了个名字，把两份 CSV 的位置列混用。
- **正确理解**：两列不是同一种测量。M3 的 `y_px` 是**红色标记质心的竖直坐标** `cy`（第 406 行取 `result["cy"]`；上游来自 `src\marker_detector.py` 第 101 行 `cy = m01 / m00`）。M6 的 `y0_px` 是**暗带上缘的竖直位置**（`src\external_oscillation_tracker.py` 第 85 行位置特征说明、第 93 行字段定义、第 326 行取值）。测量对象与几何含义都不同，数值不可互换。
- **为什么容易错**：两个名字都以 `y` 开头、都是"竖直像素位置"，两份 CSV 又都是相似的表格，不追溯来源就分不清。
- **如何避免与自检**：看到位置列先追问"它来自哪个检测流程的哪一行代码"。自检：分别说出 `y_px` 与 `y0_px` 的来源变量与定义行号。

### 6. 以为 CSV 里的数字天生就是"数字"

- **错误理解**：认为 `frame` 列存的就是 int、`time_s` 是 float、`detected` 是布尔值。
- **正确理解**：CSV 里所有 cell 都是**文本**；类型由写入端格式化决定（第 403～410 行：`"%.6f"`、`"%.2f"`、`"%.1f"`、`"True"` / `"False"`），读取端再解析（第 684～685 行把 frame 转 `int`、第 717～721 行把 x/y/area 转 `float`；现行自检统一用 `csv.reader`，第 794～818 行再用文本视角对空字段与 `detected=False` 对账，不再用 `np.genfromtxt`）。所以"字段设计"不只是起名字，还包括**顺序、格式、缺测怎么写、读回来怎么解释**。
- **为什么容易错**：在 Python 里写进去的是数字，用表格软件打开又显示成数字，容易忘记文件本身只存文本。
- **如何避免与自检**：用纯文本编辑器打开 CSV，直接看 `time_s` 与 `detected` 两列究竟长什么样。自检：说出 `detected=True` 行与 `detected=False` 行在 x/y/area 三个 cell 上分别是什么文本。

### 7. 把 CSV_FIELDNAMES 当成随便写的表头文字

- **错误理解**：表头只是给人看的说明，改列名、换顺序是小事。
- **正确理解**：`CSV_FIELDNAMES`（第 41 行）是字段名与顺序的**唯一来源**，被三处依赖：写表头（第 485 行）、校验读回的第一行（第 670～671 行）、校验每个数据行的 cell 数（第 681 / 704 行）。同时，第 402～410 行返回的 6 个值必须与它的顺序一一对应。改动其中任意一处而不注意另一处，自检就会失败。
- **为什么容易错**：表头看起来只是"文字"，改了之后程序不会立刻报错，问题要到读数据或自检时才出现。
- **如何避免与自检**：把"列名与顺序"当成契约。自检：说出 `CSV_FIELDNAMES` 被使用的四个位置，并默写 6 个字段的顺序。

### 8. 把 time_s 当成独立测量出来的时间

- **错误理解**：以为 `time_s` 是从视频里单独测出来的一个量，可以随意填写或替换。
- **正确理解**：`time_s` 由 `frame_index / fps` 推导（第 494 行），`fps` 从视频文件读取、未硬编码（第 130 行）。它是**时间轴坐标**，不是第四个测量值：帧号连续，时间轴才连续；帧号对不上，时间轴就没有意义。M3 现行自检第 9 项专门核对 `time_s` 与 `frame / fps`（第 742～783 行）。M6 同样保持这一原则——时间用原视频绝对时间轴 `frame / fps`，不重新定义时间零点（`src\external_oscillation_tracker.py` 第 322～323 行）。
- **为什么容易错**：`time_s` 与位置列长得一样都是小数，容易被当成"又一个测量值"；手写或补写数据时又最容易被随手改掉。
- **如何避免与自检**：任取一行 CSV，用 frame ÷ fps 心算核对 `time_s`。自检：说出本课为什么**不做**插值、重采样（本课只记录，不改变采样时刻）。

### 9. 以为 M3 和 M6 的 CSV 只有文件名不同

- **错误理解**：按固定列号读两份 CSV（例如"第 5 列都是 area"），或以为 `_track.csv` 与 `_trajectory.csv` 是同一套字段。
- **正确理解**：两份 CSV 共享同一设计思想（第一行表头、每帧一行、frame + time_s 时间轴、detected 标志、失败留空），但字段不同：
  - M3 `_track.csv`（`src\video_tracker.py` 第 41 行，6 列）：`frame, time_s, x_px, y_px, area_px, detected`，由 `demo\run_video_tracking.py` 第 37 行命名；
  - M6 `_trajectory.csv`（`src\external_oscillation_tracker.py` 第 88～97 行，8 列）：`frame, time_s, detected, x_px, y0_px, bbox_w_px, bbox_h_px, area_px`，由 `demo\run_m62_external_tracking.py` 第 54 行命名。
  - 共有：`frame / time_s / detected / x_px / area_px`；M3 独有 `y_px`；M6 独有 `y0_px / bbox_w_px / bbox_h_px`；`detected` 的位置也从第 6 列变成第 3 列。
- **为什么容易错**：两份文件外观相似、都叫"轨迹/追踪 CSV"，且本课第一次把两者放在一起比较，容易只记文件名不记字段。
- **如何避免与自检**：读 CSV 永远"先读表头、按列名取值"，不要背固定列号。自检：默写两份表头，并说出三处字段差异。

### 10. 把调试数据混进正式 CSV

- **错误理解**：调试时想看什么就往 CSV 里加什么列（例如清晰度、耗时、备注文字）。
- **正确理解**：项目里已经有不进 CSV 的先例：`sharpness_list` 只在 PNG 回退方案中使用（第 477、523～524 行），`find_blurriest_frame()` 的注释明确"清晰度指标只在回退方案中使用，不写入 CSV"（第 297～298 行）；CSV 的字段由 `CSV_FIELDNAMES` 固定为 6 列，并受列数与列名自检约束（第 681 / 704 行）。调试量应留在打印输出或内存变量里，不污染正式数据文件。
- **为什么容易错**：调试时"顺手加一列"最快；CSV 又是纯文本，加列不会立刻报错。
- **如何避免与自检**：想加列前先问"这是测量数据，还是调试信息？"自检：对照第 41 行，确认自己手里的 CSV 恰好是约定的 6 列。

### 11. 把 CSV 当成 Excel 工作簿或"带格式的表格文件"

- **错误理解**：以为 `.csv` 文件和 `.xlsx` 一样是"带格式的表格"：可以有多张工作表、带颜色与公式、能保存多个数据类型；或者以为"用 Excel 打开过"的表格就是 CSV。
- **正确理解**：CSV 是**纯文本**：逗号分隔、一行一条记录、第一行是表头（第 40 行注释），全部内容都是文本；`open(csv_path, "w", encoding="utf-8", newline="")` 打开的就是普通文本文件（第 483 行），写入靠标准库 `csv`（第 26 行 `import csv`、第 484 行 `csv.writer`）。它没有工作表、没有公式、没有颜色；M6 也采用同一约定（`src\external_oscillation_tracker.py` 第 367 行注释"行尾使用 \n，与 results/ 下已有 CSV 保持一致"）。
- **为什么容易错**：双击 CSV 默认被 Excel / 表格软件打开，视觉上"很像表格"，容易把软件的显示效果当成文件的真实内容。
- **如何避免与自检**：用纯文本编辑器打开一次 CSV，确认看到的就是"逗号 + 换行"的文本；再想一遍"这份文件里有没有任何格式信息？"（答案是没有）。

### 12. 把表头行当成数据行（或反过来）

- **错误理解**：读取时把第一行也当成一条测量记录，导致"数据行数比帧数多 1"；或者把第一条数据当成列名，导致所有字段名错位。
- **正确理解**：第 485 行写入的第一行就是表头 `CSV_FIELDNAMES`（第 41 行），第 497 行起写的才是数据行；读文件时第 666 行 `header = rows[0]`、第 667 行 `data_rows = rows[1:]` 把两者分开；第 674～675 行的"数据行数"只统计 `rows[1:]`；第 670～671 行专门校验第一行是否等于 `CSV_FIELDNAMES`。
- **为什么容易错**：表头和数据行在同一张文本表里紧挨着；用 `csv.reader` 读回来时两者都是"字符串列表"，不看内容分不清。
- **如何避免与自检**：拿到任何 CSV，先确认"第一行是不是列名"，再数数据行；自检：M3 真实文件共 171 行（1 行表头 + 170 行数据），数据行数应等于实际处理的帧数（第 674～675 行）。

### 13. 把教学伪代码 / 教学示例当成项目真实源码

- **错误理解**：把笔记里为讲解画的流程、编的示例行（例如失败行演示 `4,0.066667,,,,False`）当成 VisionMotion 的真实代码或真实数据；引用时也给不出文件和行号。
- **正确理解**：项目事实必须能定位到"文件 + 函数 + 行号"，例如 `CSV_FIELDNAMES` 在 `src\video_tracker.py` 第 41 行、失败行格式在第 410 行；教学伪代码（如"打开 CSV → 写表头 → 对每一帧写一行"）与教学示例（人为构造的失败行）都只是解释工具，**不是项目代码、不是项目数据**。
- **为什么容易错**：伪代码和真实流程"长得很像"；示例数字又往往比源码行号更醒目、更好记。
- **如何避免与自检**：看到一段代码先问"它能不能在仓库里找到行号？"；看到一串数字先问"它来自哪个真实文件？"。两者只要有一个答不上来，就按教学材料对待。

### 14. 以为 L06 要引入 pandas / 数据库 / FFT / Calibration

## L07 检测失败、质量检查与鲁棒性

### 1. 把"检测失败"当成程序崩溃 / 报错

- **错误理解**：某一帧没检测到目标，就以为程序出错了、坏了、需要修 bug；或者把它和"程序抛异常、直接停止"混为一谈。
- **正确理解**：检测失败是**正常返回值**。`src\marker_detector.py` 的三道判定（无轮廓第 75～76 行、面积 < `MIN_AREA` 第 83～84 行、`m00 == 0` 第 97～98 行）全部是 `return`，`detect_marker()` 最终返回 `{"success": False, "mask": mask}`（第 133、137 行）；逐帧循环继续前进（`src\video_tracker.py` 第 489～532 行）。真正会让本次处理停止的是资源级失败：视频打不开（第 433～435 行）、FPS 非法（第 438～441 行）、第一帧失败（第 444～448 行）。
- **为什么容易错**："失败"在日常语言里等于"事情搞砸了"；终端里"没检测到目标"看起来像错误信息。
- **如何避免与自检**：看控制流：这三道判定里有没有 `raise`？有没有直接结束整个视频处理？自检：分别说出三道判定触发时程序会做什么、循环接下来做什么。

### 2. 以为失败返回字典里 `cx` / `cy` 的值是 None

- **错误理解**：以为检测失败时字典仍然有 `cx` / `cy` / `area` 这些键，只是值为 `None`；于是写 `if result["cx"] is None` 之类的判断。
- **正确理解**：失败字典**只有两个键**：`success` 与 `mask`（第 132～133、136～137 行）；`cx` / `cy` / `area` / `bbox` / `contour` 只在成功分支（第 143～151 行）被放入。正确写法是先看 `success`——项目里的两处示范：`build_csv_row()` 第 401 行、`draw_tracking_frame()` 第 196～207 行。
- **为什么容易错**：很多代码习惯"返回 None 值"而不是"缺少键"；两者外观相似、含义不同（"这个字段没有值" vs "这个字段不存在"）。
- **如何避免与自检**：记住接口契约"先看 success，再取字段"。自检：说出失败字典里恰好有哪两个键；如果对失败字典取 `result["cx"]` 会发生什么（`KeyError`——这是概念推演，不要在项目代码里真的去访问）。

### 3. 把三种不同层次的"失败返回"混为一谈

- **错误理解**：看到 `None` 就以为都是"检测失败"；或者看到 `(None, None)` 以为是"这一帧没测到"。
- **正确理解**：三个层次——① 函数级：`find_target_contour()` 第 76、84 行与 `calculate_centroid()` 第 98 行的 `None` = "这个子步骤没有结果"；② 视频级：`open_video()` 第 124～127 行返回 `(None, None)`、`track_video()` 第 433～435 行返回 `None` = "整段视频无法处理"；③ 帧级：`detect_marker()` 第 133、137 行的 `success=False` 字典 = "这一帧没测到，但流程继续"。
- **为什么容易错**：都写作 `None`，不结合位置和函数看很难分辨。
- **如何避免与自检**：读代码时永远问"这个 None 出现在哪一层、谁在消费它、它让程序继续还是停止"。自检：给每个 None 标注"函数级 / 视频级"并说出后果。

### 4. 检测失败时用 0 / -1 / nan / 上一帧坐标"补"上

- **错误理解**：失败时不写空，而是填 0、-1、nan，或干脆抄上一帧坐标——"有数字总比空着强"。
- **正确理解**：第 399 行的正式原则是"**失败时绝不写 0 / -1 / nan / 字符串**"，失败行必须写成 `[frame_index, "%.6f" % time_s, "", "", "", "False"]`（第 410 行）。原因：0 是合法坐标（自检第 726～727 行专门查 (0,0)，第 738 行列为伪数据检查）；-1 会被当数字参与计算；nan 文本无法与"空字段"区分（第 794～818 行的空字段语义对账会因此错乱）；上一帧坐标是伪造测量，事后无法分辨"没动"和"没测到"。
- **为什么容易错**：很多软件默认用 0 表示空；"先填个数凑整"在调试时很顺手。
- **如何避免与自检**：把"缺失"当作一种**明确的状态**，不是缺失的数字。自检：说出 (0,0) 检查（第 726～727、738 行）与空字段语义对账（第 794～818 行）分别在哪些行、各自抓什么。

### 5. 把 "DETECTION FAILED" 当成画面上的装饰文字

- **错误理解**：以为那行红字只是随便加的提示，甚至以为失败帧也会画框、只是标了字。
- **正确理解**：`draw_tracking_frame()` 第 196～207 行是完整分支：失败帧只写红色 "DETECTION FAILED"（位置 (10, 70)、颜色 `(0, 0, 255)`）然后 `return overlay`（第 207 行）——绿框、圆圈、十字、坐标文字（第 209～237 行）**全部不会画**。它和 CSV 第 410 行"不伪造缺失"是同一条原则的两种呈现。
- **为什么容易错**：文字提示看起来像"辅助信息"；不点开函数代码看不到它后面直接 `return`。
- **如何避免与自检**：把失败帧显示理解为"可视化契约"。自检：在叠加视频里找到出现该文字的帧，核对同 frame 号 CSV 行是否为 `False` + 空字段（注意：本课核对的两份 CSV 都没有失败帧，这项自检需要等遇到含失败的真实数据时再做）。

### 6. 以为中间有一帧坏帧，整个视频处理就会中断

- **错误理解**：觉得"检测失败 = 循环报错退出"，后面的帧都不会被处理。
- **正确理解**：逐帧循环（第 489～532 行）里没有因 `success=False` 而 `break` / `return` / 抛异常的路径；失败帧照写 CSV（第 497 行）、照进 `records`（第 499～510 行）、照画失败提示（第 196～207 行），然后统一进入"读下一帧"（第 527 行）。唯一的 `break` 在第 528～530 行（读不到下一帧 = 视频正常结束）；`KeyboardInterrupt` 在第 536～539 行单独处理。
- **为什么容易错**：把"检测失败"想成异常；很多程序的错误处理确实是"一出错就退出"。
- **如何避免与自检**：数一数循环里一共有几条退出路径、各自触发条件。自检：说出"这一帧没测到"与"视频读完了"在代码里分别对应哪一行。

### 7. 只看 `detection_rate` 就给数据下结论

- **错误理解**：看到 `detection_rate = 1.0`（或 99%）就说"数据没问题，可以直接分析"；看到某个比例低就说"数据全废"。
- **正确理解**：`detection_rate`（第 570～573 行，打印第 625 行）只回答"有多少帧测到了"：① 它不反映失败分布（另看 `longest_miss_run`，第 574、591～604 行）；② 它不校验数值合理性（另看 `check_csv_data()` 十项检查，第 643～824 行）；③ 100% 检出也不等于可分析——M6 的质量检查在 100% 检出之外还要求无空值、无 >30 px 突跳、无候选歧义、时间严格（`src\external_oscillation_tracker.py` 第 477～526 行）。
- **为什么容易错**：一个百分比最直观、最好记，容易"一个数字定生死"。
- **如何避免与自检**：永远"率 + 分布 + 数值检查"三件套一起看。自检：用课堂上 A / B 两段 95% 检出率的例子（教学示例，非真实数据）说明同样比例为什么可信度不同。

### 8. 把"最长连续丢失"与"丢失帧总数"混为一谈

- **错误理解**：以为 `longest_miss_run` 就是失败帧总数，或以为"失败帧总数 > 0"时 `longest_miss_run` 一定 > 1。
- **正确理解**：`missed_frames` 是总数（第 572 行）；`longest_miss_run` 是**连续**最大值（第 591～604 行）：成功清零、失败累加、刷新历史最大（第 598～603 行）。`longest_miss_run = 0` ⇔ 整段没有失败帧；反过来，5 个分散失败帧的 `longest_miss_run` 是 1，5 个连续失败帧才是 5。
- **为什么容易错**：两个指标都和"丢"有关，名字又都带"丢失"，不看算法很容易合并成一个概念。
- **如何避免与自检**：动手在纸上对两个 10 帧假想序列（教学练习）算一遍两个指标。自检：说出成功帧在第 598～599 行对计数器做了什么。

### 9. 以为 NaN 是"写进 CSV 的失败标记"

- **错误理解**：以为检测失败时项目往 CSV 里写了 `nan`，读到 NaN 就知道失败了；或者反过来，以为 NaN 是数据错误。
- **正确理解**：文件里失败字段是**空**（第 410 行），不是 `nan` 文本——第 399 行明确禁止写 nan。现行 `check_csv_data()` 不再用 `np.genfromtxt`，而是用 `csv.reader` 的文本视角对账：空测量字段（`x_px` 为空）的行数必须等于 `detected=False` 行数（第 794～818 行，第 817 行判定）。它不是"数据错误"，而是"缺失在数值视角下的样子"。
- **为什么容易错**：pandas / NumPy 世界里 NaN 到处都是，"缺失 = NaN"成了肌肉记忆；但**文件里怎么表示**与**读进来怎么表示**是两件事。
- **如何避免与自检**：用文本编辑器（或 `csv.reader`）看失败行的原始文本。自检：说出"文件里的空字段"与"自检时的空字段判定"分别由哪几行代码产生。

### 10. 把 M3 的十项检查与 M6 的独立质量检查混用

- **错误理解**：拿 `check_csv_data()` 去检查 M6 的 `_trajectory.csv`，或拿 M6 的标准要求 M3 的 `_track.csv`"必须 100% 检出"。
- **正确理解**：两份文件、两个函数、两套口径。M3（`src\video_tracker.py` 第 643～824 行，记录型，十项检查）：允许失败存在，但要求失败被诚实标记——失败行留空（第 737 行）、空测量字段与 `detected=False` 对账（第 794～818 行）、无 (0,0)（第 726～727、738 行）、坐标在范围内（第 728～729 行）、`time_s` 与 `frame / fps` 一致（第 742～783 行）。M6（`src\external_oscillation_tracker.py` 第 442～549 行，分析型）：把 "detected 全为 True"（第 477～480 行）、无空值（第 482～484 行）、无 >30 px 突跳（第 505～508 行）、无候选歧义（第 510～517 行）、时间严格（第 519～526 行）列为硬性门槛，数值范围只是信息项（第 492～497 行）。
- **为什么容易错**：两份文件长得像、名字都带"轨迹 / 追踪"，检查函数都返回 `(checks, passed)`，很容易"拿来就用"。
- **如何避免与自检**：先问"这是记录型数据还是分析型数据、下游要拿它做什么"。自检：分别说出两套检查各自至少 3 条门槛和对应行号。

### 11. 把教学示例当成真实数据

- **错误理解**：把课堂上构造的"A / B 两段 95% 检出率"例子、或笔记里的失败行演示 `4,0.066667,,,,False`，当成 VisionMotion 的真实运行结果引用。
- **正确理解**：真实数据是仓库 `results\` 下的文件：本课只读核对的两份真实 CSV 都是 **100% 检出、0 失败行、0 空字段**（详见 `L07_检测失败与鲁棒性.md` 第 16 节）；A / B 例子与演示失败行都是**教学示例**。
- **为什么容易错**：示例数字醒目、好记，复习时最容易"记串"；真实统计反而更长更啰嗦。
- **如何避免与自检**：看到任何数字先问"来自哪个文件哪一行？"答不上来就按教学示例对待，并主动标注"非真实数据"。

### 12. 把"设计上支持失败处理"说成"实测验证过失败处理"

- **错误理解**：因为源码里写了完整的失败处理，就在总结 / 汇报里说"实验验证了系统能处理检测失败"。
- **正确理解**：本课的两份真实数据都没有失败帧（`detection_rate` 均为 1.0000，`longest_miss_run` 均为 0），失败处理是"**设计可核对（有行号）、实测未触发**"。证据边界（`L07_检测失败与鲁棒性.md` 第 15 节）：源码能证明"失败时会怎么做"；真实 CSV 能证明"这两段数据没有失败"；"失败流程端到端跑通"需要新的、真实触发失败的实验——本课不做。
- **为什么容易错**：代码里功能齐全，很容易顺手写成"已实现并验证"；"没有观察到"听起来像工作没做完。
- **如何避免与自检**：写结论前先划证据边界；把"没有观察到失败"照实写成"没有观察到失败"，不升级为"系统不会失败"或"已通过失败场景验证"。

### 13. 以为坐标范围检查不需要画面尺寸，光看 CSV 就能判断越界

- **错误理解**：只看 CSV 里的 x / y 数值，就断言"这些坐标都合法 / 有越界"，或以为画面尺寸是硬编码的 1920×1080。
- **正确理解**：`check_csv_data(csv_path, expected_rows, frame_width, frame_height, fps=None)` 第 728～729 行用**传入的画面宽高**做范围检查 `0 ≤ x ≤ frame_width`、`0 ≤ y ≤ frame_height`；这两个参数来自运行时的 `summary["width"]` / `["height"]`（`demo\run_video_tracking.py` 第 55～56 行），即程序实际处理的画面尺寸，不是硬编码。CSV 文件本身**不含画面尺寸**，所以单看文件无法断言越界。M6 的坐标范围检查则只是信息项（`src\external_oscillation_tracker.py` 第 492～497 行）。
- **为什么容易错**：范围检查藏在"读回文件"的函数里，参数是调用方传的，不打开 demo 文件看不到来源。
- **如何避免与自检**：看到"范围检查"先问"范围的上限从哪里来"。自检：说出 `frame_width` / `frame_height` 的传入链路（demo 第 52～57 行 → 函数签名第 643 行 → 第 728 行）。

## L08 为什么像素不能直接当毫米（像素与毫米标定）

### 1. 把像素当成固定的现实长度

- **错误理解**：觉得"1 px 就是 x mm"，或者拿一个从别的视频 / 别的教程记来的系数直接乘，把像素数当成长度用。
- **正确理解**：像素是采样格子；一个像素代表多少现实长度由**这一次拍摄**的几何决定。项目里的直接证据：M4 `PX_PER_MM = 5.756961`、M5 `PX_PER_MM_004 = 6.086399`（`src\displacement.py` 第 52 行、`src\dynamic_displacement.py` 第 64 行），两次拍摄的尺度相差约 5.72%。"1 px 等于多少 mm"必须补上"哪一次拍摄、哪两个点、哪一个已知真实长度"。
- **为什么容易错**：屏幕上像素均匀排列，容易误以为它像尺子的刻度一样有固定物理长度；很多科普内容也只给一个"大概系数"。
- **如何避免与自检**：看到 px 与 mm 混排的数据，先找它的标定常量与来源行；自检：说出 M4 / M5 两组常量各自写在哪一行、为什么不能互换。

### 2. 把 px/mm 与 mm/px 乘反（换算方向错）

- **错误理解**：把 `ds_mm = ds_px / PX_PER_MM` 写成 `ds_px × PX_PER_MM`，或把 `MM_PER_PX` 乘到错误的一侧。
- **正确理解**：`px/mm` 是"每毫米多少像素"，`mm/px` 是"每像素多少毫米"，两者互为倒数（`src\calibration.py` 第 137～138 行；自检见 `src\displacement.py` 第 142～147 行、`src\dynamic_displacement.py` 第 159～165 行）。正确换算是 `ds_mm = ds_px / PX_PER_MM = ds_px × MM_PER_PX`（`src\displacement.py` 第 369 行、`src\dynamic_displacement.py` 第 379 行）。
- **为什么容易错**：中文语序（"每毫米多少像素"）和公式里的位置不一致，凭印象乘除很容易反向。
- **如何避免与自检**：先写单位链条再写公式：`px ÷ (px/mm) = mm`；自检：用一个真实行（例如 `results\EXP-003-STATIC-002_ds.csv` 第 1 行 `ds_px = 4.335`、`ds_mm = 0.7530`）验证自己写的公式。

### 3. 以为"分辨率越高，像素代表的现实长度越小"是普遍规律

- **错误理解**：只看分辨率一个因素，就断定像素尺度变大或变小。
- **正确理解**：像素尺度由整套拍摄几何决定——拍摄距离、镜头（视场 / 焦距）、分辨率（画幅）、图像缩放（重采样 / 裁剪 / 数码变焦）都会改变它。项目里能核对的绑定信号：M4 标定注明坐标系统是 `CAP_PROP_ORIENTATION_AUTO=1` 之后的 1920 × 1080 画幅（`src\displacement.py` 第 42～43 行）——标定数值与画幅绑定。
- **为什么容易错**："像素更多 = 更精细"的直觉被错误外推成"像素更小 = 物理长度更短"。
- **如何避免与自检**：把"分辨率"改成"整套拍摄几何"再开口；自检：说出四种影响因素，并说明哪一个是本项目里能直接看到证据的。

### 4. 把 M4 的常量套用到 M5（或反过来）

- **错误理解**：觉得"反正都是同一把尺、同一种实验，用哪套系数都行"。
- **正确理解**：`src\dynamic_displacement.py` 第 20～23 行明文禁止"把 M4 的常量搬进来"，并禁止 `import src.displacement`（防止误用 M4 的 gate 与 s0 规则）；第 68～76 行的专属 gate 标题就是"与 M4 gate 完全不同，不得混用"。两组尺度相差约 5.72%：混用不会报错，只会让全部 mm 数字系统性偏掉。
- **为什么容易错**：项目里两套常量名字很像（只差 `_004` 后缀），而且都能通过自检——自检只证明"常量与自己的标定点自洽"，不证明"常量属于这段视频"。
- **如何避免与自检**：写数据结论前先报出"本次使用的常量与来源"（`demo\run_m43_displacement.py` 第 146～158 行、`demo\run_m52_dynamic_displacement.py` 第 72～98 行就是这么打印的）；自检：说出 M5 的两个标定点坐标与真实距离（第 60～62 行）。

### 5. 把 ds_mm 当成"另测了一遍"的量

- **错误理解**：以为 CSV 里的 `ds_mm` 是独立测量结果，可以和 `ds_px` 互相"印证"。
- **正确理解**：`ds_mm` 由 `ds_px` 经冻结标定换算得到：`ds_mm = ds_px / PX_PER_MM`（`src\displacement.py` 第 368～369 行、`src\dynamic_displacement.py` 第 378～379 行）。所以"mm 数据的可靠性 = 标定的可靠性 × 像素数据的可靠性"——两条链任何一条出问题，mm 都会错。
- **为什么容易错**：同一行里有两列不同的数，看起来像两次测量；而换算发生在代码里，不在 CSV 里。
- **如何避免与自检**：把 `ds_mm` 读成"`ds_px` 的换算视图"；自检：说出自检为什么能核对 `ds_mm = ds_px / PX_PER_MM_004`（`src\dynamic_displacement.py` 第 1140～1148 行）。

### 6. 给 M6 外部视频"配"一个 mm 系数

- **错误理解**：觉得 M6 的 `y0_px` 也能"顺手"换成毫米，或者从别处找一个系数套上去。
- **正确理解**：`src\external_oscillation_tracker.py` 第 31～34 行明文写着"本模块不做：标定（px/mm）、位移换算、周期、频率、FFT…"；它的正式轨迹 CSV 只有 8 列像素字段（第 88～97 行），没有 `s_px` / `ds_px` / `ds_mm`；项目里也没有这份外部视频的已知真实长度。任何 mm 结论都超出证据边界。
- **为什么容易错**："多一个单位看起来更专业"；而这份数据来自外部公开数据集，很容易被当成"项目自采数据"随口换算。
- **如何避免与自检**：先看它是不是自带真实长度、模块有没有明文禁止；自检：说出 M6 的正式位置特征（`y0_px = 暗带上缘`，第 19、84 行）与它的单位。

### 7. 以为 calibration.py 会读视频 / 图片、使用 OpenCV 或写文件

- **错误理解**：看到"标定"两个字，就以为 `src\calibration.py` 负责从视频里找标定点、画图、存文件。
- **正确理解**：`src\calibration.py` 是**纯数学模块**：第 6 行原文"它不读视频、不读图片、不保存文件、不使用 OpenCV，只依赖标准库 math"；第 24 行是全文唯一 import（`import math`）；找点、读视频、写 CSV 都在别的模块（`demo\pick_calibration_points.py`、`src\video_tracker.py`、`src\displacement.py` 等）。坐标一旦作为参数传进来，标定就只剩数学。
- **为什么容易错**："标定"这个词在别的工具链里常常指一整套交互流程（选点、求解、去畸变）。
- **如何避免与自检**：打开文件数一遍 import；自检：说出该文件里 `compute_scale()` 的三个参数名，以及它们分别由谁提供。

### 8. 把 pixel_distance 当成毫米距离

- **错误理解**：看到 `pixel_distance ≈ 345.42` 就以为"两点相距约 345 毫米"。
- **正确理解**：`pixel_distance` 是像素距离 `L_pixel`（`src\calibration.py` 第 128～131 行），换算是 `L_real = L_pixel / px_per_mm`：M4 的 `345.418199 / 5.756961 = 60.0 mm`，正好是标定用的真实距离；M5 的 `608.634653 / 6.086399 ≈ 100.0 mm`。
- **为什么容易错**：数字长得很像"长度"，而单位（px）只在注释与变量名里。
- **如何避免与自检**：任何长度先说单位、再说换算系数；自检：手算 M4 标定点的 `L_pixel` 并除以 60.0，看是否回到 5.756961（容差 1e-4）。

### 9. 以为可以随手重算 / 修改冻结常量（或把自检当成重新标定）

- **错误理解**：觉得自检既然会"复算"，那常量就可以随时按复算值改一下；或者标定点换个帧号也无所谓。
- **正确理解**：`src\displacement.py` 第 47 行原文"下面三个数值是这组标定点的正式冻结结果，本模块不做任何重新标定"；`src\dynamic_displacement.py` 第 59 行原文"已冻结，不得重新标定"；自检（第 98～150 行 / 第 121～174 行）只用来发现手抄错误与不自治，容差 1e-4，不会自动改常量。
- **为什么容易错**：自检打印"复算值"，看起来像给出了"更好的数"；但复算用的是同一组点，不是新的标定证据。
- **如何避免与自检**：把"需要改常量"当成触发条件——必须重新走一遍"已知真实长度 + 人工确认"，而不是改数字；自检：说出冻结常量的三条来源信息（视频 / 帧 / 坐标系）。

### 10. 把 x0_px 当成存在的字段

- **错误理解**：凭"y0_px 存在"就推断"x0_px 也存在"，在笔记或脚本里引用 `x0_px`。
- **正确理解**：全项目（排除 `.venv`、`__pycache__`）搜索确认：**不存在 `x0_px`**；实际存在的字段是 `x_px`（M3 水平坐标 / M6 bbox 中心）、`y_px`（M3 质心竖直坐标）、`s_px`（投影坐标）、`ds_px`（像素位移）、`ds_mm`（毫米位移）、`y0_px`（M6 暗带上缘）。`x_px` 与 `y_px` 在 `src\video_tracker.py` 第 41 行；`y0_px` 在 `src\external_oscillation_tracker.py` 第 93 行；`s_px` / `ds_px` / `ds_mm` 在 `src\displacement.py` 第 75～77 行。
- **为什么容易错**：对称命名的直觉（"有 y0 就有 x0"）在这里不成立。
- **如何避免与自检**：以搜索为准，不以"看起来该有"为准；自检：在仓库里搜一遍 `x0_px`，确认零命中。

### 11. 把 y0_px 里的 0 当数字读

- **错误理解**：把 `y0_px = 508` 读成"y=0、px=508"，或者把字段名写成 `y_0px` / `y_0_px`。
- **正确理解**：`y0_px` 是一个完整字段名，其中的 `0` 是**字段名的一部分**，不参与任何计算；源码里它以字符串形式出现在表头（`src\external_oscillation_tracker.py` 第 93 行）与位置特征名称（第 85 行 `POSITION_FEATURE_NAME = "y0_px = 暗带上缘（M6.2-2B 冻结）"`）。它表示"暗带上缘的竖直像素位置"，与 M3 的 `y_px`（质心竖直坐标）不是同一种测量。
- **为什么容易错**：下标式的命名习惯让人想把名字里的字符拆开当变量与数字。
- **如何避免与自检**：把 `y0_px` 当作不可拆的标识符；自检：说出它与 `y_px` 的语义差别（L01 / L06 已建立）。

### 12. 用文件里已舍入的 ds_px 反算 ds_mm，看到 ±0.0001 的差就以为数据错了

- **错误理解**：拿 CSV 里的 `ds_px`（3 位小数）去除以 `PX_PER_MM`，发现和 `ds_mm`（4 位小数）差 0.0001，就断定数据或公式有问题。
- **正确理解**：`ds_mm` 是用**未舍入**的 `ds_px` 算出来再舍入的，属于正常"双重舍入"。真实例子：`results\EXP-003-STATIC-003_ds.csv` 第 1 行 `ds_px = 0.164`、`ds_mm = 0.0284`，用文件值反算得到 0.0285（差 0.0001）。模块自检为此使用 0.0005 mm 容差（`src\displacement.py` 第 800 行、`src\dynamic_displacement.py` 第 1143 行）。
- **为什么容易错**：看到两列对不上，第一反应是"有 bug"，而不是"舍入顺序不同"。
- **如何避免与自检**：先算一遍"舍入误差的上界"（这里约 0.0001 mm），再看差异是否落在容差内；自检：说出自检容差两个数值（0.002 px / 0.0005 mm）分别写在哪一行。

### 13. 忽略"标定只对本次拍摄有效"，跨分辨率 / 跨裁剪搬用常量

- **错误理解**：把 M4 的 `5.756961` 当成"这个项目的像素系数"，用到任何一份图像或视频上。
- **正确理解**：标定与画幅、缩放、拍摄几何绑定（M4 的来源行写明 1920 × 1080 坐标系，`src\displacement.py` 第 42～43 行）；对图像做缩放 / 裁剪 / 数码变焦后，像素坐标被重采样，原常量不再适用；换实验必须重新标定并重新冻结（`src\dynamic_displacement.py` 第 59 行）。
- **为什么容易错**：项目里只有一个"看起来很像通用系数"的数字；而缩放、裁剪往往发生在别处，不会被记进标定笔记。
- **如何避免与自检**：把常量与"产物文件名 + 画幅 + 来源帧"绑在一起记；自检：说出 M4 与 M5 常量各自绑定的视频与画幅。

## L09 标定、方向向量与一维投影

### 1. 用原始方向向量直接算 s（忘记归一化）

- **错误理解**：把原始方向向量 `v = (dx, dy)` 直接代进 `s = x·ux + y·uy`，得到一个被放大过的数还当成正确投影。
- **正确理解**：`s = x·ux + y·uy` 只有在方向向量长度为 1 时才等于"沿方向的像素距离"。项目里由 `project_point()` 第 196～202 行统一兜底（函数不假设调用方守规矩）；但手算或自己写脚本时必须先归一化。教学反例（非项目数据）：`u_raw = (2, 0)`、点 `(10, 0)` 会得到 `s = 20`，正确的是 `10`。
- **为什么容易错**：归一化写在 `unit_direction()` 里，点积写在 `project_point()` 里，两段代码分开，容易只盯着 `return x * ux + y * uy` 这一行。
- **如何避免与自检**：写任何点积前先问"这个方向向量的模是不是 1"；自检：用 M4 的 `U` 手算一次 `s`，与 `results\EXP-003-STATIC-002_ds.csv` 里的 `s_px` 比，差应落在 5e-4 px 舍入上界内。

### 2. 以为冻结的 U 已经是精确的单位向量

- **错误理解**：把 `U = (0.999976, -0.006894)` 当成模恰好等于 1 的向量，觉得"再归一化一次是多余的"。
- **正确理解**：冻结常量只写 6 位小数：`|U| = 0.999999763906`、`|U_004| = 0.999999655816`，与 1 分别差约 2e-7 / 3e-7——它们只是"在自检容差内"的单位向量（M4 容差 `1e-4`，`src\displacement.py` 第 136～141 行；M5 容差 `1e-6`，`src\dynamic_displacement.py` 第 138～144 行）。
- **为什么容易错**：源码注释直接写"单位向量"，很自然会理解成"精确等于 1"。
- **如何避免与自检**：把"再次归一化"记成流水线的一环（`project_point()` 第 196～202 行）；自检：说出 `|U|` 与 `|U_004|` 各是多少、两次归一化分别在第几行。

### 3. 手算 s_px 与 CSV 差 2.5e-4 就以为数据错了

- **错误理解**：拿 `x_px` / `y_px` 按公式手算 `s`，发现与 CSV 里的 `s_px` 差 2～3 个万分之一像素，就断定程序或数据有问题。
- **正确理解**：差异有两层已知来源：① `project_point()` 会**再次归一化**（不计入会差到 `8.299e-4 ~ 9.235e-4 px`）；② `s_px` 只写 3 位小数，舍入上界正好是 `5e-4 px`。把归一化算进去后，M4 的 1050 行、M5 的 1766 行最大偏差为 `4.974e-4 / 4.998e-4 px`，正落在上界内——是文本舍入，不是算法误差。
- **为什么容易错**：差异出现在小数点后第 4 位，看起来"对不上"；而这两层原因一个在代码里、一个在文件格式里，都不显眼。
- **如何避免与自检**：先把"再次归一化 + 3 位小数舍入上界"两步算一遍，再怀疑数据；自检：复算 frame 0（M4：`x_px = 1083.63`、`y_px = 464.97`）看是否回到 `1080.399`。

### 4. 把 s_px 当位移

- **错误理解**：看到 `s_px` 随时间变化，就直接把它当作"位移曲线"解释，甚至直接读它的差值当振幅。
- **正确理解**：`s_px` 是沿尺方向的一维**坐标**（位置），不是位移；位移是相对某个基线 `s0` 的差：`ds_px = s_px - s0`（`src\displacement.py` 第 368～369 行）。`s0` 怎么选（`compute_s0()`，第 317 行起）、valid gate 的完整规则（第 57～64 行）都属于 L10。
- **为什么容易错**：传感器语境里"投影信号"常被直接叫位移；而 `s_px` 与 `ds_px` 名字只差一个字母。
- **如何避免与自检**：每引用一个一维量，先说清它的基线是什么；自检：说出 `s_px` 与 `ds_px` 的定义式各是什么、写在哪一行。

### 5. 把方向取反（P2 → P1）而不追问约定

- **错误理解**：随手交换两个标定点做复算，或把"10 cm → 16 cm"写成"16 cm → 10 cm"，结果 `s` 与 `ds` 全部反号。
- **正确理解**：方向约定写在源码里：`unit_direction()` docstring 第 149 行写"从 10 cm 刻线指向 16 cm 刻线"；M5 的自检第 167～172 行直接用 `U_004[0] > 0` 锁定"ds 增大"为正向。方向一取反，全部位移的符号都会跟着反，而且不会报错。
- **为什么容易错**：两个点在画面里谁先谁后，肉眼看不出"正确方向"，只有注释与自检记录约定。
- **如何避免与自检**：复算前先读常量注释确认方向；自检：说出 M4 / M5 的方向约定各写在哪一行。

### 6. 把 ux、uy 与 cos/sin 的关系记反

- **错误理解**：按数学课"y 向上"的直觉理解 `uy`，把 `uy < 0` 读成"指向下方"。
- **正确理解**：图像坐标系 y 轴向下（`src\calibration.py` 第 9～10 行），所以 `u = (cos θ, sin θ)` 里 `uy < 0` 表示方向**略向上**。M4 的 `U` 与 +x 轴夹角约 **−0.395°**、M5 的 `U_004` 约 **−0.224°**——两个方向都接近水平、略向上。
- **为什么容易错**：看数字时自动套用数学坐标系；而"负角"在图像坐标系里的直观含义正好相反。
- **如何避免与自检**：见到 `uy` 先默念"图像 y 向下"；自检：说出 M4 / M5 方向与 +x 轴的夹角。

### 7. 把点积与逐元素相乘混淆

- **错误理解**：以为 `s = x·ux + y·uy` 是"x 投影一次、y 投影一次，得到两个结果"。
- **正确理解**：点积的结果是**一个标量**：两个分量相乘再相加，`u` 用它把二维点压成一条数轴上的坐标；这也正是"一维投影"的由来（第 180 行公式说明、第 204 行实现）。
- **为什么容易错**：中学阶段"乘法"通常是分量各自运算；而这里两个分量最后要相加。
- **如何避免与自检**：记住 `a·b = ax·bx + ay·by = |a||b|cos θ`；自检：手算一次 frame 0 的 `s`（两个乘积、一次加法）。

### 8. 以为投影"丢掉了 y 信息"

- **错误理解**：看到公式里出现了 `x`、`y` 两个分量却只得到一个数，就说"y 被丢掉了"。
- **正确理解**：`y` 仍然通过 `uy` 进入 `s`（`y·uy` 是两项之一）；准确的说法是"**垂直于 u 的分量对 s 的贡献为 0**"。正交分解 `v = (v·u)u + (v - (v·u)u)` 里，垂直分量与 `u` 的点积恒为 0。
- **为什么容易错**："降维"听起来像"丢信息"，而点积确实只输出一个数。
- **如何避免与自检**：把"丢掉"改成"垂直分量贡献为 0"再开口；自检：说明 `uy` 在 M4 里具体等于多少、它乘进公式后贡献有多大。

### 9. 以为"削弱垂直分量" = 垂直方向的真实运动不存在

- **错误理解**：既然投影专门保留沿运动方向的分量、削弱垂直方向分量，就认为垂直方向"没有运动"或"动了也测得到"。
- **正确理解**：这是有意的降维取舍：垂直方向若真有运动，`s` 看不到它——垂直移动 10 px，`s` 里只漏进不到 0.07 px（因为 `uy` 只有千分之几）。报告里要把这条取舍写清楚，而不是当成 bug 或当成"垂直没有运动"的证据。
- **为什么容易错**：投影结果很"干净"，容易把"没看到"当成"没有发生"。
- **如何避免与自检**：写结论时用"本一维信号对垂直方向不敏感"的说法；自检：用 `uy = -0.006894` 算一次"垂直移动 10 px 会漏进多少"。

### 10. 把 px/mm 与 mm/px 乘反

- **错误理解**：把 `ds_mm = ds_px / PX_PER_MM` 写成 `ds_px × PX_PER_MM`，或把倒数用反。
- **正确理解**：`ds_mm = ds_px / PX_PER_MM`（等价于 `ds_px × MM_PER_PX`）；写反不是"差一点点"，而是变成约 **33.14 倍**（`5.756961²`）。单位链条：`px ÷ (px/mm) = mm`；自检见 `src\displacement.py` 第 142～147 行、`src\dynamic_displacement.py` 第 159～165 行。
- **为什么容易错**：中文语序与公式位置不一致，凭印象很容易反向。
- **如何避免与自检**：先写单位链条再写公式；自检：用 `results\EXP-003-STATIC-002_ds.csv` 第 1 行（`ds_px = 4.335`、`ds_mm = 0.7530`）验证自己写的换算。

### 11. 混用 M4 与 M5 的方向常量

- **错误理解**：觉得"方向都是水平的，用哪个 `U` 都一样"。
- **正确理解**：两组方向绑定各自的拍摄：M4 约 −0.395°、M5 约 −0.224°（尺度还相差约 5.72%）。混用不会报错，但会把本该被削弱的垂直分量错误地混入或剔除。源码从结构上防混用：`src\dynamic_displacement.py` 第 20～23 行禁止把 M4 常量搬进来、禁止 `import src.displacement`；第 68 行写明专属 gate"与 M4 gate 完全不同，不得混用"。
- **为什么容易错**：两个常量名字只差 `_004` 后缀，而且都能通过各自的自检——自检只证明"常量与自己的标定点自洽"。
- **如何避免与自检**：写结论前先报出"本次用的方向常量与来源"，像 `demo` 脚本打印的那样；自检：说出 `U` 与 `U_004` 各写在哪一行、来源是哪个实验。

### 12. 把教学示例当项目数据

- **错误理解**：把笔记里的算术例子（如 docstring 示例坐标 `(1043.8, 559.3)`、第 5.6 节 `u_raw = (2, 0)` 的例子）当作项目里真实存在的数值引用。
- **正确理解**：L09 笔记把材料分成六类（真实源码 / 真实项目常数 / 真实数据 / 数学公式 / 教学示例 / 概念伪代码，第 10 节）；教学示例与概念伪代码**不能**当项目事实。项目数字一律以 `results\` 下真实产物文件里的行为准，引用时要能给出行号或行内容。
- **为什么容易错**：笔记里示例与真实数据混排，格式上很接近，复习时容易记串。
- **如何避免与自检**：引用任何数字前问"它来自 `results\` 的哪一行，还是来自课堂示例"；自检：说出第 8 节 frame 0 的两条真实行内容。

### 13. 用两个标定点的 s 之差验证方向时忘记归一化

- **错误理解**：直接算 `s(P2) - s(P1)` 去和 `L_pixel` 比较，发现差 2e-4 左右就以为常量有问题。
- **正确理解**：跳过归一化会得到 M5 的 `608.634444 px`（而不是 `608.634653 px`），差 `2.09e-4 px`；把 `project_point()` 的再次归一化算进去，两者才会精确一致。这也是"再次归一化确实生效"的直接证据之一。
- **为什么容易错**：复算时只调用点积公式、忘了函数内部还会除一次模。
- **如何避免与自检**：复算脚本里显式写出 `/ |u|`；自检：分别算含归一化与不含归一化的结果，看差是不是约 2e-4 px 量级。

### 14. 跳过 compute_scale() 的检查项自己"简化"

- **如何避免与自检**：保留并复用库函数的检查，不自己重写；自检：说出三个报错分支各自的行号与异常类型。

## L10 从一维位置到位移：s0、ds_px 与 ds_mm

### 1. 把 s_px 当位移用

- **错误理解**：看到 `s_px` 随时间变化，就直接把它当"位移曲线"解释，甚至直接读它的差值当幅值。
- **正确理解**：`s_px` 是沿尺方向的一维**位置坐标**（零点由图像原点与方向 `u` 共同决定）；位移是相对基线 `s0` 的差：`ds_px = s_px - s0`（`src\displacement.py` 第 368 行 / `src\dynamic_displacement.py` 第 378 行），`ds_mm = ds_px / PX_PER_MM`（第 369 / 379 行）。
- **为什么容易错**：`s_px` 与 `ds_px` 名字只差一个字母，数值也都在同一量级；而"位置"与"位移"在口语里常被混用。
- **如何避免与自检**：每引用一个一维量，先说清它的基线是什么；自检：写出 `s_px` / `ds_px` / `s0` 三者的关系式与各自行号。

### 2. 以为第 0 帧的 ds_px 一定是 0

- **错误理解**：拿"第 0 帧 `ds_px` 应该是 0"当检查项，发现不是 0 就以为数据错了。
- **正确理解**：`s0` 是时间窗口内 valid=True 帧的 `s_px` **平均值**（第 322～323 行 / 第 361～362 行），不是 frame 0 的取值；只有 frame 0 恰好等于均值时它的 `ds_px` 才为 0。真实数据：三份 ds CSV 的 frame 0 的 `ds_px` = +4.335 / +0.164 / −3.215（STATIC-002 / STATIC-003 / EXP-004）。
- **为什么容易错**：很多仪器数据默认"从 0 开始"，容易把基线想成第一帧。
- **如何避免与自检**：正确检查是"`ds_px = s_px - s0`"（容差 0.002 px），不是"第 0 帧等于 0"；自检：说出三份数据 frame 0 的 `ds_px` 与符号。

### 3. 用首帧代替 s0 重算数据

- **错误理解**：觉得"反正 `s0` 是开头的一段，用第一帧更简单"，就自己用 frame 0 的 `s_px` 当基线。
- **正确理解**：源码第 294 行把"用首帧代替均值"列为**正式禁止**；模块里的 `s0` 是窗口内所有有效帧的平均，均值抗单帧噪声，也不依赖某一帧恰好正常。
- **为什么容易错**：用首帧在别的工作流里很常见，看起来"更直接"。
- **如何避免与自检**：改基线 = 改数据定义，必须回到"拍板参数 + 源码规则"；自检：用自己的话复述第 294 行的禁止清单（10 cm 代替、首帧代替、扩大窗口、插值、平滑、预测、分位数调整）。

### 4. 把标尺 10 cm 位置当基线

- **错误理解**：认为"位移应该从 10 cm 刻度算起"，于是拿标定点 P1 的像素位置去当 `s0`。
- **正确理解**：10 cm 是**标定点 P1 的现实位置**（`src\displacement.py` 第 44 行 / `src\dynamic_displacement.py` 第 60 行），它在画面里的投影值由标定流程确定；`s0` 是每段视频自己开头窗口内有效帧 `s_px` 的平均值。源码第 323 行明文"正式禁止：用 10 cm 代替 s0"。只读复算：M4 `s(P1) ≈ 1032.823 px`、M5 `s(P1) ≈ 812.334 px`，都不是对应视频的 `s0`（1076.063871 / 1077.364097 / 855.202603 px）。
- **为什么容易错**：标定和位移是相邻两节课的内容，"刻度 = 起点"的直觉很强。
- **如何避免与自检**：先问"这个数字回答的是标定问题还是数据问题"；自检：说出 P1 的含义（现实刻度位置）与 `s0` 的含义（数据窗口平均）。

### 5. 把 detected 当 valid（只看"检测到"就用数据）

- **错误理解**：看到 detected=True 就认为这一帧可以用，统计时只看 detection_rate。
- **正确理解**：detected 是第一道筛选（M3），valid 是第二道筛选（本模块实验专属 gate，判据 `is_valid_frame()`：detected + area 范围 + y 范围）。真实数据：STATIC-002 有 911 帧、STATIC-003 有 792 帧是 detected=True 但 valid=False（例：STATIC-002 frame 52，area 12439.0、y 35.44 被 y 门限拒绝）。
- **为什么容易错**：track CSV 里只有 detected，"检测成功 = 数据可用"的直觉很强；valid 是 ds CSV 才出现的列。
- **如何避免与自检**：统计可用数据量一律用 `valid_rate`（第 420 / 466 行），并核对 `detected_invalid_count`（第 423 / 469 行）；自检：说出 M4 与 M5 的 area / y 门限。

### 6. 把无效帧从 CSV 里删掉或填 0

- **错误理解**：觉得空字段"不好看"，把 valid=False 的行删掉，或者把位移字段填 0 / -1 / nan / 上一帧值。
- **正确理解**：规则是"不删除任何行、位移字段一律留空"（`src\displacement.py` 第 21～22 行 / `src\dynamic_displacement.py` 第 27 行）；`build_ds_row()` 把 None 写成空字符串（第 389～392 / 399～401 行），第 384 行注释"绝不写 0 / -1 / nan"。真实数据：三份 ds CSV 行数与 track CSV 完全一致（1961 / 1984 / 1766），无效行位移字段非空 0 例。
- **为什么容易错**：填数字比留空"顺手"；很多统计工具也更喜欢整齐的数字表。
- **如何避免与自检**：把"空"当作有意义的信息（没测到 / 不能用）；自检：用文件核对"无效行三列全空、有效行三列全有值"。

### 7. 以为 valid=False 的行被跳过或没有行号

- **错误理解**：认为"无效帧被删掉了"，于是按"第 N 行就是第 N 帧"的对齐方式去读 ds CSV 时对不上。
- **正确理解**：无效帧仍在文件里（行数与 track CSV 相同），只是 `s_px` / `ds_px` / `ds_mm` 为空、`valid=False`；正确对齐方式是**按 frame 列**，不是按"第几行"。
- **为什么容易错**：多数数据表默认"每行都有值"，空行很容易被当成不存在。
- **如何避免与自检**：先看 `frame` 列是否连续（本项目 0～1960 / 0～1983 / 0～1765）；自检：抽一行 valid=False 的行，说出它的 frame 与三个空字段。

### 8. 混用 M4 与 M5 的 valid gate

- **错误理解**：觉得"反正都是同一套流程"，把 M4 的 area / y 门限套到 M5，或反过来。
- **正确理解**：两组门限是为各自拍摄几何定制的（M4 注释第 57 行"本次 EXP-003 拍摄几何专属参数，不是通用视觉规则"；M5 第 68 行"与 M4 gate 完全不同，不得混用"）。真实数据后果：EXP-004 的 y 全部落在 208.63～220.61，用 M4 的 y 门限（400～540）会被**全部拒绝**；两份 STATIC 的 y 上限 470 / 464，也基本落在 M5 的 200～250 之外。混用不会报错，只会让 `valid` 全错、`s0` 失效或不写 ds CSV。

- **如何避免与自检**：写结论前先报出"本次用的 gate 与来源"；自检：说出两组 area / y 门限与所在行号。

### 9. 混用 M4 与 M5 的尺度常量

- **错误理解**：把 `PX_PER_MM = 5.756961` 用到 EXP-004 上（或反过来用 `PX_PER_MM_004 = 6.086399` 算 STATIC 的 `ds_mm`）。
- **正确理解**：两次拍摄的尺度相差约 5.72%（`6.086399 / 5.756961`）；`src\dynamic_displacement.py` 第 20～23 行明确"不得 import src.displacement"，就是为了从结构上防止这种混用；两套自检都只证明"常量与自己的标定点自洽"，**不证明常量属于这段视频**。
- **为什么容易错**：两个数字长得很像，且都能通过各自的常量自检。
- **如何避免与自检**：把常量与"视频文件名 + 来源帧"绑在一起记；自检：说出 M4 / M5 的 `PX_PER_MM` 与各自绑定视频。

### 10. 混用两套 s0 参数（或"放宽门槛"）

- **错误理解**：把 M5 的 2.0 s / 60 帧用到 STATIC 上，或者数据不达标时"把窗口拉长一点、门槛降一点"。
- **正确理解**：M4 = 0.5 s / 10 帧（第 66～68 行）、M5 = 2.0 s / 60 帧（第 78～80 行）都是拍板值；不达标时的处理是"不生成 ds CSV；不扩大窗口、不修改阈值、不做插值"（第 517 行）。真实数据：窗口内总帧 / 有效帧 = 31/31、31/31、121/121，都高于门槛。

- **如何避免与自检**：把"改规则"与"修数据"分开：结果缺失时先报告，再走决策流程；自检：说出两组窗口参数与不达标处理的三条"不做"。

### 11. 用文件里已舍入的 ds_px 反算 ds_mm，看到 ±0.0001 就以为数据错了

- **错误理解**：拿 CSV 里的 `ds_px`（3 位小数）去除以 `PX_PER_MM`，发现与 `ds_mm`（4 位小数）差 0.0001，就断定公式或数据有问题。
- **正确理解**：`ds_mm` 是用未舍入的 `ds_px` 算出再舍入的——"双重舍入"。真实复核：两种口径的最大偏差分别为 ≤ 0.000134074 mm（用写入的 `ds_px`）与 ≤ 0.000150884 mm（用 `s_px - s0` 反推），正好是 ~1e-4 mm 量级；自检容差是 0.0005 mm（`src\displacement.py` 第 800 行 / `src\dynamic_displacement.py` 第 1143 行）。
- **为什么容易错**：两列数字对不上时，第一反应是"有 bug"。
- **如何避免与自检**：先算舍入上界（`s_px`/`ds_px` 各 3 位小数 + `ds_mm` 4 位小数），再看差是否落在容差内。

### 12. 以为 s0 是"这段位移的平均"

- **错误理解**：把 `s0` 理解成"前 0.5 s 内 `ds` 的平均值"，或者在 s0 计算里先减均值再平均。
- **正确理解**：`s0` 平均的是 **`s_px`（位置）**：先按 `time_s <= window_s` 且 `valid=True` 筛出帧（第 304～305 行），再对这些帧的 `s_px` 求平均（第 322～323 行）；`ds` 是 `s0` 确定之后才算的（第 339～340 行）。
- **为什么容易错**：从结果看，`ds` 在窗口内确实接近 0，容易反推成"s0 来自 ds"。
- **如何避免与自检**：牢记计算顺序"valid → s_px → s0 → ds_px → ds_mm"；自检：说出窗口筛选用的条件（时间 + valid）与平均的对象（s_px）。

### 13. 把 s0 的容差或精度记错

- **错误理解**：以为 s0 的复算容差和 ds_px 一样、或者以为 `s0` 也像 CSV 字段一样被舍入到 3 位小数。
- **正确理解**：`s0` 复算容差是 **0.002 px**（`src\displacement.py` 第 750 行 / `src\dynamic_displacement.py` 第 1120 行），比 `ds_px` 的容差大——因为复算要用文件里已舍入的 `s_px`；`s0` 本身是完整精度的浮点数（例如 1076.063871…），只有写进 CSV 的 `s_px` / `ds_px` / `ds_mm` 才按位数舍入。
- **为什么容易错**：打印出来的 `s0` 只显示 3 位小数（`src\displacement.py` 第 499～500 行、`src\dynamic_displacement.py` 第 761 行均为 `"%.3f px"`），容易被当成文件的数值精度。
- **如何避免与自检**：弄清"内存里的完整精度"与"文本里的舍入值"是两回事；自检：说出三个容差（0.002 px / 0.002 px / 0.0005 mm）各自核对什么。

### 14. 把 detection_rate 与 valid_rate 混用

- **错误理解**：报告里写"检出率 100%，数据质量很好"，用 detection_rate 代替 valid_rate 下结论。
- **正确理解**：`detected_rate` 与 `valid_rate` 是两个不同口径（`src\displacement.py` 第 447～449 行；`src\dynamic_displacement.py` 第 464～466 行）。真实数据：STATIC-002 detection_rate = 100% 但 valid_rate ≈ 53.54%；STATIC-003 为 100% 与 ≈ 60.08%。物理结论只能建立在 valid 数据上。
- **为什么容易错**：两个比率都叫"成功率"，而且 100% 的数字很显眼。
- **如何避免与自检**：写结论前先写清"这个百分比的分母与过滤条件"；自检：同时报出 detected_rate、valid_rate 与 detected_invalid_count。

### 15. 在 L10 就急着学峰值 / 谷值 / 周期 / 频率 / FFT

- **错误理解**：在 L10 里追问"峰值怎么找""转向点算法怎么定""频率是多少""为什么不用 FFT"。
- **正确理解**：本课的目标是"valid gate → `s0` → `ds_px` / `ds_mm` → 真实数据复核"这条链；峰值 / 谷值、转向点完整算法（`detect_turning_points()`，`src\dynamic_displacement.py` 第 487～623 行）、周期、频率、FFT、简谐振动理论都属于后续课程，本课只登记名称与位置。
- **为什么容易错**：`ds` 数据一画出来就像振动曲线，很自然会想往下算。
- **如何避免与自检**：先确认"这节课要能回答什么"；自检：说出 L10 明确不展开的三类内容与它们的源码位置。

### 16. 把教学示例当真实数据

- **错误理解**：把笔记里的推演（如"混用 gate 会把 EXP-004 全部拒绝"）或算术例子当成从数据里实测出来的结果引用。
- **正确理解**：笔记里的推演与算术例子是教学材料；项目数字必须以 `results\` 下真实产物文件里的行为准，引用时给出行内容（例如 frame 0 行、frame 52 例证）。"混用 gate"本身没有实测记录，是把真实 y 范围与真实门限放在一起的算术推演。

## L11 位移数据、正负号与运动方向

### 1. 把 ds 的正负当成好坏（负号 = 失败 / 差数据）

- **错误理解**：看到 `ds_mm` 是负数，就认为"这次测量失败了"或"数据质量差"。
- **正确理解**：`ds` 的正负只是位置方向记号——负号表示这一帧落在参考位置 `s0` 的负侧（`src\displacement.py` 第 368 行 `ds_px = s_px - s0`）。真实数据里负号帧（STATIC-002 有 34 个、STATIC-003 有 18 个、EXP-004 有 161 个）都是正常测量结果。
- **为什么容易错**：日常语言里"负"常带贬义；很多仪器数据默认从 0 开始、不允许负值。
- **如何避免与自检**：先问"这个负号是在说哪一侧，还是在说质量？"；自检：说出负号帧分别出现在哪段 frame（1～51 / 2～34 / 0～237）。

### 2. 把 ds 的大小当成快慢（|ds| 当速度）

- **错误理解**：看到某个帧 `|ds_mm|` 很大就说"这一帧运动很快"，把它当速度读数。
- **正确理解**：`|ds|` 是"离参考位置多远"（沿尺方向的投影距离）；快慢要用单位时间的变化量 Δds / Δt，本项目没有速度字段。0 → 60 mm 用 1 秒还是 10 秒，`|ds|` 完全一样。
- **为什么容易错**：位移曲线与"快慢"在口语里经常混用；曲线陡峭处数值变化大，很容易被说成"速度快"。
- **如何避免与自检**：把"位置量 / 变化量 / 变化率"三层次分开；自检：说出 `|ds_mm|` 的最大值与它的单位（60.8426 / 60.1932 / 66.1663 mm）。

### 3. 用 ds 的符号判断运动方向

- **错误理解**：看到 `ds > 0` 就说"正在向正方向运动"，看到 `ds < 0` 就说"正在向负方向运动"。
- **正确理解**：运动方向由 **Δds** 决定：Δds > 0 向正方向运动、Δds < 0 向负方向运动（与 ds 本身的符号无关）。真实例子：M5 f237（`ds_mm = −0.0046`，负侧）→ f313（`+27.1660`）是**向正方向**运动；f963（`+39.7894`，正侧）→ f1015（`+26.1587`）是**向负方向**运动。
- **为什么容易错**：ds 和 Δds 只差一个"变化量"的念头；两者的符号又经常碰巧一致（因为大部分时间在远离参考位置）。
- **如何避免与自检**：判断方向前先写出 `Δds = ds[i+1] - ds[i]` 再说符号；自检：复述两条真实例子的起点 / 终点 `ds_mm` 与 Δds。

### 4. 以为 ds > 0 就是"向前"

- **错误理解**：把"正方向"当成物理上的"向前 / 向上"，直接写成"目标在向前运动"。
- **正确理解**："正方向"来自人为约定：M4 是 10 cm → 16 cm（`src\displacement.py` 第 46 行约定、第 55 行 `U`），M5 是 10 cm → 20 cm（`src\dynamic_displacement.py` 第 66 行 `U_004`）。把约定反过来，所有 `s_px` / `ds` 整体反号，且不会报错。
- **为什么容易错**：画面里目标确实在移动，"前 / 后"是最自然的说法。
- **如何避免与自检**：描述方向时写成"沿 P1 → P2 方向 / 逆着 P1 → P2 方向"，并报出约定所在行号；自检：说出 M4 / M5 各自的约定与 `U` / `U_004`。

### 5. 把 s0 当成"带方向的量"

- **错误理解**：认为 `s0` 里带着方向信息，或者把 `s0` 与 10 cm 刻度、首帧混为一谈。
- **正确理解**：`s0` 是参考位置（L10：窗口内 valid 帧 `s_px` 的平均值，`compute_s0()` 第 288～325 行）；它和 `s_px` 在同一条尺上，本身不带方向。正负来自 `s_px` 与 `s0` 的相对关系。源码第 294 行明文禁止"用 10 cm 代替 s0、用首帧代替均值"。
- **为什么容易错**：`s0` 出现在位移公式里，容易把它当成"起点 + 方向"的合成。
- **如何避免与自检**：把 `s0` 读成"参考位置读数"；自检：说出 `s0` 的来源（窗口均值）、不是首帧、不是 10 cm 位置。

### 6. 跨空洞计算 Δds（把两个可测时刻当成连续运动）

- **错误理解**：M4 静态数据平台之间是长段 `valid=False`，仍然拿空洞两侧的值直接相减，当成"这一段在向某方向运动"。
- **正确理解**：`ds` 只在 `valid=True` 的行存在（第 338～340 行）；Δds 只在**相邻且都有效**的两帧之间才有运动方向意义。M4 的空洞是合法的"留空"，不是待补齐的数据（第 360～363 行；第 355 行"绝不写 0 / -1 / nan"）。
- **为什么容易错**：CSV 里 frame 是连续的，空字段容易被跳过；跳过之后两侧的值看起来"相邻"。
- **如何避免与自检**：算 Δds 前先检查两端 `ds` 是否非空、frame 是否相差 1；自检：说出 STATIC-002 / STATIC-003 的最长连续 invalid（180 / 147 帧）。

### 7. 把 Δds 当速度

- **错误理解**：把相邻两帧的 Δds 直接称为"速度"，甚至报出单位 mm（应为 mm/s 才算速度）。
- **正确理解**：Δds 是位移的变化量（px 或 mm）；速度 = Δds / Δt（30 fps 时 Δt ≈ 0.033333 s）。本项目没有速度字段，本课也不算速度。
- **为什么容易错**：运动数据里"变化"与"速度"的说法很接近。
- **如何避免与自检**：写结论时先写清"这是变化量还是变化率"；自检：说出 Δds/Δt 才叫速度、Δt 在本项目是多少。

### 8. 以为 Δds 是源码里的字段 / 变量

- **错误理解**：在 `src\` 里找 `Δds` / `delta_ds`，或者以为 ds CSV 里有一列 Δds。
- **正确理解**：源码里没有 `Δds` 字段；对应的文字规则是"正向 = ds 增大 / 负向 = ds 减小"（`src\dynamic_displacement.py` 第 83～84、480 行）。Δds 是本课引入的概念量。此外，`detect_turning_points()` 实际用原始 `x_px` 统计方向（第 496、524～526 行），因为 `U_004` 的 `ux > 0`（第 510 行）。
- **为什么容易错**：笔记里 Δds 出现频率很高，容易误以为它是项目字段。
- **如何避免与自检**：区分"概念量"与"字段 / 变量"；自检：说出 ds CSV 的 8 列列名（不含 Δds）。

### 9. 把"正 / 负 / 零"计数当成运动方向统计

- **错误理解**：看到 STATIC-002 的 1016/34/0，就以为"1016 帧在向正方向运动、34 帧在向负方向运动"。
- **正确理解**：正/负/零计数统计的是**符号侧**（`ds_mm` 非空行，即 valid 行）；运动方向统计要看 Δds（或源码里 `detect_turning_points()` 使用的原始 x_px 序列，属于 L12 内容）。二者口径不同。

## L12 转向点检测与运动段切分

### 1. 看到一帧变大/变小就认定转向

- **错误理解**：认为"这一帧的 x 比上一帧小，所以刚才那帧就是峰值、转向了"，直接用相邻两帧的比较结果当转向判据。
- **正确理解**：转向必须用状态机 + 20 px 反向行程阈值确认。源码第 496–497 行只用原始 `x_px` 序列，并以"从当前极值反向走满至少 20 px"作为确认条件（第 557、564 行）；第 505 行的冻结说明给出噪声量级：静止段相邻帧 |dx| 中位数约 0.13 px、静止段最大约 1.25 px，远达不到 20 px。
- **为什么容易错**：人眼看曲线时"拐弯"很直观，一帧的上下起伏也恰好和"转向"长得像；而噪声在单帧尺度上就会反复制造这种假象。
- **如何避免与自检**：看到任何一个"转向点"先问三件事——它是从哪个极值反向、反向走了多少 px、有没有达到 20 px？三个问题答不全，就不能称它为转向点。

### 2. 把 20 px 当成"相邻两帧差值"阈值

- **错误理解**：以为 `MIN_TURN_TRAVEL_PX = 20.0` 是"相邻两帧的 |Δx| 要小于/大于 20"。
- **正确理解**：它是**从当前极值起的反向累计行程**阈值。第 557 行比较 `x_extreme - x_i >= 20`，第 564 行比较 `x_i - x_extreme >= 20`；不是相邻帧之差。第 85–86 行注释原文："只有当原始 x 从当前极值反向走了至少 20 px，该极值才被确认为转向点"。
- **为什么容易错**：Δds / 相邻帧差值是 L11 的核心概念，惯性会把 20 px 也理解成"帧间差值"；而"累计行程"这个词容易被略读。
- **如何避免与自检**：把阈值读成一句完整的话："从极值反向，累计走满 20 px"。自检：用 f491→f505 的真实例子算一遍——1057.86 − 1036.15 = 21.71 px，跨了 14 帧，而不是"某一对相邻帧差了 20 px"。

### 3. 混淆两种 20 px：转向确认 vs below_min_travel

- **错误理解**：认为 `below_min_travel` 就是"转向是否成立的判据"，或者反过来以为转向确认比较的是"整段行程"。
- **正确理解**：两者都用 20 px，但比较对象不同。转向确认（第 557、564 行）比较的是**从当前极值反向到当前帧的行程**，发生在状态机运行中；`below_min_travel`（第 617 行）比较的是**整个运动段两端之间的行程**（第 600 行 `travel_px = abs(tail["x_px"] - head["x_px"])`），发生在状态机结束、切分运动段之后。
- **为什么容易错**：两处都写着 `MIN_TURN_TRAVEL_PX`，字面上完全一样；不追踪"被比较的两个量"就容易合并成一个概念。
- **如何避免与自检**：每次看到 20 px 都先问"谁减谁、发生在哪个阶段"。自检：说出 EXP-004 七段的 travel_px，并确认它们与"f491→f505 = 21.71 px"这类反向行程不是同一类数字。

### 4. 把"确认帧"当成转向点

- **错误理解**：看到程序在 f505 才"发现"peak f491，就把 f505 当成转向点；或者看到 `turn_indexes.append((extreme_index, "peak"))` 时以为 `i` 被写入。
- **正确理解**：写入 `turn_indexes` 的是 `extreme_index`（第 558、565 行），也就是**极值帧**；确认帧 `i` 只用来触发确认（第 557、564 行），确认后把 `extreme_index` 重置为 `i`（第 560、567 行）。真实案例：peak f491 在 f505 确认、valley f602 在 f732 确认、peak f838 在 f971 确认。
- **为什么容易错**：程序输出里"确认"这个词很醒目，且确认帧确实出现在代码的 `if` 条件里；不仔细区分"被写入的 index"与"触发条件的 i"就会混淆。
- **如何避免与自检**：看 turn 的 frame 时回到第 583 行 `describe(series[index])`——`index` 来自 `turn_indexes` 的第一项，而第一项就是 `extreme_index`。自检：对 f491 说清"转向点 f491、确认帧 f505、反向行程 21.71 px"三件事。

### 5. 以为极值平台是数据错误 / 急着把平台抹平

- **错误理解**：看到极值附近连续几帧数值几乎不变，就认为数据坏了、需要平滑或删除"重复点"。
- **正确理解**：平台是真实采样结果，不是错误。状态机允许极值在 `x_i > x_extreme`（正向）或 `x_i < x_extreme`（负向）时继续更新（第 555–556、562–563 行）；反向没到 20 px 之前不确认转向（第 557、564 行）。平台的存在正是需要"状态机 + 阈值"而不是"一帧判据"的原因之一。
- **为什么容易错**：平台看起来"没有信息"，人们本能地想把它修成一条光滑曲线；而平滑会改变数据本身（模块第 28 行明确禁止）。
- **如何避免与自检**：先问"这个平台是测量噪声、真实静止，还是采样在当前分辨率下看不出变化？"三种情况都必须保留原始数据；自检：能说出为什么"平台 + 20 px 反向确认"不会把平台中间某帧误认成转向点。

### 6. 删除 `valid=False` 的行，或把"统计 invalid"当成"删除数据"

- **错误理解**：认为第 527 行统计 `analysis_invalid_rows` 是在"剔除无效帧"；或者在整理数据时把 `valid=False` 的行删掉。
- **正确理解**：第 527 行只做 `sum(...)` 计数；第 514 行 docstring 原文"其中 valid=False 的行数（只统计，不删除）"。`series` 的筛选条件是 `detected` 与 `x_px`，不含 `valid`——所以 `valid=False` 的行只要满足前两个条件，就仍然留在分析序列里参与状态机；模块第 27 行也规定"不删除任何 track CSV 行"。
- **为什么容易错**："统计无效数据"和"清理无效数据"在直觉上常被绑定在一起；再加上很多数据处理流程默认会剔除无效行。
- **如何避免与自检**：把"统计"与"删除"当成两个动作分别确认。自检：翻开第 524–527 行，指出哪一行在筛选、哪一行只在计数；EXP-004 恰好 `analysis_invalid_rows = 0`，但规则本身必须按源码理解。

### 7. 用 ds / s_px / 平滑曲线做转向检测

- **错误理解**：觉得 `ds_mm` 曲线更"物理"，或者 `s_px` 更"干净"，于是拿它们去做转向检测；或者先画一条平滑曲线再找极值。
- **正确理解**：第 496 行 docstring 与第 524–526 行明确只使用**原始 `x_px`**；第 30 行"转向点只使用原始 x_px 数据"。`ds` 与 `x` 方向一致（`U_004` 的 `ux > 0`，第 509–510 行），但转向检测的口径就是原始 x，不换成别的字段。
- **为什么容易错**：L10 / L11 的主角是 `ds`，惯性会让人以为"分析都应该用 ds"；平滑曲线看起来又更符合"找极值"的数学直觉。
- **如何避免与自检**：记住本模块的输入契约是 `x_px` 序列；引用转向结果时同时报 `x_px` 与 `ds_mm`，但检测依据只归 `x_px`。自检：说出第 524–526 行的筛选条件（`detected` + `x_px`）。

### 8. 为了"更漂亮"做平滑 / 滤波 / 插值 / 补帧 / 预测

- **错误理解**：认为"数据有噪声，先平滑一下再检测"是标准做法，或者把缺帧补齐后结果会更完整。
- **正确理解**：模块第 28 行明确"不做平滑 / 滤波 / 插值 / 补帧 / 补零 / 预测 / FFT / 频率 / 周期 / 振幅分析"；第 496–497 行也明确不平滑、不滤波、不插值、不补帧、不预测。噪声由"从极值反向 20 px 才确认"的规则处理，而不是靠改数据。
- **为什么容易错**：这些操作在通用信号处理里很常见，默认这是"提高质量"；但本项目把"保留测量证据"放在第一位。
- **如何避免与自检**：下结论前问"我有没有改变任何一行原始数据？"自检：说出模块第 27、28 行的两条禁令（不删行、位移字段留空；不做平滑 / 滤波 / 插值 / 补帧 / 补零 / 预测）。

### 9. 把起点 / 终点当转向点，或把段数算成转向点数

- **错误理解**：看到 `boundary_indexes` 里有 f0 与 f1765，就认为转向点有 8 个；或者把段数算成 6。

- **为什么容易错**：`boundary_indexes` 把边界和转向点放在同一个列表里（第 595 行），不区分来源就会多算。

### 10. 把 `direction_before` / `direction_after` 当成"又一次测量"

- **错误理解**：以为这两个字段是从 Δds 或前后两帧重新测量出来的，甚至怀疑它们和 `kind` 不一致。
- **正确理解**：第 585–590 行直接由 `kind` 推导：peak → 正向 → 负向；否则（valley）→ 负向 → 正向。它们不是新的测量量，也不引入新的数据来源；`DIRECTION_POSITIVE = "正向"`、`DIRECTION_NEGATIVE = "负向"` 在第 111–113 行定义。
- **为什么容易错**：字段名看起来像"测得的方向"，而且七个字段一起出现时不容易分辨哪些来自数据行、哪些是推导的。
- **如何避免与自检**：给七字段分类——`frame` / `time_s` / `x_px` / `ds_mm` 来自数据行（`describe()` 第 572–575 行）；`kind` 来自状态机；`direction_before` / `direction_after` 由 `kind` 推导（第 585–590 行）。

### 11. 把 peak / valley 与正向 / 负向说反

- **错误理解**：把 peak 说成"负向 → 正向"或把 valley 说成"正向 → 负向"。
- **正确理解**：peak 在 `direction == +1` 分支确认（第 558 行），确认后方向翻到 −1（第 559 行），所以是**正向 → 负向**；valley 在 `direction == -1` 分支确认（第 565 行），确认后方向翻到 +1（第 566 行），所以是**负向 → 正向**。因为 `ux > 0`（第 509–510 行），peak 也对应 `ds` 的局部极大、valley 也对应 `ds` 的局部极小。
- **为什么容易错**：peak / valley 是"形状词"，正向 / 负向是"方向词"，两套词汇交叉使用时容易凭直觉搭配。
- **如何避免与自检**：记住一条链——peak 是"往正向走到头"，所以之前正向、之后负向；valley 镜像。自检：说出 f491 是 peak 且方向变化为正向 → 负向。

### 12. 以为转向检测用 `ds` 的正负号来判断

- **错误理解**：因为 L11 学的是 Δds 判方向，就以为 `detect_turning_points()` 也在算 Δds 的符号。
- **正确理解**：状态机直接用原始 `x_px`（第 496、547–548 行）；只是由于 `U_004` 的 `ux > 0`，才有"正向 = x 增大 = ds 增大、负向 = x 减小 = ds 减小"（第 509–510 行）。源码里没有 `Δds` 变量；转向确认用的是 x 的行程（第 557、564 行）。
- **为什么容易错**：L11 的 Δds 是上一课的核心，容易直接迁移到 L12；而两套说法在结果上又"恰好一致"（因为 ux > 0），不深究就发现不了区别。
- **如何避免与自检**：引用转向算法时只提 `x_px` 与 `extreme_index`；引用方向语义时才提 ds。自检：说出第 509–510 行为什么允许用 x 的语言讲 ds 的方向。

### 13. 把 EXP-004 的专属口径当成通用规则

## L19 采样、频率格点与频谱泄漏——真实视频里的 FFT 为什么不会完美

### 1. 把采样率 fs 与样本数 N 混淆

- **错误理解**：把"30 fps"与"160 个点"当成同一类量，或说成"采样率是 160"、"记录长度是 30"。
- **正确理解**：fs 是**每秒取多少个点**（M6 为 30 Hz），N 是**一共取了多少个点**（M6 为 160）；两者通过记录长度联系：T_record = N / fs = 160 / 30 = 5.3333 s，而 df = fs / N。单位也不同（fs 为 Hz，N 为无量纲计数）。出处：`src\external_oscillation_tracker.py` 第 61–63 行、`README.md` 第 46 行、报告第 60、181 行。
- **为什么容易错**：两个数字都与"采样"有关，写在一起时容易只记数字、不记单位。
- **如何避免与自检**：引用前先写单位；自检：说出 30 / 160 = 0.1875 Hz、160 / 30 = 5.3333 s 分别对应哪个公式。

### 2. 把频率格点当成可以做任意取值的连续频率

- **错误理解**：以为 FFT 能报出任意频率（例如 1.843003 Hz），或把"频谱曲线"当成一条处处有定义、可自由读数的连续曲线。
- **正确理解**：FFT 的输出只落在固定格点 f_k = k · df 上（M6 为 0、0.1875、0.375 … 15 Hz）；主峰只能取**最近格点**的读数。1.843003 Hz 位于格点之间（1.843003 / 0.1875 ≈ 9.83），最近的格点是 k = 10（1.875 Hz）。
- **为什么容易错**：画出频谱图后线条在视觉上是连续的；"分辨率"又容易被理解成"精度"。
- **如何避免与自检**：把"格点位置"与"真实频率"分开；自检：说出 df、k = 10 与 0.031997 Hz 的关系。

### 3. 忽略 df = fs / N（把频率分辨率当成算法精度）

- **错误理解**：不知道 df 从哪来，或说"FFT 算法的精度是 0.1875 Hz"。
- **正确理解**：df = fs / N = 1 / T_record，由**采样率与记录长度**决定，不是算法本身的精度极限；记录越长、格点越密。M6 核对 df = 30 / 160 = 0.1875 Hz。要分辨相差 Δf 的两个成分，至少需要约 1 / Δf 的观测时间。
- **为什么容易错**：df 常被口语化地叫"分辨率"，听起来像设备精度。
- **如何避免与自检**：引用 df 时同时写算式；自检：说出 1 / 5.3333 ≈ 0.1875 Hz 与 df = fs / N 等价。

### 4. 把 zero padding 当成真正提高原始频率分辨率

- **错误理解**：以为"补零到更多点"就能把两个本来分不开的频率分开，或者把补零后的密集格点当成新的真实信息。
- **正确理解**：zero padding 只让**输出格点变密、曲线更光滑**，**不增加真实观测时间**（物理观测仍是 5.3333 s）、**不增加原始信息**；真实分辨能力仍由 T_record 决定。M6.3 封板做法是"不补零"（报告第 175 行），当前也没有 `np.pad` 实现。
- **为什么容易错**："补零后点变多、图变细"在视觉上很像分辨率提升。
- **如何避免与自检**：区分"格点加密"与"信息增加"；自检：回答"补零能改变 T_record 吗"。

### 5. 忽略频谱泄漏（把格点化读数当成频率漂移）

- **错误理解**：看到 FFT 主峰是 1.875 Hz、时域是 1.843003 Hz，就说"FFT 测到了另一个频率"或"频率发生了漂移"。
- **正确理解**：泄漏来自"有限记录 + 非整数周期截断（记录内约 9.83 个周期）→ 周期延拓边界不连续 → 能量扩散到邻近格点"；它是**系统性效应，不是数据错误**。峰值落在最近格点 1.875 Hz 是格点化读数，不代表真实频率变了。
- **为什么容易错**：泄漏的四个要素不直观，容易只记住"主峰"这个数字。
- **如何避免与自检**：按四要素复述泄漏；自检：说出"有限记录 / 非整数周期 / 边界跳变 / 能量扩散"。

### 6. 窗函数使用场景理解错误（以为加窗一定更准确）

- **错误理解**：以为只要加 Hann / Hamming / Blackman 窗，结果就一定比"不加窗"更准。
- **正确理解**：加窗压低旁瓣、减弱泄漏，代价是**主瓣变宽、分辨能力下降**——是"旁瓣 vs 主瓣"的权衡，不是免费提升；不同窗有不同折中。M6.3 封板做法是"不加窗"（报告第 175 行），当前也没有任何窗函数实现。
- **为什么容易错**："加窗"听起来像一种改进手段，容易默认它总是更好。
- **如何避免与自检**：回答"加窗改善了什么、牺牲了什么"；自检：说出矩形窗与 Hann 窗的主瓣 / 旁瓣取舍。

### 7. 把教学示例的频率（1.900 Hz）当成项目数据

- **错误理解**：把 L19 第 9 节的两个教学频率（1.875 Hz 整周期示例、1.900 Hz 非整周期泄漏示例）当成 VisionMotion 测到的频率。
- **正确理解**：1.900 Hz 只存在于**教学示例 B**（用来演示非整周期泄漏），不是项目数据、不是项目代码，也不是运行结果；项目真实频率是时域 f_exp = 1.843003 Hz 与冻结 FFT 主峰 f_FFT = 1.875 Hz。三个数字不能混用。
- **为什么容易错**：教学示例与真实冻结值都叫"Hz"，且 1.875 Hz 同时出现在教学示例 A 与真实冻结值里。
- **如何避免与自检**：看到频率先问"是项目数据还是教学示例"；自检：给 1.843003 / 1.875 / 1.900 三个数各写一句身份说明。

### 1. 把"冻结值"当成"当前代码的运行时能力"

- **错误理解**：因为报告、PPT、源码里写着一堆周期 / 频率 / FFT 数字，就说"项目支持周期、频率、FFT 计算"。
- **正确理解**：写在 `FROZEN` 字典、报告、PPT 里的数字是**已经封板的历史分析结果**，不代表当前代码能在运行时算出它们。f_exp / f_FFT / df_fft 冻结在 `src\m63_final_visualization.py` 第 112–127 行，第 7 行明确不重算；全仓库没有可执行 FFT。
- **为什么容易错**：数字出现在源码文件里，很容易被当成"代码产物"。
- **如何避免与自检**：引用数字前先问"运行时算的、只读核对的，还是冻结的"；自检：说出三个冻结值的行号与"第 7 行不重算"。

### 2. 把"文件缺失"当成"程序崩溃 / 数据错误"

- **错误理解**：看到 `results\EXP-003-STATIC-001` 只有 `_track.csv`、没有 `_ds.csv`，就以为程序出错或数据被删。
- **正确理解**：这是 **valid gate 规则下的正确行为**——该实验开头窗口内 0 帧通过 M4 gate（首帧 y = 117.04、area = 182215.5 均超出 400～540 / 2000～15000），s0 不达标，源码第 318、781、793 行的规则是"不写 ds CSV"。它是需要记录的数据缺口，不是故障。
- **为什么容易错**：缺少同名产物在直觉上像"没跑完"。
- **如何避免与自检**：先读规则再判断"缺失"；自检：说出"窗口内有效帧数为 0 → 不写 ds CSV"这条规则。

### 3. 把"文档没写 / 文档旧"当成"数据没变"（文档漂移）

- **错误理解**：按 `CHANGELOG.md`（v0.3.0 仍写 952 帧 / 60.124797 fps）或旧 `README.md` 推断当前 M3 数据，而不看工作区里的真实 CSV。
- **正确理解**：M2 / M3 数据已于 2026-10-03 替换并重跑，当前 M3 是 **170 行 / 24 fps**、首行 `0,0.000000,618.28,160.56,75863.0,True`；README / CHANGELOG 未同步是"文档漂移"，必须以**文件本身**为准并单独记录差异。
- **为什么容易错**：CHANGELOG / README 通常被视为权威描述。
- **如何避免与自检**：拿文档口径与真实文件逐项对照；自检：说出"952 帧 / 60.1248 fps"属于旧记录、"170 帧 / 24 fps"属于当前数据。

### 4. 把"检测"当成"测量"（像素坐标不是物理位移）

- **错误理解**：把 `x_px / y_px / y0_px` 这类像素坐标直接说成"位移了多少毫米"。
- **正确理解**：检测只给出**像素位置**；只有经过标定（px/mm）、一维投影与基线 `s0` 之后才得到"位移" `ds_px / ds_mm`。M6 明确不做标定，因此 M6 **只有像素、没有毫米位移**。
- **为什么容易错**：像素位置随时间变化的曲线看起来就像"位移曲线"。
- **如何避免与自检**：引用任何位置量前先问"单位是像素还是毫米、有没有经过标定"；自检：说出 M3 与 M6 在"毫米"上的差别。

### 5. 把"周期候选"（只读分析）当成"运行时功能"

- **错误理解**：认为 M5 代码会在运行时计算周期 / 频率，或把 L13 / L14 的"半周期候选"当成程序输出。
- **正确理解**：M5 源码只输出转向点 / 运动段（`src\dynamic_displacement.py` 第 28 行明确不做周期 / 频率 / 振幅）；"周期候选"来自 L14 对转向点间隔的**只读统计**，不是运行时功能。M6 的周期 / 频率是冻结分析结果。
- **为什么容易错**：转向点是真实的运行时输出，"周期"看起来只是顺手再算一步。
- **如何避免与自检**：区分"运行时输出"与"课程只读分析"；自检：说出 `dynamic_displacement.py` 第 28 行的否定声明。

### 6. 跨数据路线搬运结论（无标定路线硬给毫米 / 周期数字互相套用）

- **错误理解**：把 M6 的 T = 0.542593 s / f = 1.843003 Hz 套到 EXP-004 上，或给没有标定的 M6 配一个 px/mm 系数去算毫米。
- **正确理解**：M2–M5 自采路线与 M6 外部公开视频路线是两条独立数据链（目标、检测、标定都不同）；M6 明确禁止标定（`src\external_oscillation_tracker.py` 第 31～34 行、第 658 行打印"标定：否"），只能停留在像素；两条链的周期 / 频率数字不能互搬。
- **为什么容易错**：两条链共享同一套 CSV 记录规范，容易以为结论也通用。
- **如何避免与自检**：引用任何周期 / 频率 / 毫米数字前，先说出它属于哪条数据链、来自哪份文件第几行。

### 7. 不区分五类材料（把概念、示例、伪代码当成源码或真实数据）

- **错误理解**：把概念解释、教学示例、概念伪代码当成"项目真实源码"或"真实数据"来引用。
- **正确理解**：五类标签 = 【项目真实源码】【真实数据】【概念解释】【教学示例】【概念伪代码】；引用项目行为必须给"文件 + 行号"，引用数字必须说清出处，教学示例（如 L19 的 1.900 Hz）必须显式标注"不是项目数据、不是项目代码"。
- **为什么容易错**：伪代码与真实流程长得很像，示例数字往往比行号更醒目。
- **如何避免与自检**：看到代码先问"仓库里能不能找到行号"；看到数字先问"来自哪个真实文件"。

### 8. 以为项目是"全自动"测量系统

- **错误理解**：以为从视频进去、参数出来全程无需人工，或把项目当成工业级计量系统。
- **正确理解**：M4 的标定点是**人工点击**（`demo\pick_calibration_points.py`），M6 的参数是**人工冻结**的；项目没有精度验收、没有计量校准、没有环境控制。它的价值在"整条链路能跑通、每一步能解释、结果能复现"（`README.md` 第 15 行），是教学 / 演示级流水线，不是工业测量系统。
- **为什么容易错**：有可视化、有报告、有 PPT，容易给人"产品化 / 全自动"的印象。
- **如何避免与自检**：逐项问"这一步的参数是自动算的、还是人工冻结 / 点击的"；自检：说出至少两处人工介入点。

## 通用自检习惯

1. **先分"测量值"和"质量指标"**：读任何数据表前，先判断每一列是在描述被测对象，还是在描述测量的可信程度，不要混用。
2. **先看表头和单位**：拿到 CSV 先读第一行表头，确认列名、单位后缀（如 _px）、数据含义，再读数值。
3. **注意坐标系约定**：图像坐标系 y 轴向下为正，与数学坐标系不同；跨学科使用坐标时先确认方向约定。
4. **区分"帧序"与"时间"**：把"第几帧"和"第几秒"当作两个不同的问题分别回答，换算关系要能当场写出。
5. **承认采样的离散性**：任何来自视频的测量都发生在离散时刻，谈论"某一时刻的值"时要能说出它来自哪一帧。
6. **先确认颜色空间与通道顺序，再谈颜色**：看到"红/蓝/绿"相关代码，先确认数据是 BGR 还是 RGB、是 BGR 还是 HSV，再判断数值含义；HSV 还要记住 OpenCV 的 H 上限是 179。
7. **先区分"像素级规则判断"和"对象级表示"**：Mask 是逐像素的是/否判断表，Contour 才把像素区域变成候选形状；两者不能混为一步，更不能把 Mask 直接当成"目标"。
8. **位置输出要能说出它来自哪个公式**：本项目的位置是质心 `(cx, cy)`，来自 `cx = m10 / m00`、`cy = m01 / m00`；它不等于外接矩形中心，`boundingRect` 只用于框选与辅助检查。
9. **区分"项目真实源码"与"教学示例"**：引用项目事实时必须能指出文件、函数与行号；教学示例（手算像素、3×3 玩具图等）只是解释工具，不是项目数据，复习时不要把两者混为一谈。
10. **先确认数据的形状与维度，再谈处理方式**：视频 = 帧序列 + 帧率；帧 = 高度 × 宽度 × 通道的图像数组。说不清"正在处理的是序列还是单张图"，就说不清该用循环还是单次调用。
11. **打开的资源要成对释放**：文件、视频读取器、视频写入器用完后要 close / release，并放在 try / finally 这类"无论如何都会经过"的路径上，保证异常与中断时也完成清理。
12. **先问"数据存在哪里、活多久"**：内存变量（如 `result`）随进程结束消失，文件（如 CSV）才会长期保留；每写一份数据，都要能说出它的存放位置、字段顺序、缺失怎么表示、以后由谁来读。
13. **区分"缺测"与"数值"**：空 cell 表示"没有测到"，不等于 0、也不等于上一帧的值（第 399、410 行）；统计或画图前先确认缺失的表示方式，并用自检确认"失败行留空"与 `detected=False` 一一对应（第 730～732、794～818 行）。
14. **先问"失败怎么表达"，再读数据**：拿到任何测量数据，先找出它的"失败 / 缺失"表示方式（空字段？标志位？）和判定标准，再开始统计；不要把缺失当成一个数字，也不要只看检出率就下结论。
15. **下结论前先划"证据边界"**：分清"源码能证明什么、真实数据能证明什么、哪些只是概念解释或教学示例"；不用"设计上支持"冒充"实测已发生"，把"没有观察到"照实写成"没有观察到"。
16. **先问"单位与换算系数从哪来"**：看到 `_px` 与 `_mm` 混排的数据，先确认 mm 列的标定来源（哪两个点、哪一个已知真实长度、哪一次拍摄），并确认系数属于这一批数据；没有有效标定，就只能停留在像素层面，不写 `_mm` 字段、不给 mm 结论。
17. **换算链要能写全**：把 `ds_mm = ds_px / PX_PER_MM`（等价 `ds_px × MM_PER_PX`）的每一步单位写清楚（px / mm / px/mm / mm/px）；看到末位差异先算舍入误差与容差（例如双重舍入带来的 ±0.0001、自检容差 0.0005 mm），再判断数据是否有问题。
18. **做投影 / 点积前先确认方向向量已归一化**：点积只有在方向向量长度为 1 时才等于"沿方向的像素距离"；同时确认公式里用的是哪一个方向常量（属于哪次拍摄、写在第几行）。手算与 CSV 出现末位差异时，先按"再次归一化 + 文本舍入上界（s_px 写 3 位小数 ≈ 5e-4 px）"两步解释，再怀疑数据。
19. **分清"坐标"与"位移"**：`s_px` 是沿方向的一维坐标，`ds_px` / `ds_mm` 才是相对基线 `s0` 的位移；引用任何一个一维量时，都要能说出它的基线是什么、由哪段代码（第几行）产生。
20. **看到"投影"或"方向"先问两件事**：这个方向指向哪一头、正方向约定写在哪一行（方向取反会让全部位移反号，而且不会报错）？结果的单位是像素还是毫米（`s_px` 是像素坐标，`ds_mm` 才是毫米）？自检：引用或复算前先答出这两问，再写公式。
21. **先问"基线是怎么选的"**：拿到相对位移数据先确认基线定义——本项目是"时间窗口内 valid 帧 `s_px` 的平均值"（`src\displacement.py` 第 351～352 行），不是首帧、不是标尺刻度；因此第 0 帧的 `ds` 不一定为 0，窗口不达标时宁可没有结果也不改规则（第 546、816、828 行）。
22. **先问"这一帧能不能用"**：检测成功（detected）只是第一道门；第二道门是本实验专属的 valid gate（area / y 范围），统计可用数据量要用 valid_rate 而不是 detection_rate；被拒绝的帧不会被删除，而是位移字段留空、`valid=False`——读数据前先确认这两道门的口径。
23. **看到"转向点"先问它存的是极值帧还是确认帧**：转向点存的是 `extreme_index`（极值帧，第 558、565 行），确认帧只是"反向行程达到 20 px"的那一帧；真实案例 peak f491 在 f505 才确认、valley f602 在 f732 才确认、peak f838 在 f971 才确认。自检：对每个转向点同时说出"极值帧 / 确认帧 / 反向行程"三件事。
24. **看到两个地方用同一个阈值，先问比较对象是否相同**：20 px 既用于状态机里的"从当前极值反向的行程"（第 557、564 行），也用于段级的"整段两端之间的行程"（第 600、617 行）；把两个比较对象分开，才不会被同一个数字误导。自检：说清 `below_min_travel` 与"转向是否成立"不是同一个判断。
25. **看到"时间间隔"先问它是哪两类事件之间的间隔**：相邻异类事件（peak→valley / valley→peak）只是半周期候选；同类事件（peak→peak / valley→valley）才是完整周期候选。自检：算任何间隔之前，先说出两端事件的 `kind`。
26. **宣布周期之前先过四道检查**：同类事件间隔是否一致、半周期与完整周期是否自洽、样本数量是否足够、数据是否来自同一段可信区间；四条不过关就只说"有往复结构"，不说"周期是多少"。自检：用 EXP-004 的 5 个半周期候选（1.846156 ～ 4.307696 s，约 2.33 倍）练习这句话。
27. **不同数据链的结论不互相搬运**：M5 动态实验（EXP-004）与 M6 外部公开视频（EXP-EXT-LAB67-V1）是两条独立数据链；M6 的 T = 0.542593 s / f = 1.843003 Hz 不能套到 EXP-004 上，EXP-004 的间隔也不能拿去解释 M6。自检：引用任何周期 / 频率数字前，先说出它属于哪条数据链、来自哪份文件第几行。
