## 1. 这份指南解决什么问题

VisionMotion 是一个用**普通摄像头 + 传统计算机视觉**做**非接触式位移测量**的阶段性科研项目。它把"视频里的一段运动"变成"可以讨论的物理量"：像素轨迹 → 位移 → 周期 / 频率。

本指南面向的科研使用场景与对应章节：

| 把像素变成毫米、做空间标定 | 第 6 章 |

## 2. 项目技术链路与模块地图

整条链路的中心思想是：**检测负责"找到目标"，标定负责"把像素变成毫米"，分析负责"把位移变成周期与频率"。** 检测只实现一次，后续模块一律复用，不各写一套。

```text
原始输入
  ├─ 图片 ───────────────► M2 检测 ──► 像素中心坐标
  └─ 视频 ──► M3 逐帧检测 ──► 像素轨迹 _track.csv ──► 质量核对(QC)
                                   │
                                   ├─► M4 标定 + 静态位移 ──► _ds.csv（s_px / ds_px / ds_mm）
                                   └─► M5 动态位移 ──► 转向点 / 运动段统计

外部公开视频 ──► M6.2 轨迹提取 ──► _trajectory.csv（像素 y0(t)）
                                          └─► M6.3 可视化与一致性核对 ──► 最终成果图
```

| 模块 | 作用 | 输入 | 输出 |
| --- | --- | --- | --- |
| M2 · `src/marker_detector.py` | 红色标记检测（HSV 掩膜 → 轮廓 → 质心） | BGR 图像 | 像素中心 `cx/cy`、面积、外接矩形、掩膜 |
| M3 · `src/video_tracker.py` | 视频逐帧检测、记录时序坐标、生成叠加视频 | 视频 | `_track.csv`（像素坐标时序）+ overlay 视频 |
| M4 · `src/calibration.py` | 纯数学标定：两点 + 真实距离 → 尺度与方向 | 两个像素点 + 真实距离 | `k`（px/mm）、单位方向 `u`、一维投影 |
| M4 · `src/displacement.py` | 静态位移链：轨迹 → 位移（含 QC） | `_track.csv` | `_ds.csv`（`s_px / ds_px / ds_mm`） |
| M5 · `src/dynamic_displacement.py` | 动态位移链：位移 + 转向点 / 运动段 | `_track.csv` | `_ds.csv` + 转向点与运动段统计 |
| M6.2 · `src/external_oscillation_tracker.py` | 外部公开视频正式轨迹提取（视觉规则冻结） | 外部视频 | `_trajectory.csv`（`y0(t)` 像素轨迹） |
| M6.3 · `src/m63_final_visualization.py` | 封板轨迹的可视化与一致性核对 | 封板 `_trajectory.csv` | 三张最终成果图 + 自检结论 |
| M7.3 · `src/m73_presentation.py` | 生成最终展示 PPT | 成果图 + 冻结数值 | `docs/VisionMotion_Final_Presentation.pptx` |

> 两条设计约束值得记住：**M2 的检测实现是唯一来源**，M3 只调用它；**M4 / M5 不重新实现投影公式**，统一调用 `src/calibration.py`。这保证同一份数据在不同阶段得到一致的结论。

## 3. 推荐科研工作流

```text
新的实验数据
   ↓
M2（单张图片）/ M3（视频）
   ↓
质量检查（QC，见第 11 章）
   ↓
M4 标定（人工点选 → 得到 k / u → 人工更新冻结常量）
   ↓
M4 静态位移  →  或  →  M5 动态位移（转向点 / 运动段）
   ↓
M6.2 外部数据（如适用，独立链路）
   ↓
M6.3 展示 / 冻结结果
```

**这条链路不是"必须全走一遍"，三个入口互不等价：**

- **图片链（M2）**与**视频链（M3 → M4 → M5）**是不同入口：单张图只做检测，不走位移链路；
- **外部公开视频链（M6.2 → M6.3）**是独立链路，与自采实验**不共用**标定与冻结常量；
- 只需要"检测 / 跟踪"的实验，不必进入 M4 / M5；**只有需要毫米位移时才需要标定**。

## 4. v1.0.0 用户视频流程

v1.0.0 提供的"一键流程"：**一个视频 → 五类结果**。入口是 `demo/run_user_video_pipeline.py`，它只做串联与提示，不重新实现任何算法——检测、帧率、标定、QC 全部留在 `src/` 内。

```powershell
.\.venv\Scripts\python.exe demo\run_user_video_pipeline.py --input data\raw\your_video.mp4 --out-dir results\your_video
```

**输入**：一个视频（默认检测画面中的**红色标记**目标）。

**输出**：五类结果，文件名由输入视频名自动派生（下例前缀为 `your_video`）：

| 输出文件 | 内容 |
| --- | --- |
| `your_video_track.csv` | 逐帧像素坐标时间序列（轨迹原始数据） |
| `your_video_overlay.mp4` | 目标检测叠加视频（逐帧核对检出情况） |
| `your_video_trajectory.png` | 二维运动轨迹图 |
| `your_video_displacement.png` | 像素位移曲线 |
| `your_video_fft.png` | FFT 频谱图 |

- 相对路径按**项目根目录**解析；`--out-dir` 目录不存在时自动创建；
- 默认**不覆盖**已有结果，确认覆盖请显式加 `--overwrite`；
- 脚本的运行退出码与常见报错处理，见 [用户使用指南](USER_GUIDE.md)，本指南不重复列出。

> 科研提示：这条流程得到的是**像素位移**与**基于像素的频谱**。它足以回答"运动有没有周期性、周期大约是多少"，但**不能直接当作毫米位移**——像素到毫米需要第 6 章的标定。

## 5. 自定义图片与视频输入（M2 / M3）

要把项目换成自己的数据，只需给脚本传入输入与输出路径，**不必改源码**：

```powershell
# 图片（M2）
.\.venv\Scripts\python.exe demo\run_single_image_detection.py --input data\raw\my_image.jpg --out-dir results\my_image

# 视频（M3）
.\.venv\Scripts\python.exe demo\run_video_tracking.py --input data\raw\my_video.mp4 --out-dir results\my_video
```

- `--input` / `--out-dir` / `--overwrite` 三个参数的**完整语义、退出码与排错**见 [用户使用指南](USER_GUIDE.md)；
- 输出名由输入文件名派生（`my_video.mp4 → my_video_track.csv` + `my_video_overlay.mp4`），不会沿用历史实验名；
- **检测参数（HSV 阈值、最小面积等）不是命令行参数**，它们固定在检测模块中。只有当目标**不是红色**、或需要换一套检测方案时，才需要修改源码——那属于"换实验方案"，不是"换一张图片"。

> **关键边界**：M3 的输出 `_track.csv` 是**像素坐标**（`x_px / y_px`），**不是毫米位移**。要得到毫米，必须经过第 6 章的标定。

## 6. 像素坐标到物理量：空间标定（M4）

**标定回答一个问题：画面里 1 毫米对应多少像素？** 只有先知道它，才能把像素位置换算成毫米位移。这是整个项目里"像素 → 物理量"的唯一桥梁，也是本指南最重要的一节。

### 标定思想

用画面中**已知真实距离的两个点**（例如尺子上的 10 cm 与 16 cm 刻线，真实距离 60.0 mm），确定两件事：

- **尺度 `k`**（px/mm）：1 毫米对应多少像素，其倒数为 mm/px；
- **方向 `u`**（单位向量）：从第一个点指向第二个点的单位方向，用来把二维坐标投影到标定方向上。

有了 `k` 与 `u`，"像素位置"才能被投影并换算成沿标定方向的一维毫米位移。

### 操作流程

1. 运行交互式脚本 `demo/pick_calibration_points.py`：它打开 `data/raw/EXP-003-STATIC-002.mp4` 的第 900 帧，由你依次点选 P1（10 cm 刻线）、P2（16 cm 刻线）；
2. 终端打印 `k`（px/mm）、`1/k`（mm/px）与单位方向 `u`；
3. **认清一个关键事实**：这个点选脚本**只在终端打印结果，不写任何文件**——标定结果**不会自动**进入后续位移管线，需要你人工接上（第 4 步）；
4. 按你的新实验，人工更新静态位移模块中的**实验专属冻结常量**：基准点与真实距离、像素 / 毫米换算常量、单位方向 `u`，以及配套的有效门限与零点参考窗口规则；
5. 重新运行静态位移入口。脚本会用你的新基准点**复算**换算常量并与冻结值比对、检查 `u` 是单位向量——**如果只改了标定点却没同步改换算常量，自检会报错并停止**。

### 为什么新数据必须重新标定

因为 `k`（px/mm）取决于**相机到目标的拍摄几何**：换视频、换机位、换焦距、换分辨率、改变拍摄距离，都会让"1 毫米 = 多少像素"发生变化。**不要复制旧实验的换算常量到新视频**——照搬旧值会得到"看起来正常、实际错误"的结果。

> 本项目当前**没有**把标定做成命令行参数或配置文件，这是**有意的设计选择**：标定是"实验条件"的一部分，必须显式记录，而不是藏在一个可随时改动的配置里。

## 7. 动态位移与运动分析（M5）

M5 面向**动态往复运动**，与 M4 共用前半段链路（检测 → 像素坐标），差别在"后半段"：

- M4 面向**静态位移**（较短的起始参考窗口、较宽的门限）；
- M5 面向**动态往复运动**（更长的参考窗口、更严格的门限），并额外做**转向点 / 运动段**统计。

### 分析思想

| 概念 | 含义（使用视角） |
| --- | --- |
| **s0（零点参考）** | 位移的零点。只用起始窗口内**有效帧**的平均位置作为起点；窗口内有效帧不足时**不生成位移文件**（属正常冻结行为，不是失败） |
| **valid gate（有效门限）** | 逐帧判断"这一帧的位置是否可信"（依赖检测是否成功、目标面积与画面位置是否合理）。`valid=False` 的位移字段**留空**，不写 0、不插值 |
| **转向点（turning point）** | 运动方向的反转点，在**原始像素序列**上检测，设有最小反向行程；**不平滑、不滤波、不插值** |
| **运动段（segment）** | 由起点、各转向点、终点切分出的区间；**运动段数 = 转向点数量 + 1** |

运行入口：

```powershell
.\.venv\Scripts\python.exe demo\run_m52_dynamic_displacement.py
```

> **结构性约束**：动态位移模块**不得 import** 静态位移模块。目的是从根上防止动态代码误用静态实验的门限与零点规则——**实验常量必须各自独立冻结**，不要为了"共享常量"让 M5 去 import M4。

转向点与运动段的**原理与推导**属于学习材料，见 [源码学习课程索引](learning/COURSE_INDEX.md)，本指南不重复展开。

## 8. 外部公开视频实验边界（M6.2）

- **自采实验数据**：你自己拍摄的图片 / 视频，其标定与结果属于你自己的实验；
- **外部公开数据**：第三方公开教育视频，放在项目根目录的 `_external/`（**注意：不在 `data/` 下**），来源、作者、许可与哈希记录在 [ATTRIBUTION.md](ATTRIBUTION.md)。

当前正式使用的外部视频为 ComPADRE / OSP 条目（许可 CC BY-NC-SA 3.0）。其处理区间（帧范围）与**文件身份**在源码中被冻结校验，用于保证"每次分析的都是同一段、同一个文件"。

**M6.2 得到的是 `y0(t)`——像素位置轨迹。**

> ### 关键边界
> **本项目没有为这段外部视频建立并应用有效的 px/mm 标定。** 因此**不能把 M6.2 的输出直接写成毫米位移或振幅**。它是以**像素**为单位的位置时间序列，把它当作毫米数据是错误用法。

这条边界是**实验结论的一部分**，不是"暂时没做"。任何引用该轨迹振幅、幅度或毫米级量值的说法，都必须先说明它只是像素量。

## 9. M6.3 实验验证与科研意义

M6.3 的定位：

```text
封板 trajectory CSV  →  可视化  →  一致性核对  →  最终展示图
```

它**不是"运行时重新做 FFT"**：封板可视化脚本使用**已封板的数值与极值清单**作图并做一致性核对，**不重新计算**周期 / 频率 / 极值 / FFT。

因此要正确理解：

- 报告中的周期、频率、FFT 主峰等数值属于**冻结分析结果 / 展示层**；
- 它们**不等于**每次运行脚本重新算出来的值；
- 若要**重建**这些数值，需按 [M6.3 阶段成果报告](M6.3_FINAL_REPORT.md) 中规定的规则（基于封板轨迹的"仅减均值后 rFFT"）自行实现——这属于"从原始数据重新分析"，项目当前**没有**提供现成的 FFT 运行时实现。

运行入口：

```powershell
.\.venv\Scripts\python.exe demo/run_m63_final_visualization.py
```

> M6.3 的科研意义在于**可核对**：它把"结论数值"与"展示图形"分离，使任何人可以用同一份封板数据复现出同样的图，并逐条核对自检结论。

## 10. 如何复现实验结果

有两种不同层次的"复现"：

### A. 结果复现（使用仓库内冻结数据）

- 直接使用仓库里已有的 `results/*.csv` 与 `results/*.png`；
- 运行 `demo/run_m63_final_visualization.py`，即可从封板轨迹**重新生成三张成果图**；
- 前提：仓库内数据未被修改，且本机具备所需中文字体；
- 这是"展示层复现"，**不涉及**从原始视频重跑算法。

### B. 从原始数据重新运行

- 需要：对应的**原始图片 / 视频**、正确的**参数**、正确的**标定**，以及每步的 **QC**；
- 图片链从 M2 起，视频链从 M3 起；需要毫米位移时才进入 M4 / M5；外部数据走 M6.2 独立链；
- **注意字节级一致性**：项目对部分上游产物有 SHA-256 冻结检查。若你重新生成上游 CSV，下游的冻结检查**可能**因字节不同而失败；
- 因此：**本指南不保证"重跑一定得到完全相同的 SHA"**。是否字节级一致取决于生成过程的确定性（浮点舍入、换行、编码等）。遇到不一致时，应判断"这是否是新实验 / 新版本"，而不是强行删掉校验。

> 仓库中的**原始实验图片 / 视频未随仓库分发**（体积原因），`_external/` 的第三方视频同样不随仓库分发。因此 **A 方式**可开箱复现，**B 方式**需要你本地具备相应素材。

## 11. 数据质量与结果可靠性

项目在每个阶段都内置**自动质量核对（QC）**，原则只有一条：

> **QC 用来发现问题，不用来修复问题。** QC 未通过时应**定位原因**，而不是绕过或跳过。

各阶段核对的重点不同，但共同关心三件事：**文件结构是否完整**（表头、行数、帧是否连续、时间轴是否自洽）、**数值是否合法**（坐标 / 面积 / 位移字段的取值与格式）、**结论是否可复算**（用同样的规则重算，能否得到同样的结果）。

三个需要记住的可靠性要点：

1. **SHA-256 用于确认数据文件身份一致性，不代表测量精度。** 它回答"你手上的文件是不是那个被冻结的版本"，与"测得准不准"无关；
2. **上游轨迹的完整性会影响下游位移是否可用**：当上游视频的逐帧处理存在中断或无法确认完整时，位移计算会**给出警告或跳过**，而不会假装数据完整。也就是说，**"跑出结果"不等于"结果可用"**；
3. **完整性、检出质量与测量精度是三个独立维度**：轨迹完整但检出率低并不可靠；检出率高但轨迹不完整同样不能算可靠。

（各脚本的运行退出码与报错处理属使用层内容，见 [用户使用指南](USER_GUIDE.md)。）

## 12. 项目限制与修改原则

### 可以修改

- 你自己的实验数据（放进 `data/raw/`）；
- M2 / M3 的输入路径请用命令行 `--input` / `--out-dir`，不要改源码；
- 针对**新实验重新标定**得到的常量（按新实验在对应位移模块中更新）；
- 实验专属冻结参数（属于高级用法，需自行承担"这是新实验"的责任并重跑 QC）。

### 不应随意修改

- **历史正式结果**（`results/` 里已封板的 CSV / PNG）；
- **外部数据 SHA**（外部视频的冻结哈希）；
- **QC 逻辑**（各阶段的自动校验）；
- **已封板实验数据与常量**（标注为"冻结"的常量）；
- **M6.2 的能力边界**（不要把 `y0(t)` 像素轨迹当作毫米位移）。

> 一句话原则：**如果确实要改变核心方法或换一套实验条件，应"新建版本 / 新实验"，而不是直接覆盖已冻结的结果。**

### 项目已知限制

- 标定是**实验专属**的：换设备、换机位、换距离都要重新标定，不能跨实验复用；
- 外部公开视频链**没有** px/mm 标定，只能给出像素量；
- 动态分析采用**不滤波、不插值**的保守策略：宁可留空，也不填补缺失值；
- 检测依赖**红色标记**，对光照、背景与目标大小敏感，更适合可控实验环境，而非通用场景。

## 13. 项目目录与命名说明

### 目录

| 目录 | 用途 |
| --- | --- |
| `data/raw/` | 实验**原始输入**（你自己的图片 / 视频） |
| `results/` | 程序输出与已封板结果 |
| `_external/` | 第三方公开数据（**不在 `data/` 下**） |
| `data/processed/` | 当前版本**暂未**作为主要运行入口使用（保留目录） |

### CSV 后缀

| 文件后缀 | 当前用途 |
| --- | --- |
| `_track.csv` | M3 / M4 / M5 的视频检测轨迹（像素坐标时序） |
| `_ds.csv` | M4 / M5 的位移数据（`s_px / ds_px / ds_mm`） |
| `_trajectory.csv` | M6.2 的外部轨迹（`y0(t)`） |

> `_track.csv` 与 `_trajectory.csv` 的差异是**模块历史设计差异，不代表错误**。本阶段**只说明、不重命名**：强行统一后缀可能影响冻结结果、文档引用与历史实验。
>
> `data/raw/` 中还留有若干**历史 / 示例文件**（例如 `red_move.mp4`、`red_test.jpg` 等），它们**不是**当前 demo 的标准输入，请以"当前 demo 实际读取的文件名"为准。
