- 说清"检测失败不等于程序崩溃"：失败是 `detect_marker()` 的正常返回值，程序不抛异常、不中断整段视频，只把这一帧如实标记为缺失；

## 2. 检测成功与检测失败

### 2.1 检测成功：有测量值

`detect_marker()`（`src\marker_detector.py` 第 105～151 行）在一切顺利时返回第 143～151 行的字典：

```python
# src\marker_detector.py 第 143～151 行
return {
    "success": True,
    "cx": cx,          # 目标中心 x（像素，浮点数）
    "cy": cy,          # 目标中心 y（像素，浮点数）
    "area": area,      # 目标轮廓面积（像素²）
    "bbox": (x, y, w, h),  # 外接矩形
    "contour": contour,    # 目标轮廓
    "mask": mask,          # 红色二值掩膜
}
```

其中 `cx` / `cy` 来自质心公式（第 100～102 行），`area` 来自 `cv2.contourArea(contour)`（第 140 行），`bbox` 来自 `cv2.boundingRect(contour)`（第 141 行）。

**检测成功的含义是**：这一帧里找到了一个满足项目规则的红色目标（外部轮廓、最大、面积 ≥ `MIN_AREA`、质心可计算），并且给出了完整的测量值。后续 CSV 的成功行（第 395～403 行）与叠加视频的绿框（第 204～231 行）都以此为输入。

### 2.2 检测失败：这一帧没有可用的测量值

当三道判定之一触发时（第 75～76、83～84、97～98 行），`detect_marker()` 返回：

```python
# src\marker_detector.py 第 132～133 行与第 136～137 行（两处相同）
return {"success": False, "mask": mask}
```

**检测失败的含义是**：这一帧没有测到可用的目标——不是"程序坏了"，而是"这一帧没有答案"。项目把这种状态明确写成 `success=False`，让调用方一眼就能分辨。

### 2.3 检测失败 ≠ 程序崩溃

这是本课最重要的一句话。它至少有三个层次的含义：

| 层次 | 检测失败时的实际行为 | 源码位置 |
| --- | --- | --- |
| 函数层 | `detect_marker()` **正常返回**一个字典（`success=False`），不抛异常、不中断 | `src\marker_detector.py` 第 132～133、136～137 行 |
| 循环层 | `track_video()` 的逐帧循环不因为 `success=False` 而退出；失败帧照样写 CSV、照样进 `records` | `src\video_tracker.py` 第 483～526 行（写行第 491 行、记账第 493～504 行） |
| 可视化层 | 失败帧只显示 "DETECTION FAILED"，不画任何虚假中心 | `src\video_tracker.py` 第 190～201 行 |

需要区分的是：项目里确实有"真的要停下来"的情况，但它们属于**资源级失败**，不是检测失败：

- 视频打不开：`open_video()` 返回 `(None, None)`（第 118～121 行），`track_video()` 打印错误并返回 `None`（第 427～429 行）；
- FPS 非法（≤ 0）：打印错误并停止（第 432～435 行）；
- 第一帧都读不到：打印错误并停止（第 438～442 行）。

这三条说明：**该停下来的时候停下来（整段视频无法处理），该继续的时候继续（某一帧没测到）**——两种"失败"层次不同，处理方式也不同。

## 3. marker_detector.py 的三道失败判定

检测流程是一条链：**掩膜（第 41～63 行）→ 找轮廓（第 66～86 行）→ 算质心（第 89～102 行）→ 组装结果（第 105～151 行）**。三道失败判定就是这条链上的三个"出口"。

### 3.1 第一道：没有任何轮廓

```python
# src\marker_detector.py 第 73～76 行
contours, _ = cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)

if len(contours) == 0:
    return None
```

触发条件：掩膜里一个外部轮廓都没有（整帧没有足够红的区域，或者红色区域被开运算全部消掉）。含义：**这一帧根本没有候选目标**。`find_target_contour()` 返回 `None`（第 76 行）。

### 3.2 第二道：面积不够（面积门槛失败）

```python
# src\marker_detector.py 第 78～84 行
contours_sorted = sorted(contours, key=cv2.contourArea, reverse=True)
biggest_contour = contours_sorted[0]

# 面积太小，说明不是我们想要的目标
if cv2.contourArea(biggest_contour) < MIN_AREA:
    return None
```

触发条件：即使有轮廓，**最大轮廓的面积**也小于 `MIN_AREA = 200`（第 33 行）。含义：有红色的东西，但太小，按项目规则"这不是我们想要的目标"（远距离、被遮挡、只剩噪点等都可能触发）。同样返回 `None`（第 84 行）。

### 3.3 第三道：质心无法计算（m00 == 0）

```python
# src\marker_detector.py 第 95～98 行
moments = cv2.moments(contour)

if moments["m00"] == 0:
    return None
```

触发条件：轮廓通过了两道前判定，但图像矩的零阶矩 `m00` 为 0，质心公式 `cx = m10 / m00` 会除以 0（第 100～102 行），因此必须先判无效。含义：**轮廓存在但退化到无法定位**。`calculate_centroid()` 返回 `None`（第 98 行）。

### 3.4 三道判定的共同出口

| 判定 | 位置 | 触发条件 | 谁返回 None | 在 `detect_marker()` 里的处理 |
| --- | --- | --- | --- | --- |
| 第一道：无轮廓 | 第 75～76 行 | `len(contours) == 0` | `find_target_contour()` | 第 131～133 行 → `{"success": False, "mask": mask}` |
| 第二道：面积门槛 | 第 83～84 行 | 最大轮廓面积 `< MIN_AREA`（200） | `find_target_contour()` | 第 131～133 行 → `{"success": False, "mask": mask}` |
| 第三道：m00 == 0 | 第 97～98 行 | 矩的面积总量为 0 | `calculate_centroid()` | 第 135～137 行 → `{"success": False, "mask": mask}` |

三道判定的共同点：**都不抛异常、都只是"提前返回"，最终都汇合成同一个失败字典**（第 133、137 行）。所以 `detect_marker()` 对调用方永远只有两种输出：成功字典或失败字典——调用方不需要写 `try / except`，只需要看 `success`。

> 概念解释：这种"用一个明确的返回值表达失败，而不是让程序报错"的做法，是接口设计层面的选择。项目里检测参数集中在 `src\marker_detector.py`（第 17～33 行），`video_tracker.py` 第 19～21 行的模块说明也声明"检测参数唯一来源是 `src/marker_detector.py`"——失败规则同样只有这一处，保证全项目一致。

## 4. None、success=False 与失败返回结构

### 4.1 三层表达，三种作用

| 表达 | 出现在哪 | 具体形态 | 作用 |
| --- | --- | --- | --- |
| `None` | `find_target_contour()` 第 76、84 行；`calculate_centroid()` 第 98 行 | Python 空值 | 函数级信号："这个子步骤没有结果" |
| `success=False` 字典 | `detect_marker()` 第 132～133、136～137 行 | `{"success": False, "mask": mask}` | 模块级信号："这一帧检测失败"（调用方的唯一判据） |
| 失败 CSV 行 | `build_csv_row()` 第 404 行 | `[frame, "%.6f" % time_s, "", "", "", "False"]` | 文件级表达："这一时刻缺失，且不伪造数字" |

这三层是逐级翻译的关系：`find_target_contour()` 的 `None` 被 `detect_marker()` 翻译成 `success=False`；`result["success"]` 又被 `build_csv_row()`（第 395 行判断）翻译成 `detected=False` 加三个空字段。

### 4.2 为什么失败返回结构里没有 cx / cy / area / bbox / contour

因为**这些键只在成功分支才被放进去**：

```python
# src\marker_detector.py 第 139～151 行（成功分支才会执行到这里）
cx, cy = centroid
area = cv2.contourArea(contour)
x, y, w, h = cv2.boundingRect(contour)

return {
    "success": True,
    "cx": cx,
    "cy": cy,
    "area": area,
    "bbox": (x, y, w, h),
    "contour": contour,
    "mask": mask,
}
```

逐个解释"为什么没有"：

| 键 | 要算出它需要什么 | 失败时为什么没有 |
| --- | --- | --- |
| `cx` / `cy` | 合法轮廓 + `m00 ≠ 0` 的矩（第 95～102 行） | 要么根本没有轮廓，要么 `m00 == 0` 除不了——测量值不存在 |
| `area` | 一个通过面积门槛的轮廓（第 140 行） | 面积不达标时该轮廓已被判定"不是目标"；没有目标就没有目标面积 |
| `bbox` | 轮廓（第 141 行 `cv2.boundingRect`） | 同上，没有合格轮廓就没有外接矩形 |
| `contour` | 通过两道判定的"最大轮廓"（第 86 行返回） | 判定失败时轮廓被丢弃，函数返回的是 `None` |
| `mask` | 本帧的掩膜（第 129 行已经算好） | **失败字典里保留了 mask**——它和第 129 行同一次计算，保留它可供诊断（看看到底哪里红、红色区域长什么样） |

两个使用侧的配套设计保证"没有键"不会引发 `KeyError`：

- `build_csv_row()` 只在 `if result["success"]:` 分支里访问 `result["cx"]` / `["cy"]` / `["area"]`（第 395～403 行），失败分支（第 404 行）根本不碰这些键；
- `draw_tracking_frame()` 在 `if not result["success"]:` 时直接显示失败文字并 `return overlay`（第 190～201 行），后面的 `result["bbox"]` / `["cx"]` / `["cy"]`（第 204～224 行）只在成功路径上执行。

> 概念解释：这就是"**先看 success，再取字段**"的接口契约。字典里"缺键"不是缺陷，而是在类型层面表达"这一帧没有测量值"。

## 5. detected=False 与 CSV 空字段

### 5.1 失败行长什么样

```python
# src\video_tracker.py 第 387～404 行
def build_csv_row(frame_index, time_s, result):
    """
    检测成功：frame, time_s(6 位小数), x(2 位), y(2 位), area(1 位), True
    检测失败：frame, time_s(6 位小数), 空, 空, 空, False
    失败时绝不写 0 / -1 / nan / 字符串。
    """
    if result["success"]:
        return [ ... 六个字段 ... ]
    return [frame_index, "%.6f" % time_s, "", "", "", "False"]
```

失败行的 6 个字段逐个看：

| 字段 | 失败行的值 | 为什么 |
| --- | --- | --- |
| `frame` | 照常写帧号 | 时间轴必须连续：这一帧"存在过"，只是没测到 |
| `time_s` | 照常写 `frame_index / fps`（第 488 行算好传入） | 同上，测量时刻是确定的事实 |
| `x_px` | `""`（空） | 没有测量值 |
| `y_px` | `""`（空） | 没有测量值 |
| `area_px` | `""`（空） | 没有合格轮廓，没有目标面积 |
| `detected` | `"False"` | 明确的失败标志（文本，不是数字 0） |

一句话：**"没有测量值"与"测量值为某个数"是两件不同的事，CSV 用空字段表达前者**。

> 注意（证据边界）：本课核对的两份真实 CSV（EXP-002 与 EXP-EXT-LAB67-V1）中**没有任何失败行**（第 16 节），
> 所以上面的失败行形状来自源码第 404 行与 L05 / L06 的课程约定，**不是**从这两份真实数据中"看到"的。
> 教学演示用的失败行（例如 `4,0.066667,,,,False`）是教学示例，不是项目数据。

### 5.2 为什么缺失不能用 0 / -1 / nan / 上一帧坐标代替

第 393 行的原则是项目对这个问题的正式回答："**失败时绝不写 0 / -1 / nan / 字符串**"。逐条分析：

| 代替方案 | 为什么不行 | 项目里的对应证据 |
| --- | --- | --- |
| 写 `0` | `0` 是**合法坐标**（画面边缘方向），无法与"真的测到 (0,0)"区分；并且它会被下游当数值参与平均、位移、极值等计算，**污染统计** | 自检第 701～702 行专门收集 `x==0.0 且 y==0.0` 的成功行，第 713 行把它列为"伪数据"检查项 |
| 写 `-1` | `-1` 不是本坐标系的合法位置，但它仍是数字，读进程序后会被当成测量值参与计算；事后同样无法分辨"失败"与"测到 -1" | 第 393 行明确禁止；第 711 行要求成功行 x/y/area 都是合法数值——一旦把 -1 写进成功行，自检口径就被破坏 |
| 写 `nan` | 在 CSV 文本里 `nan` 会被当字符串写入；读回时看起来像缺失，但与"空字段读回产生的 NaN"混在一起，**无法区分"没测到"和"程序写了个 nan"**；而且第 393 行本身就把 nan 列为禁止项 | 项目的设计是：**文件里留空**（第 404 行）；读取工具 `np.genfromtxt` 自然把空字段理解为 NaN（第 725～731 行），这是读取端的表示，不是写文件时写入 nan |
| 抄上一帧坐标 | 这是**伪造测量**：数据表里会出现一个"不存在的测量值"，事后任何人都无法分辨"目标真的没动"还是"这一帧没测到" | 第 190～201 行的可视化同款原则：失败帧连画都不画，就是为了不制造"虚假中心" |

第 393 行那句话的完整含义是：**测不到，就明确标记缺失，而不是制造一个假测量。** 数据可以缺失，但不可以撒谎——这是整个项目数据可信度的底线。

### 5.3 空字段与时间轴完整性

失败帧不是"跳过不写"：第 490 行注释明确"**每帧一行，检测失败也要写**"，第 491 行无条件写行。这样 frame 与 time_s 保持连续（`0…N-1`，自检第 675～677 行），缺失只发生在测量列。**时间轴完整 + 测量值明确缺失**，后续分析才能同时知道"什么时候测了"与"什么时候没测到"。

## 6. records 中如何记录失败

### 6.1 源码：三条固定键 + 三条可选键

```python
# src\video_tracker.py 第 493～504 行
record = {
    "frame": frame_index,
    "time_s": time_s,
    "success": bool(result["success"]),
}
if result["success"]:
    record["cx"] = result["cx"]
    record["cy"] = result["cy"]
    record["area"] = result["area"]
    detected_count += 1
    area_list.append(result["area"])
records.append(record)
```

关键在**缩进**：`records.append(record)` 在 `if` 外面（第 504 行），所以：

| 帧的结果 | 进 `records` 的字典 | 键的数量 |
| --- | --- | --- |
| 检测成功 | `{"frame", "time_s", "success", "cx", "cy", "area"}` | 6 个键 |
| 检测失败 | `{"frame", "time_s", "success"}`（`success` 为 `False`） | 3 个键 |

也就是说：**失败帧同样在 `records` 里占一条**（时间轴完整），但它的字典里**没有** `cx` / `cy` / `area` 键——这和失败返回结构（第 133、137 行）"没有键"的思想完全一致，只是换了一层容器。

### 6.2 失败记录如何被后续使用

`records` 是"程序自己的账本"，它的失败记录被这些地方使用：

- `compute_longest_miss_run()` 读 `record["success"]`（第 592 行）统计最长连续丢失；
- 统计计数：`detected_count` 只在成功分支 +1（第 502 行），`area_list` 只在成功分支追加（第 503 行）；
- `find_fastest_motion_frame()`（PNG 回退方案）在成功帧之间比较中心点距离，遇到失败帧会把 `previous` 重置为 `None`（第 274～284 行），不会跨失败帧乱算距离。

注意一个容易混的点：**内存里叫 `success`，CSV 里叫 `detected`**（第 496 行 vs 第 41 行）。同一件事，两种命名：`success` 是 Python 布尔值，`detected` 是 CSV 文本列里的 `"True"` / `"False"`（第 402、404 行）。

## 8. 为什么中间坏帧不会让整个视频处理停止

### 8.1 控制流证据

`track_video()` 的逐帧循环（第 483～529 行）里，`result` 只被用于三件事：写 CSV 行（第 491 行）、写 `record`（第 493～504 行）、画叠加帧（第 506～518 行）。**没有任何一处根据 `success` 决定继续还是停止**——成功就写成功行，失败就写失败行，然后统一进入"读下一帧"（第 521 行）。循环里没有 `break`、没有 `return`、没有 `raise` 是针对 `success=False` 的。

### 8.2 循环真正的退出方式

| 退出方式 | 位置 | 触发条件 | 性质 |
| --- | --- | --- | --- |
| `break` | 第 522～524 行 | `cap.read()` 返回 `ret=False`（读不到下一帧） | 序列层面的**正常结束**（第 523 行注释："视频解码结束（ret=False）：正常结束，不因为单帧失败中断"） |
| `except KeyboardInterrupt` | 第 530～533 行 | 用户按 Ctrl+C | 人为中断；已处理的帧数据保留在 CSV 与叠加视频中（第 532～533 行） |
| 函数提前返回 | 第 427～442 行 | 视频打不开 / FPS 非法 / 第一帧失败 | 资源级失败（整段视频无法处理） |

所以"中间坏帧不停止"不是运气，而是**控制流里根本没有"因失败而退出"的路径**。

### 8.3 概念对比（不是项目源码）：如果失败时抛异常会怎样

> 概念伪代码（不是 VisionMotion 真实源码），用于说明设计差异：
>
> ```text
> # 概念伪代码（不是项目真实源码）
> for 每一帧:
>     if 检测不到目标:
>         raise 错误        # 或 return 提前退出整个函数
>     记录这一帧
> ```
>
> 在这种写法下，**第一帧没测到，整段视频就报废**：后面的帧再成功也没有机会被处理，CSV 只写到坏帧为止。
> 项目的写法正好相反：失败被当成"这一帧的答案"记录下来（第 404 行），循环继续走到视频结束。
> 这就是"检测失败 ≠ 程序崩溃"在工程上的实际价值。

## 9. compute_longest_miss_run()：最长连续丢失

```python
# src\video_tracker.py 第 585～598 行
def compute_longest_miss_run(records):
    """
    计算最长连续丢失帧数量。
    """
    longest = 0
    current = 0
    for record in records:
        if record["success"]:
            current = 0
        else:
            current += 1
            if current > longest:
                longest = current
    return longest
```

逐行读：

| 行号 | 做了什么 |
| --- | --- |
| 第 589～590 行 | 初始化 `longest`（历史最长）与 `current`（当前连续丢失长度）为 0 |
| 第 592～593 行 | 遇到成功帧：**当前连续丢失清零**（连续性被打断） |
| 第 594～597 行 | 遇到失败帧：`current` 加 1，并刷新历史最大值 |
| 第 598 行 | 返回历史最大值 |

两个性质：

- **返回值 0 意味着整段没有失败帧**（只要出现过 1 个失败帧，`longest` 至少为 1）；
- 它统计的是"**连续**"而不是"总数"：5 个分散的失败帧（两两之间都有成功）与 5 个连成一排的失败帧，`missed_frames` 都是 5，但 `longest_miss_run` 分别是 1 和 5——对时序分析的含义完全不同。

它被 `summary` 调用（第 568 行），并在 `print_statistics()` 第 8 项打印（第 621 行："最长连续丢失帧：%d"）。

## 10. detection_rate：会算，还要会读

### 10.1 定义与来源

```python
# src\video_tracker.py 第 564～568 行（summary 节选）
"processed_frames": len(records),
"detected_frames": detected_count,
"missed_frames": len(records) - detected_count,
"detection_rate": detected_count / float(len(records)) if records else 0.0,
"longest_miss_run": compute_longest_miss_run(records),
```

`detection_rate = 检出帧数 ÷ 实际处理帧数`（第 567 行），在 `print_statistics()` 里以百分比打印（第 619 行，`%.4f%%`）。它是运行期统计（来自内存 `records` / 计数器），不是从 CSV 重新读出来的。

### 10.2 为什么不能只看 detection_rate

三条理由：

1. **它不反映失败的分布。** 同样 95% 的检出率，"失败分散成单帧"与"连续 5 帧黑段"对后续分析的影响完全不同——这正是 `longest_miss_run`（第 585～598 行）存在的理由：两个指标要一起看。
2. **它不校验数值是否合理。** `detection_rate = 1.0` 只说明"每帧都返回了 success=True"，不说明坐标没有 (0,0)、没有越界、面积没有异常。数值合理性要靠 `check_csv_data()` 的九项检查（第 637～748 行）。
3. **100% 检出也不等于"数据可以直接拿去分析"。** M6 的质量检查就是在 100% 检出之外，还要求无空值、无 >30 px 突跳、无候选歧义、时间戳严格一致（`src\external_oscillation_tracker.py` 第 452～501 行）——见第 13 节。

> 教学示例（非真实数据）：假设两段各 100 帧的视频都是 95 帧成功、5 帧失败。
> A 段失败分散在第 10、30、50、70、90 帧 → `longest_miss_run = 1`；
> B 段失败集中在第 48～52 帧 → `longest_miss_run = 5`。
> 两段的 `detection_rate` 都是 0.95，但 B 段中间有 5/30 秒（30 fps）连续空白，
> 用它做频率分析的风险明显更大。这个例子是课堂上构造的，不是项目数据。

### 10.3 真实数据的检测率

两份真实 CSV 的只读统计结果：**`detection_rate` 都是 1.0000（952/952 与 160/160），`longest_miss_run` 都是 0**（详见第 16 节）。这说明：

- 这两段数据的采集条件良好，没有出现检测失败；
- **同时**说明本课的"失败处理"结论**无法从这两份数据中得到实测证据**——它是由源码（第 75～76、83～84、97～98、404、493～504、190～201 行）与课程约定支撑的。这一点必须在长期记录里写清楚（见第 15 节"证据边界"）。

空字段在文件里是"空"，但用 `np.genfromtxt` 读回来时会变成 NaN。第 725～735 行做的就是**用两种完全不同的读取方式对暗号**：

```python

detected_values = data["detected"]
true_count = int(np.count_nonzero(detected_values))

    genfromtxt_note = ("成功，失败字段读取为 NaN（NaN 行数 %d，"
                       "与 detected=False 行数一致）" % nan_count)

```

含义：文本层面（`csv.reader` 读到的空字符串个数）与数值层面（`np.genfromtxt` 读到的 NaN 个数）必须讲同一个故事——**"失败了几帧"从两个入口数出来必须一样**（第 729～731 行）。如果某一行失败却写了 0，NaN 数就会小于 False 数；如果成功行漏写了坐标，NaN 数又会大于 False 数——两种情况都会被这项检查抓住。

### 11.4 重点二：坐标范围检查（第 703～704 行）

```python
# src\video_tracker.py 第 703～704 行

    out_of_range_rows.append(frame_number)
```

坐标必须落在**程序实际处理的画面尺寸**内（`frame_width` / `frame_height` 由调用方从 `summary["width"]` / `["height"]` 传入，即第一帧的真实宽高，不是硬编码 1920×1080）。这条检查的作用：即使 `detected=True`，一个越界坐标也说明测量可疑（掩膜 / 轮廓环节出了问题），不能让这种数据悄悄通过。

### 11.5 重点三：0/0 伪数据检查（第 701～702 行）

```python

    zero_zero_rows.append(frame_number)
```

为什么专门查 (0,0)？因为它是**"没算出来却写了个默认值"的典型痕迹**：图像坐标的原点在左上角，真实目标恰好落在精确 (0,0) 的概率极低；而程序里很多"没数据"的默认写法就是 0。第 713 行把它列为独立检查项，正是对第 393 行"绝不写 0"的机器验收：**人立了规矩，自检程序负责证明规矩被执行了。**

### 11.6 检查项的读法：每一条都对应一个"可能撒谎的地方"

| 检查组 | 防的是什么 |
| --- | --- |
| 表头 / 列数 / 行数（第 1～3 项） | 文件结构被改动、表头和数据错位、写漏行 |
| frame 连续（第 4 项） | 跳过失败帧不写、帧号重复 |
| 成功行数值 + 0/0 + 范围（第 5、7、8 项） | 成功行里混进非法值、默认值、越界值 |
| 失败行留空（第 6 项） | 失败时写 0 / -1 / 上一帧坐标等伪数据 |
| 通用读取 + NaN 对应（第 9 项） | 文件与约定不一致、失败数量在两个读取视角下对不上 |

## 12. area 的质量意义

`area_px` 在 M3 的 CSV 里来自 `cv2.contourArea(contour)`（`src\marker_detector.py` 第 140 行），以 1 位小数写入（`src\video_tracker.py` 第 401 行）。它在项目里的角色是**质量字段**，不是运动测量量（这一点 L01 已经登记过）：

1. **进门资格：** 最大轮廓面积必须 ≥ `MIN_AREA = 200`（第 33、83～84 行），否则直接判定"不是目标"→ 检测失败。面积在这里是"候选是否够格"的门槛。
2. **运行期画像：** `summary` 汇总 `area_min` / `area_median` / `area_max`（第 569～571 行，只统计成功帧，来自第 503 行 `area_list`），`print_statistics()` 第 9～11 项打印（第 623～625 行）。面积的"平时水平"就是这批数据的第一张体检照。
3. **异常线索：** 某帧面积明显偏离中位数，即使 `detected=True` 也值得警惕——常见原因包括目标被部分遮挡、离镜头远近变化、模糊、掩膜被背景红色干扰。面积突变提示"这一帧的测量可能不可靠"，但项目**本课不做自动判断**（M6 才在质量检查里加入突跳与歧义检查，且也只打印给人工核对）。
4. **area 的单位：** 像素²（面积），所以两条边的长度都影响它；它不能当作"目标大小（长度）"直接使用。

真实数据的 area 统计（只读核对）：

| 文件 | area_px 最小值 | 中位数 | 最大值 |
| --- | --- | --- | --- |
| `results\EXP-002-VIDEO-001_track.csv` | 4673.0 | 5265.0 | 6061.5 |
| `results\EXP-EXT-LAB67-V1_trajectory.csv` | 226 | 508.5 | 658 |

> 对比可见两份数据的"质量画像"完全不同：EXP-002 的红色目标面积在 4600～6100 像素² 一带；EXP-EXT 的暗带面积只有 226～658 像素²。面积量级不同，正是两个测量任务的差异——但它们都各自远离 M3 的 `MIN_AREA = 200` 门槛（注意：`MIN_AREA` 是 `marker_detector.py` 的规则，只约束 M3 的红色标记检测）。

## 13. M3 与 M6 对失败的不同质量门槛

同一个"失败"，两个模块给的待遇不同——因为两份数据的**下游用途不同**。

### 13.1 M3：允许失败存在，但要求诚实

`check_csv_data()` 的九项检查（第 637～748 行）里，没有一项要求"不许有失败帧"；相反，第 712 行专门等着一行行失败行来对暗号：**失败行必须留空、必须写 False，且读回时的 NaN 数必须与 False 数一致**（第 725～731 行）。M3 的质量门槛可以概括为：

> **"数据可以缺失，但缺失必须被如实记录、可被两个独立视角对账。"**

### 13.2 M6：把"100% 检出 + 无异常"当成硬性通过项

`check_trajectory_csv()`（`src\external_oscillation_tracker.py` 第 422～505 行）是 M6 轨迹 CSV（`_trajectory.csv`）的独立质量检查，共追加 17 条检查项，其中与"失败 / 异常"直接相关的硬性门槛包括：

| 检查 | 行号 | 通过条件 |
| --- | --- | --- |
| detected 全为 True | 第 452～455 行 | 160/160 全部成功，**一帧失败即"未通过"** |
| y0_px 空值数量 = 0 | 第 457～459 行 | 正式位置特征 `y0_px` 不允许空 |
| 单帧 \|Δy0_px\| > 30 px 突跳次数 = 0 | 第 480～483 行（阈值 `MAX_JUMP_PX = 30.0` 在第 99 行） | 不允许出现大幅跳变 |
| 候选数量歧义帧数（合格暗带 > 1）= 0 | 第 485～492 行 | 不允许"这一帧有好几个候选、系统可能选错" |
| time_s 严格满足 frame / fps | 第 494～501 行 | 时间戳偏差 ≤ `TIME_TOLERANCE_S = 1e-5`（第 100 行） |
| 原始视频 SHA-256 完整性（第 16 项） | 第 528～534 行 | 运行前哈希 = 预期基线，且运行后 = 运行前；未提供哈希即"未通过" |
| y0_px 有限性（第 17 项） | 第 536～546 行 | `y0_px` 不允许 NaN / ±inf，非有限值数量 = 0 |

另外，第 468～472 行的数值范围与第 475～478 行的最大单帧跳变属于**信息项**：它们在文件里被追加为"永远通过"，只打印数字供人工核对，不作为通过 / 不通过判据（第 467 行注释原文："7 ~ 11. 数值范围（信息项，用于人工核对；不作为'通过/不通过'判据）"）。

> 现行实现（只读核对所得）：第 16 项"原始视频 SHA-256 完整性"与第 17 项"`y0_px` 有限性"都已由 `checks.append(...)` 追加进 checks 列表
> （第 528～534 行 / 第 536～546 行），因此纳入函数末尾 `passed = all(ok for _, ok in checks)` 的汇总判定；
> 视频 SHA-256 由 `sha256_before / sha256_after / expected_sha256` 共同判定（运行前 = 预期基线、运行后 = 运行前，即原始视频未被改动），
> 更早的 `verify_video_sha256()`（第 119～132 行）仍是运行前校验，不一致直接报错停止。

### 13.3 为什么门槛不同：下游用途不同

| 对比项 | M3 `_track.csv` | M6 `_trajectory.csv` |
| --- | --- | --- |
| 记录对象 | 整段视频的逐帧测量记录 | 自由振荡段的正式轨迹（frame 76～235） |
| 失败能不能出现在最终数据里 | 能——失败是"测量过程"的一部分，如实记录即可 | 不能通过验收——正式分析段要求完整、无歧义 |
| 质量检查的立场 | 对账："失败被诚实标记了吗？两个视角数得一样吗？" | 准入："这数据可以直接拿去做频率 / 周期分析吗？" |
| 关键行号 | 第 705～712、725～735 行 | 第 452～459、480～492、494～501 行 |

结论：**这不是谁更严格，而是两支质检员在回答不同的问题。** 记录型数据（M3）要"诚实完整地还原测量过程"；分析型数据（M6）要"保证窗口完整可用"。写失败数据的人和用失败数据的人，都要先知道自己面对的是哪一种。

## 14. 质量检查与鲁棒性的定义

### 14.1 质量检查（Quality Check）

**以"写出来的产物"为对象，验证它是否符合设计约定、是否可信的只读流程。**

- 对象是磁盘上的 CSV（第 646～648 行重新打开），不是内存变量；
- 只读（第 639 行说明"只读，不创建任何额外测试文件"），发现问题也不修改数据，只报告；
- 检查"结构"（表头、行数、帧连续性）与"内容"（成功行合法、失败行留空、无 (0,0)、范围、NaN 对账）；
- 结论是显式的通过 / 不通过（第 747 行）——数据也要"体检合格"才算完成。

### 14.2 鲁棒性（Robustness）

**系统在"测不到 / 条件变差"时的行为是否仍然可预测、可解释、可追溯。**

本项目里鲁棒性具体化为五条：

1. **不崩溃**：失败是 `return` 出来的字典（第 133、137 行），不是异常；
2. **不伪造**：绝不写 0 / -1 / nan / 上一帧坐标（第 393 行）；
3. **不破坏时间轴**：失败帧照写 frame / time_s（第 404、490～491 行），帧号连续；
4. **不被坏帧拖垮**：循环不因单帧失败退出（第 483～526 行），坏帧只影响它自己那一行；
5. **把问题暴露出来**：`detected=False`（第 404 行）、"DETECTION FAILED"（第 190～201 行）、`detection_rate` / `longest_miss_run`（第 564～568 行）、九项自检（第 637～748 行）——失败不会被悄悄吞掉，而是留给人和下游程序判断。

因此本项目里：**鲁棒 ≠ 检出率 100%；鲁棒 = 坏情况发生时，数据仍然诚实、行为仍然可预测、问题仍然可被发现。**

三层防线一览：

| 层 | 职责 | 关键位置 |
| --- | --- | --- |
| 检测层（marker_detector.py） | 判定"这一帧有没有可用目标" | 三道失败判定：第 75～76、83～84、97～98 行 |
| 记录层（video_tracker.py） | 如实表达失败，不伪造、不丢时间轴 | 第 190～201、393、404、490～504 行 |
| 检查层（video_tracker.py） | 对产物体检、统计与报告 | 第 556～580、585～598、606～629、637～748 行 |

## 15. 证据边界与诚实记录实验数据

### 15.1 什么是"证据边界"

**证据边界 = 一条结论"最多能被什么支持到哪一步"。** 写学习记录和写实验报告一样：先说清证据在哪，再说结论。

### 15.2 本课的三类证据

| 结论类型 | 证据来源 | 本课的实际情况 |
| --- | --- | --- |
| 代码怎么设计失败处理 | 真实源码：`src\marker_detector.py`、`src\video_tracker.py`（可给出行号） | 全部可核实（第 20 节源码地图） |
| 数据里有没有失败 | 真实 CSV 只读统计（第 16 节） | 两份文件都是 100% 检出、0 失败行、0 空字段、0 个 NaN |
| 失败处理"跑起来"效果如何 | 需要真实触发过失败的运行记录 | **没有**——两份 CSV 里没有失败帧，本课不制造新实验去验证 |

### 15.3 因此本课"能说"和"不能说"

- 能说：**代码在检测失败时会怎么做**（有确定性设计，可逐行核对）；
- 能说：**这两份数据的检测率、缺失数、NaN 数、坐标与面积范围**（只读统计，可复核）；
- 能说：**"数据可信"在本项目里必须通过九项检查 / M6 独立检查来证明**；
- 不能说：**"本项目在真实视频上处理过检测失败，并验证了恢复流程"**——因为现有两份数据没有失败帧；
- 不能说：任何把教学示例（如 `4,0.066667,,,,False`）或伪代码当作"项目真实运行结果"的话。

### 15.4 诚实记录实验数据的四条纪律（本课约定）

1. **只读核对**：核对 `results\` 下的产物不修改、不覆盖、不重新生成（本笔记严格遵守）；
2. **标注来源类型**：每条结论注明是"源码 / 真实数据 / 概念解释 / 教学示例 / 概念伪代码"（第 18 节有对照表）；
3. **数字可复核**：给出文件名 + 统计口径（怎么数的），让别人能独立数出同样的数；
4. **不越界表述**：设计上支持 ≠ 实测已发生；样本中没有 ≠ 永远不会发生。写报告时把"没有观察到"写成"没有观察到"，不写成"已经解决"。

## 21. 本节课最重要的概念

1. **检测失败 = 这一帧没有可用测量值**：它是正常返回值（第 132～133、136～137 行），不是异常、不是崩溃；
2. **三道失败判定**：无轮廓（第 75～76 行）、面积 < 200（第 83～84 行）、`m00 == 0`（第 97～98 行）——全部"提前返回"；
3. **失败返回没有测量键**：`cx` / `cy` / `area` / `bbox` / `contour` 只在成功分支（第 143～151 行）存在；先看 `success`，再取字段；
4. **CSV 的失败行**：frame / time_s 照写，x / y / area 留空，`detected=False`（第 404 行）；"绝不写 0 / -1 / nan / 字符串"（第 393 行）；
5. **为什么不能伪造缺失**：0 是合法坐标、-1 是数字、nan 分不清来源、上一帧坐标是假测量——都会污染下游统计（自检第 701～702、713、725～735 行负责抓假）；
6. **records 的失败记录**：三条固定键（`frame` / `time_s` / `success`），成功才追加 `cx` / `cy` / `area`（第 493～504 行）；
7. **可视化也诚实**：失败帧只显示 "DETECTION FAILED"，不画虚假中心（第 190～201 行）；
8. **坏帧不拖垮整段**：循环没有因失败退出的路径；唯一 `break` 是"读不到下一帧"（第 522～524 行）；
9. **`compute_longest_miss_run()`**：最长连续丢失帧数（第 585～598 行），回答"有没有连续一大段空白"；
10. **`detection_rate` 不够用**：它不反映失败分布、不校验数值合理性（第 564～567、619 行）；
11. **九项检查**：表头、行数、frame 合法与连续、成功行数值、失败行留空、无 0/0、坐标范围、`np.genfromtxt` + NaN 对账（第 637～748 行；第 747 行全过才算通过）；
12. **NaN ↔ False 对账**：两个读取视角数出的失败帧数必须一致（第 725～735 行）；
13. **area 是质量字段**：进门门槛 200（第 33、83～84 行），运行期看 min / median / max（第 569～571、623～625 行）；
14. **M3 与 M6 门槛不同**：M3 允许失败但要求诚实（第 705～712、725～735 行）；M6 要求 100% 检出 + 无空值 / 无突跳 / 无歧义 / 时间严格（`external_oscillation_tracker.py` 第 452～501 行）；
15. **鲁棒性定义**：坏情况来临时不崩溃、不伪造、不丢时间轴、不被坏帧拖垮、把问题暴露出来——鲁棒 ≠ 检出率 100%；

## 22. 易错点

1. **把"检测失败"当成"程序崩溃 / 报错"。** 失败是返回值；崩溃是异常。本课的三道判定全部 `return None` / `return {"success": False, ...}`；
2. **以为失败返回字典里也有 cx / cy，只是值为 None。** 不是——那些键根本不存在（第 133、137 行）；访问前必须先看 `success`；
3. **看到 `None` 以为是"空对象"，不看它出现在哪一层。** 第 76、84、98 行的 `None` 是函数级信号；第 118～121 行 `(None, None)` 是视频级失败；层次不同；
4. **失败时用 0 / -1 / nan / 上一帧坐标"补"上。** 第 393 行明确禁止；第 701～702、713 行会抓 (0,0)，第 725～735 行会抓"数目对不上"；
5. **把 'DETECTION FAILED' 当成字幕装饰。** 它是失败帧的正式显示约定（第 190～201 行），是"不伪造"原则在可视化上的投影；
6. **以为有坏帧就会中断视频处理。** 循环只按"读不到下一帧"退出（第 522～524 行）；坏帧只影响自己那一行；
7. **只看 detection_rate 就下结论。** 还要看 `longest_miss_run`（第 568、585～598 行）与九项检查（第 637～748 行）；100% 检出也可能数值可疑；
8. **认为 `longest_miss_run = 0` 与 `missed_frames = 0` 是同一件事。** `longest_miss_run = 0` 必然意味着零失败帧；但反过来，有失败帧时 `missed_frames > 0`，`longest_miss_run` 至少为 1（第 592～597 行）；
9. **以为 NaN 是"程序故意写进 CSV 的"。** 文件里失败字段是"空"（第 404 行）；NaN 是 `np.genfromtxt` 读取空字段时的表示（第 725～731 行）；
10. **把 M3 的九项检查与 M6 的独立质量检查混为一谈。** 两份文件、两个函数、两套口径；M6 多了 100% 检出、突跳、歧义等门槛（`external_oscillation_tracker.py` 第 422～505 行）；
11. **把教学示例（A/B 段 95% 检出率、`4,0.066667,,,,False`）当成真实数据。** 真实数据要看第 16 节的统计与原始文件；
12. **把"设计上支持失败处理"说成"实测验证过失败处理"。** 两份真实 CSV 都没有失败帧——这是本课最重要的证据边界。
