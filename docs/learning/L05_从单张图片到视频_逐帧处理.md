## 2. 视频与 Frame

本节课的两个基础概念（课堂上给出的原话）：

> **视频可以理解成按时间顺序排列的一系列静态图片。**
>
> **每一帧是一个 Frame。**

换句话说：

- 视频本身不是一个"新的数据种类"，它是**帧的序列**；
- Frame（帧）是一张**实际存在的图片**——在本项目里就是一个 BGR NumPy 数组，有高度、宽度、3 个颜色通道，可以像 L02～L04 学过的任何单张图片一样被处理；
- 视频的"时间"来自两帧之间的先后顺序和帧率（下一节），而不是来自某一张图内部。

把"视频"和"Frame"放在一起对比：

| 对比项 | 视频（Video） | 帧（Frame） |
| --- | --- | --- |
| 是什么 | 按时间顺序排列的一系列静态图片 | 其中的一张静态图片 |
| 数据形态 | 帧序列（加上帧率等元数据） | BGR NumPy 数组（高度 × 宽度 × 3） |
| 数量关系 | 一个视频包含很多帧 | 一帧只是视频中的一个瞬间 |
| 能否直接检测 | 不能，检测函数只接受"一张图片" | 可以，直接交给 `detect_marker()`（`track_video()`，当前约第 491 行） |
| 时间含义 | 由帧序与帧率共同表达 | 单独一帧是"某个时刻的一张画面"，本身不含时间长度 |

由此得到一个贯穿全节的结论：

> 处理视频 = 对每一帧重复做"单张图片能做的一切"。

需要特别强调的一点：

> 视频不是"一张巨大图片"。不存在"把整个视频铺开来当一张图检测"这种操作；
> 计算机逐帧处理视频——**一次拿一帧 → 处理 → 换下一帧**。

## 3. FPS 与时间采样

**FPS 表示每秒多少帧**（frames per second，帧率）。

把 fps 换算成时间，就得到相邻两帧之间的间隔：

```text
相邻帧间隔 = 1 / fps

30 fps 时：1 / 30 s ≈ 0.033333 s
```

也就是说，该示例视频（30 fps）的两帧之间相隔约 0.033333 秒；计算机在这两帧之间的"中间时刻"**没有任何记录**——视频数据是**离散采样**的，时间分辨率就是 1/fps（约 0.033333 s）。

项目源码里，帧号与时间的换算写在逐帧循环中：

```python
# track_video() 主循环内（当前约第 494 行）
time_s = frame_index / fps
```

配合 `frame_index = 0`（当前约第 481 行，帧号从 0 开始），可以算出一张时间对照表：

| frame_index | time_s（30 fps 时） |
| --- | --- |
| 0（第一帧） | 0.000000 s |
| 1 | ≈ 0.033333 s |
| 30 | ≈ 1.000000 s |
| 60 | ≈ 2.000000 s |

两个必须记住的细节：

1. **fps 不是写死在代码里的**：它在 `open_video()` 中从当前视频文件读取（`float(cap.get(cv2.CAP_PROP_FPS))`，当前约第 130 行），`print_video_info()` 打印时也特别注明"从当前视频文件读取，未硬编码"（当前约第 153 行）；
2. **fps 也要做有效性检查**：`track_video()` 读取 fps 后，如果 `fps <= 0` 就直接报错并停止处理（当前约第 437～441 行）——因为 fps 是 `time_s` 的分母，非法 fps 会让整条时间轴失去意义。

一句话总结本节：

> FPS 决定相邻帧的时间间隔，也决定时间轴的分辨率；`time_s = frame_index / fps` 把"第几帧"翻译成"第几秒"。

### 4.1 源码定位

### 4.2 真实代码

```python
# 当前约第 119 行：函数定义
def open_video(video_path):
    # 当前约第 125 行：创建视频读取对象
    cap = cv2.VideoCapture(str(video_path))
    # 当前约第 126～127 行：打开失败时明确返回 (None, None)
    if not cap.isOpened():
        return None, None

    video_info = {}
    # 当前约第 130～131 行：读取 fps 与总帧数
    video_info["fps"] = float(cap.get(cv2.CAP_PROP_FPS))
    video_info["frame_count"] = int(round(cap.get(cv2.CAP_PROP_FRAME_COUNT)))
    ...
    return cap, video_info
```

### 4.3 输入、处理、输出、去向

| 环节 | 内容 |
| --- | --- |
| 输入 | 视频文件路径 `video_path`（先转成 `str` 再交给 OpenCV） |
| 处理 | 用 `cv2.VideoCapture` 打开视频文件；用 `cap.get()` 读取 fps、总帧数、旋转元数据；尝试开启自动方向处理（`enable_orientation_auto(cap)`，当前约第 140 行） |
| 输出 | `(cap, video_info)`：`cap` 是视频读取对象，`video_info` 是信息字典 |
| 失败时 | `return None, None`（当前约第 127 行），由上层 `track_video()` 判断并终止（当前约第 433～435 行） |
| 去向 | `cap` 交给后续的 `cap.read()`（当前约第 444、527 行）使用；`video_info` 供打印信息（当前约第 450 行）与主循环使用（当前约第 437 行取 fps） |

### 4.4 VideoCapture 是什么

> **VideoCapture 是从视频文件中读取帧的对象。**

它记住"读到哪儿了"这一状态：每调用一次 `cap.read()`，读取位置就前进一帧。所以对同一个 `cap` 连续调用 `cap.read()`，拿到的就是依次排列的每一帧（顺序读取）。

`cap.get()` 可以读取视频属性，本节代码里出现的属性：

| 属性 | 含义 | 源码位置 |
| --- | --- | --- |
| `cv2.CAP_PROP_FPS` | 帧率（每秒帧数） | 当前约第 130 行 |
| `cv2.CAP_PROP_FRAME_COUNT` | 文件声明的总帧数 | 当前约第 131 行 |
| `cv2.CAP_PROP_ORIENTATION_META` | 文件内记录的旋转元数据（只读，用于报告） | 当前约第 134～137 行 |
| `cv2.CAP_PROP_POS_FRAMES` | 当前读取位置（PNG 回退方案中用 `cap.set` 跳帧） | `read_frame_at()`，当前约第 309 行 |

### 4.5 三个容易忽略的细节

1. **路径先转字符串**：`cv2.VideoCapture(str(video_path))`（当前约第 125 行）——项目路径含中文，代码统一先转成 `str` 再交给 OpenCV；
2. **打开失败要"明确失败"**：`if not cap.isOpened(): return None, None`（当前约第 126～127 行）。注意此时 `cap` 对象仍然存在，但项目选择直接返回失败，不继续往下走；
3. **fps 的合法性在上层检查**：`track_video()` 中 `fps <= 0` 时 `cap.release()` 后返回 `None`（当前约第 438～441 行）——资源要在失败路径上也被释放。

### 5.3 ret 与 frame 的分工

`cap.read()` 返回**两个值**，必须分开理解：

| 返回值 | 类型 | 含义 | 项目里怎么用 |
| --- | --- | --- | --- |
| `ret` | 布尔值 | **是否成功读取**这一帧 | 当前约第 445 行、第 528 行用它判断"读到了吗" |
| `frame` | NumPy 数组或 `None` | **当前一张图像**（BGR NumPy 数组） | 当前约第 444 行存为 `first_frame`、第 527 行存为 `next_frame`，最终交给 `detect_marker()`（当前约第 491 行）检测 |

一句话：

> `ret` 回答"这一帧读到了没有"，`frame` 才是"读到的那张图片"。

### 5.4 为什么第一帧要单独读一次

`track_video()` 开始的注释（当前约第 443～444 行）写得很清楚：**先读第一帧，用于确定程序实际处理的画面尺寸（以及叠加视频尺寸）**。

具体去向：

- 当前约第 450 行：`print_video_info(...)` 打印"程序实际处理的画面尺寸"；
- 当前约第 452～453 行：从 `first_frame.shape` 取出高度与宽度；
- 当前约第 456～463 行：按 0.5 倍（`OVERLAY_SCALE`，第 44 行）算出叠加视频尺寸并取偶数（避免编码器报错）；
- 当前约第 480 行：`current_frame = first_frame`——第一帧读出来后直接进入循环被处理，**不会浪费这一帧**。

### 5.5 读取位置会前进

`cap` 内部记录读取位置：每调用一次 `cap.read()`，位置前进一帧。因此：

- 当前约第 444 行读走第 0 帧（`first_frame`）；
- 循环第一次执行时处理的就是第 0 帧；
- 当前约第 527 行读回第 1 帧（`next_frame`），第 531～532 行把它更新为新的 `current_frame`；
- 以此类推，直到 `cap.read()` 读不到为止。

补充：PNG 回退方案里也有一次 `cap.read()`（`read_frame_at()` 内，当前约第 310 行），但那是先把位置 `cap.set(cv2.CAP_PROP_POS_FRAMES, frame_index)`（当前约第 309 行）跳过去、再读一帧——属于回退路径，不属于主循环。

| --- | --- |
| 输入 | 已打开的视频读取对象 `cap` |
| 处理 | 从当前读取位置解码一帧，位置前进一帧 |
| 输出 | `(ret, frame)` / `(ret, next_frame)` |

## 6. current_frame

### 6.1 源码定位与真实代码

```python
# 当前约第 480～481 行：初始化
current_frame = first_frame
frame_index = 0

# 当前约第 531～532 行：循环末尾更新
frame_index += 1
current_frame = next_frame
```

### 6.2 current_frame 是什么

> **current_frame 表示当前正在处理的那一帧。**

它有明确的"一生"：

| 时刻 | 源码位置 | current_frame 的值 |
| --- | --- | --- |
| 循环开始前 | 当前约第 480 行 | `first_frame`（第 0 帧，第一帧被单独读出来的那张） |
| 每轮循环中 | 当前约第 491、513～521 行 | 就是"这一轮要检测、要画框"的那一帧 |
| 每轮循环末尾 | 当前约第 532 行 | 被替换成 `next_frame`（新读到的下一帧） |
| 直到视频结束 | 当前约第 528～530 行 | 不再更新，循环退出 |

### 6.3 它不是什么

- **它不是整个视频**：current_frame 只是"一张图片"，视频是"很多张这样的图片按顺序排起来"；
- **它不是检测结果**：检测结果是 `detect_marker(current_frame)` 的返回值（当前约第 491 行 `result`）；
- **它不会带着历史**：每次被整体替换（当前约第 532 行），上一帧的内容不留在 current_frame 里——上一帧的检测结果是通过 CSV 与 `records`（当前约第 499～510 行）另外"记账"保存的。

### 6.4 frame_index 与 current_frame 是一对搭档

- `frame_index`：这是**第几帧**（编号，从 0 开始，当前约第 481 行初始化、第 531 行递增）；
- `current_frame`：这是**那一帧的画面**（图像数据）。

主循环里每一轮检测、记录、划线，用的都是"`frame_index` 号的那张 `current_frame`"。两者同步更新（当前约第 531～532 行紧挨着），这保证了：**CSV 里第几行、叠加视频里的帧号、以及被检测的那张图，三者始终对得上。**

## 8. 单图检测如何升级成视频检测

### 8.1 两种流程对照

| 对比项 | 单张图片检测（L02～L04） | 视频逐帧追踪（本节） |
| --- | --- | --- |
| 输入 | 一张图片 | 一个视频文件（很多帧） |
| 检测调用 | `detect_marker(image)` 一次 | `detect_marker(current_frame)` 每帧一次（当前约第 491 行） |
| 检测函数本身 | `src\marker_detector.py` | **完全相同，没有重写** |
| 时间信息 | 无（只有这一瞬间的一张图） | `time_s = frame_index / fps`（当前约第 494 行） |
| 结果形式 | 一次性结果（如单图 demo） | 每帧一行 CSV（当前约第 497 行），例如 100 帧就是 100 行 |
| 循环控制 | 无 | `while True` + `cap.read()` + 结束判断（当前约第 489、527～530 行） |
| 可视化 | 单张 overlay 图 | Overlay Video（当前约第 513～521 行） |
| 资源管理 | 基本一次性使用 | `try / finally` + `release()`（当前约第 540～544 行） |

### 8.2 "升级"涉及的只有三件外围的事

1. **循环**：对每一帧重复调用同一个检测函数（当前约第 489、491 行）；
2. **记账**：给每一帧的结果标上帧号与时间并写进 CSV（当前约第 494、497 行）；
3. **收尾**：读完 → 判断结束 → 释放资源（当前约第 527～530、540～544 行）。

检测算法、颜色阈值、轮廓与质心计算（L02～L04 的内容）**没有任何变化**——这正是"函数复用"的直接体现。

### 8.3 必须强调

> 视频处理不是"换了一种新算法"，而是"给同一个函数加了一圈循环、一支笔（CSV）和一套收尾流程"。

## 9. marker_detector 与 video_tracker 的分工

### 9.1 分工表

| 对比项 | `src\marker_detector.py` | `src\video_tracker.py` |
| --- | --- | --- |
| 负责回答 | "**这一张图片里目标在哪里。**" | "**视频什么时候读哪一帧、如何循环、如何记录结果、如何输出。**" |
| 工作层次 | 单张图片内部（像素 → Mask → 轮廓 → 质心） | 帧与帧之间（序列、时间、输出） |
| 输入 | 一张图片（BGR 数组） | 一个视频文件路径（加输出路径） |
| 输出 | 结果字典（`success / cx / cy / area / bbox / ...`） | CSV 文件、叠加视频、统计字典 |
| 是否管时间 | 不管（它对"第几帧、第几秒"一无所知） | 管（当前约第 494 行 `time_s = frame_index / fps`） |
| 是否管文件读写 | 不管 | 管（打开视频、写 CSV、写叠加视频） |

一句话对照：

> `marker_detector.py` 是"眼睛"，回答"目标在哪里"；`video_tracker.py` 是"导演"，决定"什么时候看哪一帧、看的结果记到哪儿、给谁看"。

### 9.2 真实调用

```python
# src\video_tracker.py 第 34 行：模块导入（分工的入口）
from src.marker_detector import detect_marker

# src\video_tracker.py::track_video()：主循环内逐帧调用（当前约第 491 行）
result = detect_marker(current_frame)
```

### 9.3 这是一种模块化设计

`video_tracker.py` 的文件头说明（第 15～23 行）明确写着：本模块**只做"测量与记录"**；检测参数的唯一来源是 `src\marker_detector.py`，本模块不重新定义 `RED_LOWER_1` / `RED_UPPER_1` / `RED_LOWER_2` / `RED_UPPER_2` / `MORPH_KERNEL_SIZE` / `MIN_AREA`（第 19～21 行）。

这就是**模块化设计**的体现：

1. **每个模块可以被单独理解和检查**：检测规则在 `marker_detector.py`，视频流程在 `video_tracker.py`；
2. **改动影响范围小**：调整颜色参数不需要动视频循环；调整叠加视频画法不需要动检测逻辑；
3. **边界清晰**：`video_tracker` 不"重新发明"目标检测算法，它只是调用者。

### 9.4 函数复用的证据

同一个 `detect_marker()` 被两个不同场景直接使用：

| 使用场景 | 调用位置 | 调用方式 |
| --- | --- | --- |
| 单张图片检测（M2） | `demo\run_single_image_detection.py` 第 115 行 | `result = detect_marker(image)` |
| 视频逐帧追踪（M3，本节主角） | `src\video_tracker.py::track_video()`（当前约第 491 行） | `result = detect_marker(current_frame)` |
| 视频回退方案取代表性帧 | `src\video_tracker.py::save_fallback_frames()`（当前约第 371 行） | `result = detect_marker(frame)` |

**同一段检测函数、三种调用场景**——这就是"函数复用"（Function Reuse）：写一次、测一次、被多处直接调用，而不是在每个新场景里复制粘贴一套检测逻辑。

## 10. 视频结束

### 10.1 源码定位与真实代码

```python
# 当前约第 527～530 行
ret, next_frame = cap.read()
if not ret or next_frame is None:
    # 视频解码结束（ret=False）：正常结束，不因为单帧失败中断
    break
```

### 10.2 循环结束的几种情形

| 情形 | 触发位置 | 代码表现 | 性质 |
| --- | --- | --- | --- |
| 解码到文件末尾 | 当前约第 527～530 行 | `ret=False`（或 `next_frame is None`）→ `break` | **正常结束**，最后一帧已经处理完 |
| 用户按 Ctrl+C | 当前约第 536～539 行 | `except KeyboardInterrupt`，标记 `interrupted=True` | 人为中断；已完成的数据保留 |
| 其他异常 | 当前约第 540～544 行 | `finally` 清理后异常继续向上抛出 | 异常路径；资源仍被释放 |

### 10.3 为什么这个顺序能处理最后一帧

本项目采用的循环节奏是：

> **处理当前帧 → 读取下一帧 → 判断是否结束**

用 3 帧的小视频（帧 0、1、2）演示一遍：

| 轮次 | current_frame | 这一轮做了什么 | 读完 next_frame 后 |
| --- | --- | --- | --- |
| 第 1 轮 | 帧 0 | 检测帧 0、写第 0 帧结果 | 读到帧 1，继续 |
| 第 2 轮 | 帧 1 | 检测帧 1、写第 1 帧结果 | 读到帧 2，继续 |
| 第 3 轮 | 帧 2 | **检测帧 2、写第 2 帧结果** | 读不到（ret=False）→ break |

可见最后一帧在 `break` 之前**已经被完整处理**。

反过来，如果写成"先读取下一帧、先判断、再处理"，最后一帧就会在"发现没有下一帧"时被顺手丢掉——这是视频逐帧处理里最典型的少一帧错误。

### 10.4 不要把"视频结束"当成"检测失败"

- 视频结束：整段视频正常读完了，是**序列层面的终止**（当前约第 528～530 行）；
- 检测失败：某一帧还在放，但这一帧没测到目标，是**单帧层面的缺失**（`detected=False`，见第 11 节）。

两者都会在数据里"留下痕迹"，但含义完全不同：前者决定"循环到此为止"，后者只影响"这一行有没有坐标"。

## 11. 检测失败

### 11.1 检测失败在代码里长什么样

某一帧检测失败时：

- `result["success"]` 为 `False`（`detect_marker()` 的失败返回，来自 L02～L04）；
- **坐标不应该伪造**——不能拿上一帧的坐标充数，也不能随手写一个 0；
- 失败时坐标字段**保持为空**。

### 11.2 CSV 中的表现

构造 CSV 行的函数是 `build_csv_row()`（当前约第 393 行定义），表头是第 41 行的：

```text
frame,time_s,x_px,y_px,area_px,detected
```

检测成功与失败两种行的写法：

```python
# 当前约第 402～409 行：成功行（真实数值）
[
    frame_index,
    "%.6f" % time_s,
    "%.2f" % result["cx"],
    "%.2f" % result["cy"],
    "%.1f" % result["area"],
    "True",
]

# 当前约第 410 行：失败行（坐标与面积全部留空）
return [frame_index, "%.6f" % time_s, "", "", "", "False"]
```

对比表：

| 行类型 | `frame` | `time_s` | `x_px` | `y_px` | `area_px` | `detected` |
| --- | --- | --- | --- | --- | --- | --- |
| 检测成功 | 帧号 | 计算值 | `cx`（两位小数） | `cy`（两位小数） | 面积（一位小数） | `True` |
| 检测失败 | 帧号 | 计算值 | **空** | **空** | **空** | `False` |

注意：失败行的 `frame` 与 `time_s` **照常填写**——失败的是"这一帧的检测"，不是"这一帧的存在"。时间轴必须保持连续，否则后续按时间分析就会错位。

### 11.3 项目当前约第 399 行的设计原则

`build_csv_row()` 的文档字符串（当前约第 399 行）原话：

> **失败时绝不写 0 / -1 / nan / 字符串。**

为什么这条原则重要：

- 写 `0`：会被误读成"目标恰好在图像原点"，制造一个不存在的测量；
- 写 `-1`：会被误读成"坐标在图像左侧外面"；
- 写 `nan`：数值计算里会悄悄传播，把统计结果污染成 NaN；
- 写字符串（如 `"None"`、`"failed"`）：破坏列的数据类型，让按列解析数值的下游读取工具出错。

要重点理解的这句话：

> **"测不到，就明确标记缺失，而不是制造一个假测量。"**

`detected=False` + 坐标留空，就是"明确标记缺失"的标准做法：既保留了"这一帧存在过"的事实，又诚实地声明"这一次没有测到"。

### 11.4 自检程序也在验证这一点

`check_csv_data()`（当前约第 643 行起）会逐行检查 CSV，其中相关的检查项包括：

- "detected=True 的行 x/y/area 都是合法数值"（当前约第 736 行）；
- "detected=False 的行 x/y/area 全部为空"（当前约第 731～732、737 行）；
- "不存在 x=0, y=0 伪数据"（当前约第 726～727、738 行）；
- "坐标全部落在 ... 显示画面范围内"（当前约第 728～729、739～740 行）。

也就是说，"不伪造坐标"不是一句口号，而是**被自动检查约束的工程规范**。

## 12. VideoWriter 与 Overlay Video

### 12.1 写入器：open_overlay_writer()

```python
# 当前约第 242 行：函数定义
def open_overlay_writer(overlay_path, fps, frame_size):
    ...
    for codec_name in OVERLAY_CODECS:                                    # 当前约第 251 行
        fourcc = cv2.VideoWriter_fourcc(*codec_name)                     # 当前约第 252 行
        writer = cv2.VideoWriter(str(overlay_path), fourcc, fps, (width, height))  # 当前约第 253 行
```

要点：

- **当前约第 252～253 行**是 VideoWriter 的创建处：`fourcc` 是编码器标识，`fps` 与画面尺寸 `(width, height)` 必须和写进去的帧一致；
- 编码器候选写在第 47 行：`OVERLAY_CODECS = ("mp4v", "avc1")`——`mp4v` 在 Windows 上一般可用，`avc1` 作为备选；逐个尝试，成功即返回（当前约第 254～255 行），失败候选立即 `release()`（当前约第 256 行）；
- 所有候选都失败时返回 `(None, None)`，由调用方走 **PNG 回退方案**（当前约第 472 行打印警告；第 548～555 行保存最多 5 张代表性 PNG，`MAX_FALLBACK_PNGS = 5` 见第 50 行）。

### 12.2 主流程里的写入

```python
# 当前约第 513～521 行
scaled_frame = cv2.resize(
    current_frame, (scaled_width, scaled_height),
    interpolation=cv2.INTER_AREA

```

顺序是：**缩放画面 → 画检测结果 → 写入视频**。

配合的参数：

- `OVERLAY_SCALE = 0.5`（第 44 行）：叠加视频按 0.5 倍缩放，减小文件体积（只用于人工核查）；
- 当前约第 455～463 行：缩放后的宽高取偶数（避免编码器对奇数尺寸报错），并算出 `scale_x / scale_y` 供画框坐标换算使用；
- 当前约第 465～467 行：用 `open_overlay_writer(overlay_path, fps, (scaled_width, scaled_height))` 打开写入器——叠加视频与源视频**同一个 fps**。

### 12.3 叠加帧是怎么画的

画框函数是 `draw_tracking_frame()`（当前约第 175 行起）：

- 检测成功：绿色外接矩形 + 中心点（圆圈 + 十字）+ 中心坐标文字（用原视频像素坐标，便于和 CSV 对照）（当前约第 209～237 行）；
- 检测失败：**只显示 "DETECTION FAILED"**，不画任何虚假中心（当前约第 196～207 行）——和第 11 节的"不伪造坐标"是同一条原则在可视化上的体现。

### 12.4 Overlay Video 的用途

叠加视频是给人看的**检查工具**，课堂上明确列出的三个检查问题：

- **检测框有没有跑偏**（框是否一直包住红色标记）；
- **中心点有没有跟着目标**（十字/圆是否落在目标中心附近）；
- **哪些帧检测失败**（出现 "DETECTION FAILED" 的帧）。

它**不是新的测量数据**：正式数据以 CSV 为准；overlay 只是"一眼看出测量可不可信"的辅助手段。

## 13. release 与资源清理

### 13.1 源码定位

主流程的收尾在 `finally` 块里（**当前约第 540～544 行附近**）：

```python
    finally:
        csv_file.close()          # 当前约第 541 行
        cap.release()             # 当前约第 542 行
        if writer is not None:    # 当前约第 543 行
            writer.release()      # 当前约第 544 行
```

### 13.2 try / finally 结构

```text
当前约第 488 行  try:
            ... 逐帧循环（当前约第 489～535 行）...
当前约第 536 行  except KeyboardInterrupt:   # Ctrl+C
            ... 标记 interrupted，提示数据已保留 ...
当前约第 540 行  finally:                    # 无论正常/异常/中断都要执行
            csv_file.close()
            cap.release()
            writer.release()（writer 存在时）
```

`finally` 的含义：**不管 try 里是正常跑完、还是中途抛出异常、还是被 Ctrl+C 打断，这段清理代码都会执行**。这就是"即使中途异常或 Ctrl+C，也尽量完成资源清理"的实现方式。

### 13.3 要释放哪些资源

| 资源 | 打开位置 | 释放位置 | 不释放的后果（直观理解） |
| --- | --- | --- | --- |
| 视频读取器 `cap` | 第 125 行（`cv2.VideoCapture`） | 当前约第 542 行 `cap.release()` | 解码器与文件句柄被占用，Windows 上文件可能无法被其他程序占用/移动 |
| 视频写入器 `writer` | 第 253 行（`cv2.VideoWriter`） | 当前约第 544 行 `writer.release()`（writer 非 None 时） | 输出视频的尾部数据可能没写完，文件不完整 |
| CSV 文件 `csv_file` | 当前约第 483 行 `open(...)` | 当前约第 541 行 `csv_file.close()` | 缓冲区内容未落盘，最后几行可能丢失 |

### 13.4 失败路径上的 release 同样存在

## 16. 本节课最重要的概念

1. **视频 = 按时间顺序排列的一系列静态图片**；每一帧是一个 Frame，帧是实际的图像数组（BGR NumPy 数组），视频不是"一张巨大图片"。
2. **逐帧处理的节奏是"一次拿一帧 → 处理 → 换下一帧"**：处理视频 = 对每一帧重复做单张图片能做的一切。
3. **FPS 决定相邻帧的时间间隔**：30 fps → 1/30 s ≈ 0.033333 s；视频数据是离散采样，时间分辨率 = 1/fps。
4. **`time_s = frame_index / fps`（当前约第 494 行）**：把"第几帧"翻译成"第几秒"；fps 从文件读取、不硬编码（当前约第 130、153 行）。
5. **VideoCapture 是视频的入口**：`cv2.VideoCapture(str(video_path))`（当前约第 125 行）打开视频；`cap.get()` 读 fps / 总帧数（当前约第 130～131 行）；打开失败明确返回 `(None, None)`（当前约第 126～127 行）。
6. **`cap.read()` 返回两个值**：`ret` 是"是否成功读取"，`frame` 才是图像数据；第一帧单独读一次（当前约第 444 行）用于确定画面尺寸，之后每轮读下一帧（当前约第 527 行）。
7. **`current_frame` 是"当前正在处理的那一帧"**（当前约第 480、532 行），不是整个视频；它每轮被下一帧整体替换，历史靠 CSV 与 `records` 记账保留。
8. **逐帧循环的主顺序**：检测（当前约第 491 行）→ 时间（第 494 行）→ 写 CSV（第 497 行）→ 可视化（第 513～521 行）→ 读下一帧（第 527 行）→ 判断结束（第 528～530 行）→ 更新编号与帧（第 531～532 行）。
9. **"单张图片检测升级为视频处理，本质上是把同一个检测函数放进逐帧循环中"**：`detect_marker()` 一行未改，只是被逐帧调用。
10. **模块化分工**：`marker_detector.py` 回答"这一张图片里目标在哪里"；`video_tracker.py` 负责"什么时候读哪一帧、如何循环、如何记录结果、如何输出"；检测参数唯一来源是 `marker_detector.py`（第 19～21 行说明、第 34 行导入、当前约第 491 行调用）。
11. **"处理当前帧 → 读取下一帧 → 判断是否结束"**：这个顺序保证最后一帧也被正常处理；视频结束（`break`）不是错误，是正常出口。
12. **检测失败的正确处理**：`detected=False`、坐标字段留空，绝不写 0 / -1 / nan / 字符串（当前约第 399、410 行）；"测不到，就明确标记缺失，而不是制造一个假测量。"
13. **VideoWriter 生成 Overlay Video**（当前约第 252～253 行创建、第 513～521 行写入，编码器候选 mp4v / avc1）：用途是人工检查检测框有没有跑偏、中心点有没有跟着目标、哪些帧检测失败；写入器不可用时走代表性 PNG 回退（当前约第 548～555 行）。
14. **release 与 try / finally**：`cap.release()`、`writer.release()`、`csv_file.close()` 放在 finally（当前约第 540～544 行）；即使异常或 Ctrl+C 也尽量完成资源清理（当前约第 536～539 行）。

## 17. 易错点

1. **把视频当成"一张巨大图片"。** 视频是帧的序列；处理方式是逐帧，而不是整段一起检测。
2. **把 Frame 当成一个抽象概念。** 每一帧都是一张**实际的图像数组**（BGR NumPy 数组），可以被单图检测函数直接处理。
3. **忽略 FPS 与时间的换算。** FPS 决定相邻帧的时间间隔（30 fps → 约 0.033333 s）；不知道 fps 就没法把帧号翻译成时间。
4. **把 ret 和 frame 混为一谈。** `cap.read()` 返回两个值：`ret` 是成功标志，`frame` 是图像数据；判断"读到了吗"看 ret，检测用 frame。
5. **把 current_frame 当成整个视频。** 它只是"当前正在处理的那一帧"，每轮循环末尾会被替换（当前约第 532 行）。
6. **以为 video_tracker 重新发明了检测算法。** 它不重新定义颜色阈值等检测参数；检测参数的唯一来源是 `src\marker_detector.py`（第 19～21 行说明）。
7. **把 marker_detector 和 video_tracker 的职责搞混。** 一个回答"这一张图里目标在哪里"，另一个负责"读帧、循环、记录、输出"。
8. **检测失败时伪造坐标。** 失败必须 `detected=False` 且坐标留空；绝不写 0 / -1 / nan / 字符串（当前约第 399、410 行）。
9. **把 VideoWriter 当成"读取视频"的工具。** 读视频用 VideoCapture（当前约第 125 行），写输出视频用 VideoWriter（当前约第 253 行），方向相反。
10. **用完视频资源不 release。** `cap.release()` 与 `writer.release()`（当前约第 540～544 行 finally）必须配对出现；否则输出文件可能不完整、资源被占用。
11. **循环顺序写反导致丢最后一帧。** 本项目的顺序是"处理当前帧 → 读取下一帧 → 判断是否结束"（当前约第 491、497、527～530 行），保证最后一帧被处理。
12. **把"视频结束"当成"检测失败"。** 视频结束是序列层面的正常终止（`break`）；检测失败是单帧层面的缺失（`detected=False`），两者含义完全不同。
