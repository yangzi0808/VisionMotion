## 0. 项目背景

### 0.1 为什么做这个项目

项目的出发点在 `README.md` §2 里写得很直接，是四个问题：

1. 普通摄像头的视频里，能否提取出**可重复**的运动位置特征？
2. 如何从像素位置序列中测量出振动的**周期与频率**？
3. 如何用独立的频域方法（FFT）对时域测量做**交叉验证**？
4. 如何把视觉测量结果与基础物理模型（质量—弹簧简谐振动）联系起来，并**诚实说明差异与证据边界**？

把这四个问题合起来看，这个项目的真实动机不是"做一个位移测量仪"，而是**验证一条低成本的视觉测量链路是否成立，并且把这条链路上每一步都讲清楚**。

### 0.2 项目目标

`PROJECT_SPEC.md` §1 给出的总目标是：

> 用低成本的非接触方式测量简单机械目标的位移与振动：用普通手机/电脑摄像头拍摄目标运动视频，用计算机视觉方法把视频中的像素位置变化换算成实际位移，并进一步得到振动周期、频率和状态判断结果。

第一版具体目标 5 条（原文列出）：稳定提取标记中心位置；像素坐标换算成毫米；输出位移-时间曲线并读出周期与频率；用简单阈值给出"正常 / 异常"状态判断；**代码简单、步骤清晰，作者能逐行解释每个环节在做什么**。

同样重要的是"非目标"（`PROJECT_SPEC.md` §1）：

- 不追求计量级精度，不追求亚像素、微米级测量；
- 不做实时在线处理，不做三维、多相机测量；
- 不追求对任意目标、任意背景的通用识别能力，只针对事先设计好的目标标记。

### 0.3 初始设想

初始设想是一条**单向、串行、每步只做一件事**的流水线（`PROJECT_SPEC.md` §6，共 12 步）：

```
采集 → 读取 → 预处理 → 目标标记检测 → 中心提取 → 标定
     → 位移计算 → 曲线绘制 → 峰值检测 → 周期与频率 → 状态判断 → 结果输出与记录
```

这条设想后来基本被完整执行了，但中途发生了两次重要偏移，都记录在本报告里：

1. **M5 的动态实验**发现"单方向位移"在实际拍摄几何下必须先沿标定方向投影，否则会把垂直方向的抖动混进位移（见第五阶段）；
2. **M6 引入外部公开视频**后，原设想中"红色标记 + 阈值状态判断"的路线无法直接套用，最终改为"暗带上缘 y₀ + 周期/频率 + 有限的物理对照"，并把"状态判断"从交付目标中退出（见第四、六阶段与第七阶段问题 4）。

### 0.4 最初技术路线与它自己的"负面清单"

最初技术路线就是上面那 12 步，工具只有三个：OpenCV（读视频、预处理、阈值分割、轮廓检测）、NumPy（数组运算与统计）、Matplotlib（绘图）。

真正体现工程判断力的是 `PROJECT_SPEC.md` §5 的**禁止技术清单**，原文列出：

> YOLO、PyTorch、TensorFlow、深度学习 / 神经网络、Kalman 滤波、DIC 完整算法、有限元 / COMSOL、复杂振动理论、复杂信号处理（多级滤波、时频分析等）、复杂优化算法、任何没有明确必要性的第三方框架

理由原文写的是：

> 原因：这些方法对本阶段的精度提升有限，但会显著增加理解与调试成本。

同一节还列了"第一版不做的事情"：实时视频流与在线处理、多相机 / 三维重建 / 二维全场测量、任意目标任意背景识别、相机畸变校正 / 亚像素定位 / 运动模糊复原、图形界面（GUI）。

### 0.6 为什么选择这个难度

项目的难度定位写在 `README.md` §1：

> 本项目**不使用深度学习或复杂跟踪算法**，重点在于：整条测量链路能够跑通、每一步都能解释清楚、结果可以复现。

也就是说，这个项目主动放弃了"算法先进性"这条评价轴，换成了三条可交付的标准：**能跑通、能解释、能复现**。

这不是自我安慰式的降级，而是一个具体的工程取舍：在只有 5 天可用时间（2026-09-22 至 2026-09-26，依据 Git 提交时间）、没有硬件、没有数据集的条件下，把"链路完整 + 记录完整 + 边界诚实"做到位，比做出一个说不清楚的复杂模型更接近"科研训练"的目的。

后续事实也证明这条难度的选择是对的：项目真正花时间的地方，**不是写检测算法**（`src/marker_detector.py` 只有 151 行），而是标定几何、有效帧门限、时间轴正确性、特征选择与不确定度边界这些"看起来不高级、但决定结论对不对"的问题。

### 1.1 为什么采用这种目录结构

目录结构不是随手建的，它对应两种不同的"数据生命周期"：

- **不可再生的原始素材**（`data/raw/`）与**可再生的中间数据**（`data/processed/`）分开：原始视频一旦被程序改写就无法回溯，所以放单独目录，并在 `.gitignore` 中排除大文件，只提交 `.gitkeep`；
- **结果**（`results/`）与**代码**（`src/`）分开：任何一张图、任何一个 CSV 都能单独删除后重跑再生，而不会影响代码；
- `tests/`、`demo/`、`docs/` 各自独立：测试脚本、演示入口、报告素材互不混放，避免"演示脚本里藏着测量逻辑"。

这套结构在后续阶段确实起了作用：M6.2 的 `src/external_oscillation_tracker.py` 在运行前后都会比对原始视频的 SHA-256（见第四阶段），如果原始素材和结果混在一个目录里，这种校验就无从谈起。

### 1.2 Git 初始化过程与第一次提交的内容

Git 仓库的第一次提交只包含**文档、配置与空占位文件**，`src/` 下一个 `.py` 文件都没有。`CHANGELOG.md` 在"未发布"区块里对此的说明是：

> 当前只有文档与配置，`src/` 下尚无任何业务代码

这次提交里同时写入了三条后来的"项目纪律"，它们贯穿整个项目：

1. `CHANGELOG.md` 规定：每次改动都要记"做了什么、为什么做、影响了哪些文件"，并给出 `v0.x.y` / `v1.0.0` 的版本号规则；
2. `EXPERIMENT_PROTOCOL.md` 规定：每次拍摄、每组数据单独填一份记录，做到"任何一个结果都能回溯到当时的拍摄条件"；
3. `.gitignore` 排除虚拟环境、Python 缓存、临时文件与大型视频。

### 1.3 遇到的问题

| 问题 | 当时的处理 | 后果 |
| --- | --- | --- |
| 没有业务代码，无法验证目录结构是否合理 | 先按流水线各步骤建目录，用 `PROJECT_SPEC.md` 的功能清单反向约束目录 | 目录结构在整个项目期间没有被重构过 |

## 2.1 PROJECT_SPEC 是如何形成的

`PROJECT_SPEC.md` 的结构本身就说明了它的形成逻辑——它先写"不做什么"，再写"做什么"：

1. §1 总目标 + 第一版具体目标 5 条 + 非目标 3 条；
2. §2 输入（视频、拍摄参数、标定信息、标记说明、实验记录）+ 对视频的 5 条前提假设（机位固定、运动平面与光轴垂直、光照稳定、参考物同平面、避免运动模糊）；
3. §3 输出 8 项（中心位置序列、标定系数、位移序列、CSV、曲线图、周期与频率、状态判断、结果说明）；
4. §4 功能与完成标准 10 项，每项都要求"输入明确、输出明确、出错时有能看懂的错误提示"；
5. §5 禁止技术清单与不做的事情；
6. §6 12 步技术路线 + 关键假设与误差来源；
7. §7 未来可扩展方向（亚像素、畸变校正、抗抖动、FFT、二维轨迹、自动标定、多目标、对比验证、批量处理与界面、拍摄条件对比实验）。

值得注意的是 §7 里已经写下"**频谱分析：用 FFT 求主频，作为峰值检测的交叉验证**"——在项目第一天，FFT 就被定义为"交叉验证"而不是"主结果"，这个定性一直保留到了 M6.3。

## 2.3 当时的候选方案（A / B / C）

必须先声明：**`PROJECT_SPEC.md` 中没有以"方案 A / B / C"命名的对照表，也没有保存逐条权衡的文字记录。**下面三个方案是依据该文档的禁止技术清单、功能清单与最终代码路径**重建**的对照，用于说明取舍关系；其中"为什么最后选择当前方案"的理由，全部能追溯到文档原文或代码注释。

**方案 A：深度学习检测 / 跟踪路线**

用 YOLO 之类的学习类检测器做目标检测，必要时加 Kalman 滤波做时序跟踪，再跑完整测量链路。

- 需要：带标注的数据集或大量标注工时、GPU、模型调参、可解释性说明成本；
- 收益：对任意目标、任意背景的泛化能力；
- 与本项目的冲突：本项目的目标是"事先设计好的标记"，泛化能力用不上；而"作者能逐行解释每个环节"是硬指标，学习类方法直接违背这一条。

**方案 B：传统 CV + 完整测量系统路线**

传统阈值分割 + 轮廓检测做检测，但同时上相机畸变校正、亚像素定位、多相机/二维全场、实时处理、GUI。

- 需要：标定板、硬件、更多开发时间；
- 问题：`PROJECT_SPEC.md` §5 明确列出"相机畸变校正、亚像素定位、运动模糊复原"与"图形界面（GUI）"为第一版不做；§1 明确"不追求计量级精度"。

**方案 C：可解释的最小链路 + 单点验证路线（最终选择）**

固定机位、单相机、单方向、传统 CV 检测、两点标定、位移序列、峰值检测求周期频率、FFT 交叉验证、最后与基础物理模型做条件性对照；每一阶段先冻结规则、再写代码、再人工验收。

- 只依赖 OpenCV / NumPy / Matplotlib 三个库；
- 每一步都有可复现的数值自检或人工核查手段（掩膜图、标注图、叠加视频、联系表、哈希校验）；
- 出错的代价低、定位快——这正是后面遇到"中文路径""竖屏视频""fps 误用""面积误锁"等问题时能逐个解决的前提。

## M2.2 算法设计

**输入**：M2.1 的图像分析结论（红色目标、浅色瓷砖背景、环境光、有明显阴影）。

### 为什么用 HSV 颜色空间而不是 RGB

项目文件没有保存当时逐条比较 RGB 与 HSV 的文字，但可以从代码与实现结果反推选择理由，并说明 RGB 路线在本图上的具体困难：

1. **RGB 三通道与"颜色"不是线性对应**：在 OpenCV 中 RGB/BGR 三通道都要同时给上下限，一个颜色要在三维立方体里框，参数互相耦合；而 HSV 把"是什么颜色"（H）与"多鲜艳"（S）、"多亮"（V）分开，红色只需要在 H 上取区间。
2. **本图的光照不均匀**：画面中有明显阴影与瓷砖缝的明暗起伏。阴影改变的是 V（亮度）甚至 S（饱和度），但基本不改变 H（色相）。用 HSV 可以让 H 的判断对阴影更稳，而用 RGB 必须为亮部和暗部分别调参数。
3. **实现代价**：`cv2.cvtColor(image, cv2.COLOR_BGR2HSV)` 是一行代码，转换后仍是三个 0–255 的通道，不引入额外依赖。

### 为什么用 H ∈ [0,10] 与 H ∈ [170,179] 两段

这是 HSV 的一个基本性质，也是本项目在文档里明确写出的一条规则（`CHANGELOG.md` v0.2.0 与 `README.md` 的运行说明均有对应描述）：

- OpenCV 的 H 取值范围是 0–179；
- 红色位于色相环的"两端"：靠近 0 的一侧是偏橙的红，靠近 179 的一侧是偏紫的红；
- 因此单段 `inRange` 无法覆盖全部红色，必须取两段掩膜再按位或合并。

代码中的具体参数（`src/marker_detector.py`，本项目检测参数的唯一来源）：

```python
RED_LOWER_1 = np.array([0, 100, 70]);   RED_UPPER_1 = np.array([10, 255, 255])
RED_LOWER_2 = np.array([170, 100, 70]); RED_UPPER_2 = np.array([179, 255, 255])
MORPH_KERNEL_SIZE = 3
MIN_AREA = 200
```

两个区间的 S 下限 100、V 下限 70 是"饱和度/亮度门限"：饱和度用来把彩色目标与接近灰白的瓷砖地面分开，亮度门限用来排除过暗的阴影区。

### 为什么加入形态学处理

代码对形态学的处理非常克制：只做一次 **3×3 开运算**（`MORPH_OPEN`），注释原文是"先腐蚀再膨胀，去掉零散噪点但保留主体形状"。

选择开运算而不是闭运算，是本项目一次真实的工程修正——**被隔离的早期实现用的是 5×5 高斯模糊 + 9×9 闭运算**（`VisionMotion_M2.2_quarantine/src/marker_detector.py`，参数 `blur_ksize=5`、`morph_ksize=9`、`sat_min=90`、`val_min=60`），闭运算会把被高光切碎的红色区域"粘"到一起，同时也会把附近的小红点并入目标。该版本在同一张图上给出的检测结果是：

```
frame,time_s,x_px,y_px,area_px,found
0,0.0000,518.689,966.605,2149.000,1
```

即中心 (518.689, 966.605)、面积 2149 px²。而最终 M2.3 版本在同一张图上的结果是中心 (512.7, 964.5)、面积 1278.5 px²、外接矩形 (494, 940, 37, 51)。两次的中心相差约 6 px，面积相差约 68%。

**必须如实说明**：项目文件中**没有保存**"为什么把早期实现隔离"的文字说明。可核实的客观差异是：早期版本是"配置文件 + 视频 IO + 追踪模块 + 检测模块 + 自检脚本"的多模块结构（`src/config.py`、`src/video_io.py`、`src/track_marker.py`、`src/marker_detector.py`、`tests/check_basic.py`、`demo/run_track.py`，并用 `argparse` 支持命令行参数覆盖），而正式版本收敛为"一个 151 行的检测模块 + 一个无参数的 demo 脚本"，形态学从"闭运算补洞"改为"开运算去噪"，参数集中在一个文件里。隔离目录的命名（`M2.2_quarantine`）本身表明这是一次**主动隔离而非直接删除**的处理，位于仓库之外，未进入任何提交。

还有一处可以核实的细节：隔离目录里**同时存在两套参数定义**——`src/config.py` 里写着另一套默认值（S ≥ 100、V ≥ 80、`MARKER_MIN_AREA = 80`、5×5 形态学核），而 `src/marker_detector.py` 的 dataclass 默认值是 S ≥ 90、V ≥ 60、5×5 模糊、9×9 闭运算、`min_area = 200`。本次复核实测确认：`src/config.py` **没有被任何脚本 import**（`demo/run_track.py` 只从 `src.marker_detector`、`src.track_marker`、`src.video_io` 导入），也就是说早期设计里存在一套"写了但没用上"的参数源。与之对照，最终实现把参数收敛成单文件顶部的 4 个常量，并被后续所有阶段当作唯一来源——这正是"参数单一来源"这条纪律的由来。

### 为什么选择最大轮廓

`find_target_contour()` 的逻辑是：`RETR_EXTERNAL` 取外部轮廓 → 按面积从大到小排序 → 取最大者 → 若面积小于 `MIN_AREA = 200` 则返回 `None`。

理由在代码注释中写明："画面里最像目标标记的那个"。这个策略成立的前提是**目标标记在画面里是最大的红色区域**，而这一前提在 M4 的静态实验里被打破过（见第七阶段问题 6：`EXP-003-STATIC-001` 的最大检测面积达到 301,628.5 px²，说明画面里出现了远大于标记的红色区域），这是后话。

### 为什么用轮廓矩算质心，而不是外接矩形中心

`calculate_centroid()` 用 `cv2.moments`，公式为 `cx = m10/m00`、`cy = m01/m00`，并在 `m00 == 0` 时返回 `None`。被隔离的早期实现里写下了这条理由："用轮廓矩算质心（比外接矩形中心更稳，因为标记边缘不一定对称）"——而本项目 M2.1 的图片里，红色目标恰恰是**外形不规则**的，这条理由在这张图上直接成立。

### 为什么不用深度学习模型

对 M2 这个具体任务，不用深度学习有四个可核实的理由：

1. 任务是**单目标、固定外观、固定场景**：只需要在一张已知布局的图里找到红色区域，学习类检测器的泛化能力在这里没有用武之地；
2. **没有标注数据**：训练一个检测器需要标注框，而项目里只有 1 张静态图；
3. **不需要 GPU 与额外依赖**：`requirements.txt` 全程只有 opencv-python / numpy / matplotlib 三项，未引入任何深度学习框架；
4. **可解释性要求**：检测结果必须能用"掩膜图 + 标注图"两张图解释清楚（`PROJECT_SPEC.md` §4 功能 2 要求"能输出二值掩膜图便于检查"），这是阈值法天然具备、学习类方法不具备的优势。

## 5.1 当时的候选方案（A / B / C / D）

先声明证据边界：**`PROJECT_SPEC.md` 与 `CHANGELOG.md` 中没有保存标定方案的 A/B/C/D 对照评估文字。** 下面的四个方案依据 `PROJECT_SPEC.md` 的技术边界与最终代码实现重建，其中"为什么最终选择 C"的理由可以直接追溯到代码与文档：

**方案 A：单尺度（single scale）**

只算一个标量 k（px/mm），把二维位移整体乘一个系数。

- 优点：最简单，只要一段已知长度；
- 致命问题：它隐含假设"目标的运动方向与图像坐标轴平行"。而 M4 的标定实测给出 `u = (0.999976, -0.006894)`、M5 给出 `u = (0.999992, -0.003913)`——直尺在画面里都有轻微倾斜，`uy` 虽小但不为 0。纯标量 k 会把垂直于运动方向的抖动也算进位移。

**方案 B：横纵分别标定（separate x/y scale）**

分别标定 x 方向与 y 方向的 px/mm，位移按两个分量各自换算。

- 问题一：需要画面里同时存在水平与垂直两个方向的已知长度参考。M2.1 的图片里直尺是竖直的，M4/M5 的视频里直尺是水平的，**没有任何一次拍摄同时提供了两个正交方向的参考**；
- 问题二：横纵分别标定仍然假设"运动恰好沿 x 或 y 轴"，遇到倾斜的物理方向时需要在两个标定值之间做插值，反而把问题复杂化。

**方案 C：沿物理方向投影（projection onto the physical direction）— 最终选择**

用两个已知刻线点 P1、P2 同时定出**尺度 k** 与**单位方向向量 u**，然后把每一帧的目标中心投影到 u 上，得到一维坐标 s，再算位移。

- 只需要两个点、一段已知长度；
- 直接处理"直尺在画面中轻微倾斜"这个真实情况；
- 只保留沿物理运动方向的位移，垂直方向的抖动自然被投影剔除。

**方案 D：单应性校正（homography）**

用 4 个以上共面点求单应矩阵 H，把画面校正到"正视平面"后再测量。

- 需要：至少 4 组不共线的点对应、更复杂的误差分析、以及相机畸变校正的配合；
- 与项目边界冲突：`PROJECT_SPEC.md` §5 明确把"相机畸变校正、亚像素定位、运动模糊复原"列为第一版不做，§1 明确"不追求计量级精度"；
- 识别性问题：本项目的标定素材只提供了**一条直线上的两个点**（尺上的两条刻线），单应矩阵在这种输入下无法唯一确定。

**结论**：在"只有一条直尺、只需要单方向位移、要求每一步可解释"的约束下，方案 C 是可实现、可验证且不超边界的选择。

## 5.2 数学表达与物理意义

`src/calibration.py` 的数学定义（文件头注释原文结构）：

```
P1 = 10 cm 刻线的像素坐标（起点）
P2 = 16 cm 刻线的像素坐标（终点）        [M4 阶段；M5 改为 10 cm → 20 cm]
L_real_mm = 60.0 mm                      [M4；M5 为 100.0 mm]
L_pixel   = sqrt((x2 - x1)^2 + (y2 - y1)^2)
k         = L_pixel / L_real_mm          单位：像素/毫米（px/mm）
1 / k     = L_real_mm / L_pixel          单位：毫米/像素（mm/px）
u         = (P2 - P1) / |P2 - P1|        单位方向向量，方向约定"从 10 cm 指向 16 cm"
```

投影与位移（`project_point()` 与位移模块）：

```
s        = x * ux + y * uy               一维投影坐标（单位：像素）
ds_px    = s - s0                        相对位移（像素）
ds_mm    = ds_px / k                     相对位移（毫米）
```

物理意义逐条解释：

1. **k 是把"画面里的长度"换算成"真实长度"的唯一比例系数**。它由两个已知刻线之间的真实距离与像素距离之比确定，不需要知道拍摄距离与焦距；
2. **u 是"物理运动方向在图像坐标里的方向"**。图像坐标系原点在左上角、x 向右增大、y 向下增大，因此 `uy` 为负号表示直尺沿画面方向略微向上倾斜；
3. **s 是把二维位置压成一维坐标**。这样做的代价是丢失了垂直于 u 方向的信息，收益是位移不再被垂直抖动污染；
4. **s0 是位移零点**，取实验开始后一段静止窗口内有效帧的 s 平均值（M4 为前 0.5 s、至少 10 帧；M5 为前 2.0 s、至少 60 帧）。用平均值而不是首帧，是为了减小单帧噪声对零点的影响；
5. **ds_mm 是最终对外表达的量**，但在 M6 的外部数据上这个换算没有做（原因见下）。

## 6.3 时域测量：周期与频率是怎么算出来的

**极值判定的规则**（`docs/M6.3_FINAL_REPORT.md` §5.1）：先把相邻相同取值合并为"平台块"并取块内帧号中点，再在合并后的序列上用**两侧严格不等号**判定极值；全过程不使用阈值筛选，也不人工挑选或修改极值位置。

**方向约定必须写清楚**：y₀ 是图像坐标，数值增大表示目标在画面中**向下**移动，因此 **y₀ 的局部极大 = 物理最低点**，y₀ 的局部极小 = 物理最高点。

**封板极值清单**：10 个峰 + 10 个谷（frame 85 ~ 231.5、77 ~ 223.5），其中 166.5、223.5、231.5 是 2 帧平台块的中点。

**周期测量的主方法**是峰—峰间隔（9 段）：

| 方法 | 结果 |
| --- | --- |
| 峰—峰间隔（9 段） | **T_exp = 0.542593 s** |
| 谷—谷间隔（9 段） | 0.542593 s |
| 半周期法（19 段，2 × 均值） | 0.542105 s |
| 频率 | **f_exp = 1/T_exp = 1.843003 Hz** |

三种时域方法互差 ≤ 0.09%，在当前数据分辨率范围内一致。

## 6.4 频域交叉验证：FFT 是怎么做的、为什么这么做

FFT 的实现方式（`docs/M6.3_FINAL_REPORT.md` §6）：

- 对**原始** y₀(t) 序列做实数 FFT（rFFT）；
- **仅减去均值**，不做去趋势、不加窗、不补零、不重采样；
- 结果：主峰 **1.875 Hz**，频率分辨率 **df = 0.1875 Hz**，记录长度 5.3333 s。

**为什么这样做**：因为 FFT 在这个项目里的角色是"独立交叉验证"，而不是"更高级的算法"。任何去趋势、加窗、补零都会改变频谱形状，从而引入需要额外解释的处理步骤；只减均值是让它尽可能直接地反映原始序列的主频成分。

**为什么必须说明分辨率**：1.875 Hz 与 1.843003 Hz 相差 1.74%，小于分辨率半格（0.094 Hz，约 5.09%）。因此项目明确写：

> **不能把 1.875 Hz 视为比 1.843003 Hz 更"正确"的结果**，两者属于不同方法在同一数据上的一致性确认。

## 6.6 参数估计：物理参考是怎么来的

M6.3 使用的物理参考不是自己测的，而是**外部资料给出的参数**加**项目采用的标准模型**：

| 参数 | 数值 | 不确定度 | 来源 |
| --- | --- | --- | --- |
| 悬挂质量 m（Lab67 Video 1） | 0.0515 kg | ±0.00005 kg | 归档内 PDF `Equipment values - IV is Amount of Mass on Srping.pdf` |
| 弹簧常数 k | 7.05 N/m | ±0.045 N/m | 同一份 PDF |

模型采用标准质量—弹簧简谐振子：

```
T = 2π √(m / k)        f = (1 / 2π) √(k / m)
```

计算结果：

| 量 | 值 |
| --- | --- |
| T_theory | **0.537018101 s** |
| f_theory | **1.862134625 Hz** |

**两条必须与结果同时出现的声明**：

1. 该模型是**项目采用的标准 SHM 模型**，**不是**外部资料明文给出的完整公式（外部资料要求学生自行查找并陈述理论模型）；
2. 资料**未说明** 0.0515 kg 是否包含全部挂具/夹持件质量，因此这是**条件性的参考计算**。

## 6.7 三方验证：为什么这样验证

项目的验证设计可以概括成一句话：**用三种来源不同的证据去核对同一个数，并明确它们各自的能力边界。**

| 证据 | 来源 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 时域峰谷测量（主结果） | 原始 y₀(t) 序列 | 主振动周期与频率，以及三种时域算法之间的一致性 | 无法排除系统性的定位偏移 |
| FFT 频域交叉验证 | 同一序列的频域变换 | 主频成分是否与时域结果落在同一分辨率格内 | 分辨率 df = 0.1875 Hz，不足以区分 1.843 与 1.875 |
| 标准模型条件性参考 | 外部资料参数 + 项目采用的标准 SHM 模型 | 结果是否落在"物理上说得通"的量级 | 不能归因差异，也不能替代独立测量 |

**差异与边界的完整表述**（`docs/M6.3_FINAL_REPORT.md` §8–§9、`README.md` §6）：

| 量 | 实验值 | 参考值 | 差值 | 相对差异 |
| --- | --- | --- | --- | --- |
| 周期 T | 0.542593 s | 0.537018101 s | +0.005574899 s | **+1.0381%** |
| 频率 f | 1.843003 Hz | 1.862134625 Hz | −0.019131625 Hz | **−1.0274%** |

参数边界：由 m、k 各自不确定度构成的参数矩形给出 f ∈ [1.855281725, 1.868975645] Hz（对应 T ∈ [0.535052451, 0.539001698] s）——实验频率**位于该矩形下界之外**（低于下界约 0.0123 Hz）。

三层不确定度（**不合并、不相加**）：

| 层次 | 名称 | 数值 | 性质 |
| --- | --- | --- | --- |
| A | m、k 给定不确定度的一阶传播尺度 | 周期约 ±0.3228%（±0.0017336 s）；频率约 ±0.006011 Hz | 资料给定值传播，非实测 |
| B | 实验统计不确定度 | SE_T ≈ 0.0038 s；SE_f ≈ 0.0129 Hz | 由 9 个峰间周期样本得到，是统计量，不是误差覆盖边界 |
| C | 采样保守定位上界 | δT ≈ 0.0333 s；δf ≈ 0.1132 Hz | ±0.5 frame/极值的方法学上界，非统计误差 |

**边界结论**（必须整句引用）：

> 当前实验与参考模型之间的差异**超过** m、k 不确定度传播尺度，但**没有超过**本项目设定的保守采样定位上界。

并且必须同时说明：这句话**并不表示**该差异已由采样相关因素完全解释。项目最后明确写"由于缺少弹簧自身质量、挂具/夹持件总质量与阻尼参数等独立测量，当前不能将该差异归因于某一个具体物理因素"。

**为什么必须做到这一步**：因为 1.0% 这个数字最容易被误读。`docs/DEMO_VIDEO_SCRIPT.md` §8 专门为此列出禁语：

- 不得说"测量精度达到 1%"或"误差只有 1%"（应说：与标准模型参考值相差约 1.0%）；
- 不得说"毫米级位移测量"（本阶段位置以像素 y₀ 表达）；
- 不得把外部数据说成"我们自己拍摄的实验视频"；
- 不得出现任何未经仓库文件支持的荣誉、成绩或第三方背书。

这四条禁语本身就是项目对"科研诚实"的具体执行方式：**把结论的口径写在文档里，并且写进演示脚本的红线表，避免在不同场合出现不同说法。**

## 问题 1 Windows 中文路径导致 OpenCV 读取/写入失败

**现象**：`cv2.imread` / `cv2.imwrite` 在含中文的路径下失败（写入时通常静默返回 False，不产生文件，也不抛异常）。

**原因**：OpenCV 的图像读写走的是本地编码路径处理，在本机（用户目录名为中文"杨千贤"）无法正确打开含非 ASCII 字符的路径。

**尝试与最终方案**：改为先把文件读成字节再用 OpenCV 解码，保存时先编码再写字节：

```python
# 读取
data = np.fromfile(path, dtype=np.uint8); img = cv2.imdecode(data, cv2.IMREAD_COLOR)
# 保存
ok, buf = cv2.imencode(".png", img); buf.tofile(path)
```

该方案写在 `src/video_tracker.py` 的 `save_png()`，注释为"Windows 上 `cv2.imwrite` 在含中文的路径下可能失败（本项目路径含中文）"；`CHANGELOG.md` v0.2.0 把它登记为一条"修复"。

**影响**：所有图片输出通道（掩膜、标注图、回退 PNG、最终成果图）都绕开了该问题。**本次复核实测中，我刻意用 `cv2.imwrite` 写到含中文的临时目录并按返回值判定：`cv2.imwrite ok = False`、`exists = False`（静默失败，不生成文件也不抛异常）；换成 `imencode` + `tofile` 后 `ok = True` 且文件正常生成**——说明这不是历史问题，而是本机环境长期存在的约束。

## 问题 2 视频不是预想中的横屏

**原判断**：`PROJECT_SPEC.md` §2 只写"目标在画面中部运动，运动平面与镜头光轴尽量垂直"，**没有写画幅方向**；项目文件中**没有保存**当时对横屏/竖屏的具体预期文字。

**实际检测**：M3 视频 `EXP-002-VIDEO-001.mp4` 实际处理画面为 **1080 × 1920（竖屏）**；`CHANGELOG.md` v0.3.0 原文记录为"程序实际处理画面 1080 × 1920"。

**修正**：在读取第一帧之前调用 `cap.set(cv2.CAP_PROP_ORIENTATION_AUTO, 1)`，并在代码里写明"本模块不手工旋转画面，也不交换 x/y"；`CAP_PROP_ORIENTATION_META` 只做只读记录。

**影响**：M3 的 952 帧全程在这个坐标系下完成检测与验收；紧随其后的 M4、M5 自采视频全部是 1920 × 1080 横屏（本次复核实测），说明"同一套检测算法能跨画幅工作"，但也意味着**不同实验的像素坐标不能直接互相比较**。

| frame 26 | t = 0.432420 s | t = 0.432432 s | 0.432432 s |
| frame 1837 | t = 30.552105 s | t = 30.552998 s | 30.552998 s |

**原因**：旧时间戳对应的 fps ≈ 60.12679，这恰好是**另一段视频**（`EXP-003-STATIC-001.mp4`，本次复核实测 fps = 60.126790）的帧率；修正后的时间戳对应 ≈ 60.12503，即 `EXP-003-STATIC-002.mp4` **自身的**帧率（本次复核实测 60.125033）。也就是说，第一版抽帧用的是"别的视频的帧率"，修正后改用"当前视频的帧率"。

**项目文件的态度**：目录名直接写成"obsolete / wrong fps / ignore"，把错误版本保留在原处而不是删除，也没有在任何文档里掩盖这件事；但**没有留下文字说明是哪一个环节写错了 fps**。

**最终方案**：所有时间轴一律 `time_s = frame_index / fps`，fps 由 `cap.get(CAP_PROP_FPS)` 从当前文件读取，禁止硬编码；`src/external_oscillation_tracker.py` 还额外规定 `time_s` 与 `frame / fps` 的允许差为 `TIME_TOLERANCE_S = 1e-5`。

**影响与教训**：本次复核实测显示，同一部手机在同一天拍摄的 5 段视频 fps 分别为 60.124797 / 60.124948 / 60.125033 / 60.126790 / 60.124978（另有一张 60.124990），彼此都不相同。**"用同一个 fps 处理所有视频"在这个项目里是一个真实会犯的错误**，这也解释了为什么代码里反复强调 fps 必须从文件读取。

## 问题 4 "红色目标"的物理含义在外部数据上不成立

**最初理解**：项目的检测对象是"事先设计好的红色标记"（`PROJECT_SPEC.md` §1 非目标里明确"只针对事先设计好的目标标记"）。M2–M5 自采数据完全符合这个假设。

**后来发现**：M6 使用的外部公开教育视频里**没有**本项目设计的红色标记。如果要继续用"红色目标"，就必须重新调参、重新论证，而且红色区域在这段视频里并不对应一个明确的物理运动量。

**处理过程（M6.2-2A / 2B）**：对"悬挂组件暗带（夹持块）"做了全片 236 帧的受控诊断（检出率、最大连续丢失、bbox/面积范围、高速模糊窗口、误锁检查、f0–73 身份一致性、f74–75 条件放宽测试），最后**冻结**正式视觉方案，并把正式位置特征定为 **暗带上缘 y₀**。

**为什么是上缘，而不是面积 / 质心 / 下缘**（最终报告 §3.2 的论证）：

- 暗带**下缘**位于渐变过渡区，对姿态与阈值更敏感；
- 上缘对应暗带宽度的**强阶跃变化处**，在本数据中重复性更好；
- 上缘与带高 h 之间**不存在代数耦合**（带中心为 y₀ + (h−1)/2、下缘为 y₀ + (h−1)），因此高度变化不会直接污染位置读数。

**如何影响算法设计**：

1. `src/external_oscillation_tracker.py` 明确写明**不调用**红色目标检测器（`src/marker_detector.py`），检测逻辑独立实现，参数单独冻结；
2. 正式轨迹的字段从"中心坐标"改为"暗带上缘 y₀"，同时保留 `x_px`、`bbox_w_px`、`bbox_h_px`、`area_px` 作为**质量控制量**而非位置量；
3. 面积、质心、下缘这三种被否决的方案以文字形式写进最终报告，保留决策痕迹。

## 问题 5 是否应该使用复杂算法（YOLO / Kalman / 深度学习 / ROI）

**考虑过的方案与最终决定**：

| 方案 | 考虑的理由 | 最终是否采用 | 决定依据 |
| --- | --- | --- | --- |
| YOLO / 学习类检测器 | 通用目标检测、对背景变化更鲁棒 | **不采用** | `PROJECT_SPEC.md` §5 禁止；无标注数据、无 GPU；可解释性不满足"逐行解释"要求 |
| Kalman 滤波 | 抑制逐帧检测抖动、预测缺失帧 | **不采用** | §5 禁止；且会引入"预测"语义，导致缺失帧被"补"出来——而本项目在 frame 74–75 的选择恰恰是**保持缺失** |
| 深度学习 / 神经网络（含 PyTorch、TensorFlow） | 端到端学习 | **不采用** | §5 禁止；项目定位是"可解释的图像处理" |
| ROI（感兴趣区域） | 减少搜索范围、提高稳定性 | **分情况采用** | M3 明确禁止"ROI 搜索"（`src/video_tracker.py` 头部）；M6 则采用**固定 ROI**（x ∈ [690,780)、y ∈ [380,760)），因为它是冻结的常量、不随帧变化、可被任何人核对，不属于"自适应搜索" |
| 平滑 / 滤波 / 插值 / 去趋势 / 重采样 | 让曲线更"好看"、让频谱更干净 | **不采用** | 位置序列保持原始采样；FFT 只减均值 |
| 光流 / DIC / 有限元 | 更完整的运动场信息 | **不采用** | §5 禁止；超出本科阶段可解释范围 |

**这条决策的代价与收益**：代价是结果图不够"光滑"、单帧噪声直接进入序列；收益是每一个数值都能追溯到原始像素，任何异常都能在叠加视频里被肉眼定位。

## 问题 6 检测面积异常与"最大轮廓"假设被打破

**现象**：`EXP-003-STATIC-001` 的 track CSV 中，目标面积从 4278.0 px² 一直到 **301,628.5 px²**（本次复核实测；均值 136,875.1 px²）。这个量级显然不是一个小标记的面积，说明画面中出现了更大的红色区域（可能是标记靠近镜头、或画面中出现了其它红色物体）。

**原因**：M2 的检测策略是"取面积最大的红色轮廓"（见第三阶段），它默认"画面里最大的红色区域就是目标"。在拍摄距离或视角变化时该假设会失效。

**尝试与最终方案**：

- M4：引入 **valid gate**（`detected=True` 且 2000 ≤ area ≤ 15000 且 400 ≤ y ≤ 540），把不合格帧标记为 `valid=False`，**位移字段留空**，不删除行；
- M5：为 EXP-004 单独定义 gate（4500 ≤ area ≤ 6500，200 ≤ y ≤ 250），并且**用 import 禁令把两组 gate 彻底隔离**；
- M6.2：为外部视频定义更细的几何约束（连通域面积 ≥ 150 px、行跨度 ≥ 35 px 连续 ≥ 3 行、带宽 40–75 px、带高 ≤ 15 px）与 `MAX_JUMP_PX = 30.0` 的突跳检查（**只做 QC，不做补偿**）。

**影响**：`EXP-003-STATIC-001` 因此**没有位移结果**（前 0.5 s 内 0 个有效帧，规则要求至少 10 帧）；`EXP-003-STATIC-002/003` 的有效帧比例分别为 53.5% 与 60.1%。项目没有为了让结果好看而放宽门限，把"检测到了但不可用"如实记录为 `valid=False`。

## 问题 7 叠加视频写入器可能不可用

**现象**：`cv2.VideoWriter` 在某些环境下无法打开（编码器缺失）。

**最终方案**：`src/video_tracker.py` 使用备选编码器 `OVERLAY_CODECS = ("mp4v", "avc1")`；若都失败，则回退保存最多 `MAX_FALLBACK_PNGS = 5` 张代表性 PNG（起始 / 中间 / 结束 / 最快运动 / 最模糊），并保证 **CSV 照常完整生成**。

**为什么这样设计**：测量数据（CSV）与可视化（视频）的重要性不对等——可视化失败不应影响数据产出。这条原则与"如果需求有变化先改文档再改代码"一样，属于项目早期就定下来的工程纪律。

# 第十阶段：最终项目总结

## 10.1 技术路线

项目最终形成**两条并行、性质不同的技术链**：

**链路一：自采数据的完整测量链（M2 → M5）**

```
自采视频/图像
  → 红色标记检测（HSV 双区间 + 3×3 开运算 + 最大外部轮廓 + 轮廓矩质心）
  → 逐帧 track CSV（frame, time_s, x_px, y_px, area_px, detected）
  → 两点标定（k = L_pixel / L_real，u = 单位方向）
  → 沿物理方向投影 s = x·ux + y·uy
  → 有效帧门限（valid gate）+ s0（静止窗口均值）
  → ds_px / ds_mm（毫米位移）
  → 位移-时间曲线 + 转向点统计
```

**链路二：外部公开数据的方法验证链（M6.2 → M6.3）**

```
外部公开视频（带 SHA-256 校验）
  → 固定 ROI + 灰度阈值 + 暗连通域 + 行宽带
  → 暗带上缘 y₀（正式位置特征）
  → y₀(t) 位置序列（160 帧，未平滑、未插值）
  → 峰谷检测 → 周期 T → 频率 f
  → FFT 频域交叉验证（1.875 Hz，df = 0.1875 Hz）
  → 标准质量—弹簧 SHM 条件性参考（m、k 来自外部资料）
  → 差异 + 三层不确定度 + 证据边界
```

两条链共同的技术特征：**只用 OpenCV / NumPy / Matplotlib 三个库；每一步的参数都被冻结并写入代码常量；每个结论都能追溯到一份 CSV；不使用的技术被明确写进文档与代码注释。**

## 10.3 学到的能力

按"能做什么"而不是"学了什么课"来列：

1. **把物理问题翻译成图像问题**：把"测振动周期"拆成"找一个稳定、可重复、与运动强相关的像素特征"；
2. **可解释视觉方法的基本功**：BGR→HSV 转换、双区间阈值（红色跨色相环两端）、形态学开/闭运算的差别、外部轮廓与面积筛选、轮廓矩求质心；
3. **标定的几何思维**：用两点同时定出尺度与方向，理解"尺度 k 与方向 u 必须绑定在同一次拍摄几何里"，以及"不同视频的标定不能互用"；
4. **数据完整性的工程习惯**：原始文件哈希、逐帧完整记录、不删行、不填值、缺失就标缺失；
5. **有效帧门限的意义**：知道"检测到了"不等于"可用"，懂得用 gate 把不可用帧隔离成 `valid=False` 而不是删掉；
6. **频域分析的分辨率素养**：会用 FFT，也知道 `df = 1/T_record` 决定了自己**能分辨什么、不能分辨什么**（5.3333 s → df = 0.1875 Hz）；
7. **不确定度分层与证据边界**：区分"参数传播尺度""统计标准误""方法学上界"，不把三者相加，也不把差异随便归因；
8. **科研表述的自律**：为"约 1.0%"这个数字专门写禁语，明确它不是精度指标；
9. **版本控制的实操**：分支与默认分支、独立历史、提交粒度、amend 修正、推送与远端状态核对；
10. **文档驱动开发**：先改文档再改代码、每步记录"做了什么/为什么/影响哪些文件"——本项目所有阶段的实际执行都留下了可核对的文字痕迹。

## 10.4 当前不足（客观列出，不做淡化）

**数据与物理层面**

1. 正式验证只用**一段外部公开视频、单一质量**（Lab67 Video 1，51.5 g），没有跨视频、跨质量的一致性验证；
2. 外部视频**没有有效的动态 px/mm 标定**，正式结果以像素 y₀ 表达，**没有毫米位移与振幅**；
3. 视频 30 fps，极值时刻的定位精度受限于单帧 0.0333 s；
4. 正式记录长度只有 5.3333 s，FFT 分辨率只有 0.1875 Hz；
5. 未独立测量弹簧自身质量、挂具/夹持件总质量、阻尼参数，因此**约 1.0% 的差异无法归因**；
6. 自采数据的实验条件（设备、距离、光照、载荷）**没有书面记录**，多数只能从视频文件与代码常量反推。

**工程与方法层面**

7. `EXP-003-STATIC-002/003` 的可用帧比例只有 53.5% 与 60.1%，`EXP-003-STATIC-001` 完全无法生成位移结果——说明"取最大红色轮廓"的策略在拍摄条件变化时会失效；
8. **没有任何自动化测试**（`tests/` 只有 `.gitkeep`），所有验证靠人工跑脚本、人工看图；
9. 项目**没有为目标检测做任何跨场景鲁棒性实验**（不同光照、不同背景、不同距离）；
10. 文档一致性存在 8 条遗留问题（第七阶段问题 12），包括 CHANGELOG 未跟上 M7、AUTHOR_PROFILE 许可表述过期、README 分支提示过期、发布 ZIP 过期、`v1.0` 命名与自定义版本规则冲突、PROJECT_SPEC 未同步。

综合起来，项目当前阶段的准确定位是：**一次视觉测量与证据边界的完整方法验证**；它**不是**一套成熟的高精度实验力学测量系统。

## 10.5 后续升级方向

按"先补证据、再提精度"的顺序排列（与 `PROJECT_SPEC.md` §7、`README.md` §11、演示脚本 S9 的方向一致）：

**第一优先：把证据补齐**

1. **自采多组数据完成动态 px/mm 标定**，让外部/自采结果都能落到毫米量级；
2. **跨视频、跨质量一致性验证**（Lab67 归档里还有 Video 2/3/4，质量标签 91.5 g / 111.5 g / 131.5 g）；
3. **与独立仪器对比**：加速度计、激光位移计或千分表；
4. **补齐实验记录**：真正执行 `EXPERIMENT_PROTOCOL.md` 模板，逐次记录设备、距离、光照、载荷。

**第二优先：提高测量能力**

5. 提高拍摄帧率、延长记录长度，直接改善极值定位与频率分辨率；
6. 引入**亚像素中心定位**（灰度重心或轮廓拟合）提高位移分辨率；
7. 用**相机畸变校正**改善画面边缘精度；
8. **视频抗抖动**（背景特征点稳定化）减小机位微小晃动的影响；
9. 扩展到**二维轨迹**（同时分析 x、y），观察摆动或椭圆轨迹；
10. **多目标同时测量**，观察相对位移。

**第三优先：工程化与物理深化**

11. 尝试**阻尼与有效质量**的独立测量（对应本报告"无法归因约 1% 差异"这一缺口）；
12. **批量处理与简易界面**：一次处理多个视频，或用图形界面选参数；
13. 建立**自动化测试与持续核对**（把现在靠人工跑的 41 项自检、CSV 完整性检查固化为可重复执行的测试）；
14. 拍摄条件对比实验（不同手机、不同帧率、不同距离下的精度对比）。

只有在完成前两类工作、且确有精度需求之后，才考虑 DIC 类全场测量或基于学习的特征跟踪——这也是 `PROJECT_SPEC.md` §7 原文的边界表述。
